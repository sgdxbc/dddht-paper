How do we ensure encoded fragments of an object are not lost simultaneously due to correlated failures, when the failure domains of the system are unknown?
Given that failure domains are probabilistic in our fault model, \sys leverages \emph{random sampling} to address this durability challenge in decentralized settings.
First, let us target a failure domain of a particular size, $n_f$.
We will later generalize the protocol to handle failure domain of all sizes.

For each encoded fragment of an object, every storage node in the system is sampled with a \emph{uniform random distribution}.
The distribution parameter is chosen such that the expected number of selected nodes matches the target redundancy level.
Due to the law of large numbers, as the independent sampling count $m$ increases, the sample count $m_f$ of a failure domain $f$ can be approximated by the system size $N$ and the failure domain size $n_f$:
$$
\frac{m_f}{m} \sim \frac{n_f}{N}
$$
Given $n_f$, we can choose a proper sample count to ensure that, with overwhelming probability, sufficient number of encoded fragments are \emph{not} stored within \emph{any} failure domain of size $n_f$ to recover the original object.
Since there is no failure correlation across failure domains, the scheme is able to tolerate correlated failures of all failure domains of size $n_f$.

\subsection{To a First approximation: Store on All Nodes}

The simulation in \autoref{sec:simulation} hints the importance of large scale placement groups.
Thus, the ideal solution would be pushing the idea to the extreme: store fragments of each data object on every storage node, effectively maximizing every placement group.
As the result, correlated failures are tolerated with the best possible efforts; every node outside the failed domain can assist the repair.
We first describe the general idea of this approach, and discuss its practical deployment later.

\paragraph{Rateless erasure coding.}
This approach is akin to blockchain storage which also populate every data object to the whole network.
However, unlike blockchain that suffers from poor scalability because of its unbounded redundancy, \sys maintains bounded and practical redundancy by deploying erasure code.
With $N$ storage nodes, \sys encodes each data object into $N$ fragments, while every set $k$ fragments can recover the original data object.
The overall redundancy level is $N/k$, which is tunable by varying $k$, which effectively trades redundancy with durability guarantee: \sys can tolerate only up to $N - k$ simultaneous node failures \ie is invulnerable to failure domains consist of up to $N - k$ nodes.
Notice that this threshold is proportional to the total number of storage nodes $N$, showing that \sys is able to provide better durability guarantees without incurring additional redundancy as the system scales up.

Our use of erasure code exposes two challenges.
Erasure code requires each storage node to store a unique encoded fragment to ensure expected recoverability.
As $N$ is expected to be large (\eg in the scale of 10K-100K), coordinating the storage nodes to store unique fragments efficiently is challenging.
Moreover, \sys must continuously schedule the encoding for repairment as the storage nodes constantly leave and join the network.
It is highly challenging if not impossible to ensure the uniqueness of fragments in such dynamical condition in a decentralized system.

\sys addresses these issues using \emph{rateless erasure code}.
Unlike traditional fixed rate codes, rateless erasure code produces an \emph{infinite} sequence of fragments for a data object;
every set of $k+\epsilon$ unique fragments can recover the object.
\sgd{Need to further explain the $\epsilon$ here?}
\sys picks a rateless erasure code as public information in the protocol.
Each storage node encodes a random fragment in the infinite fragment sequence based on the public rateless code.
As such, the probability of two storage nodes storing the same fragment is negligible.

In this section, we elaborate how \sys combines rateless erasure code and verifiable random peer selection to design a durable decentralized storage system.

\subsection{System Model and Assumptions}
We consider a decentralized system in which nodes can freely join and leave.
Each node maintains finite local storage, and the entire set of participants collectively implements a storage system.
\sys exposes a \emph{synchronous} object storage interface with two API calls: \query and \store.
\store takes an object, a private key, and an expiration time, and returns an object ID when the object is successfully stored;
\query takes an ID and returns the object if it exists in the system.
Objects are immutable --- \sys does not provide an explicit interface to update existing objects.
Similar to IPFS, \sys uses content addressing, \ie, an object ID uniquely identifies the content of the object stored.
Issuing a new \store with a different object content is therefore equivalent to an object update.
Mapping client objects to \sys issued IDs is out of scope.
Unlike IPFS, object IDs are private to data owners to protect objects from targeted attacks.

\sys guarantees the following \emph{data durability} invariant.
A direct implication of the invariant is that once a \store successfully returns, all subsequent \query{}s for the returned ID output the original object until expiration.
We use \emph{outer code} to denote the rateless code that a client applies to generate the encoding chunks of an object.
Each chunk is applied another rateless code when storing, referred to as the \emph{inner code} (\autoref{sec:approach:code}).

\begin{invariant}
At any time $t$ after a \store for object $o$ is completed and until $o$ expires, at least $\kout$\footnote{For brevity, both $\kout$ and $\kin$ include $\epsilon$ of rateless code.} encoded chunks of $o$ are \emph{recoverable} with overwhelmingly high probability.
An encoded chunk is recoverable if at least $\kin$ encoding fragments of the chunk are stored on non-faulty nodes.
\label{inv:safety}
\end{invariant}

%As \sys does not support explicit object update, our data durability definition directly implies linearizability~\cite{linearizability} of client \query{}s and \store{}s.

We assume two types of failures that relate to data losses -- storage device failures and Byzantine failures.
Storage device failures lead to unrecoverable data loss of the entire or part of a device.
They are stochastic events: The failure probability of a device is modeled after annualized failure rate (AFR), which depends on factors such as device makes, models, and years of usage~\cite{disk_failure}.
A node exhibiting Byzantine failure can deviate arbitrarily from the protocol, including losing or modifying any data stored locally.
For other types of node failures that are recoverable such as crashes or power failures, we treat them as transient faults.
Permanent node failures are equivalent to nodes leaving the system.

\sys uses a distributed hash table (DHT)~\cite{chash,chord,kademlia}, but mainly for its routing and peer lookup functionality.
We make weak assumptions about the DHT.
A DHT lookup is best-effort, i.e., it returns peers closest to a hash value on the ring with high probability.
%Some \sys optimizations store metadata in the DHT, but only for performance.
%The protocol always guarantees safety (\autoref{inv:safety}) even when DHT loses data or returns wrong data.

We consider a strong Byzantine fault model in which adversaries can collude with each other and generate arbitrary node identities.
We, however, assume a stake-based system, and that adversaries do not possess more than $1/3$ of the system stakes in aggregate, a standard assumption made in proof-of-stake protocols.
Note that using stake is not an inherent part of the protocol.
\sys only leverages stake to defend against strong Sybil attacks; other approaches such as proof-of-work or permissioned settings can also be applied.
%We also assume that adversaries have enough computational power to launch targeted attacks (e.g., DDoS attack) on a small percentage of nodes in the system.
%These attacks can partition the victims from the network during the attack period.
We also make standard cryptography assumptions, i.e., the probability of subverting cryptographic hash functions or public-key cryptography algorithms is negligible.

As shown in \autoref{fig:store}, \sys uses two layers of erasure coding to ensure object durability (\autoref{sec:approach:code}).
When storing an object, a client first applies an outer-layer rateless code to generate a sequence of \emph{encoded chunks}.
It then uses its private key and the object hash to deterministically select a set of chunks from the sequence.
The process is \emph{irreversible}: Even when external parties know the object content, they can only infer the mapping between the encoded chunks and the object with negligible probability.

The client then stores $R$ encoding fragments, where $R$ is large enough to ensure \emph{recoverability} of the chunk, at randomly selected nodes in the system.

Randomly selecting nodes to store chunk fragments is critical to the safety of \sys (\autoref{sec:approach:random}).
To that end, \sys designs a \emph{decentralized} selection protocol with verifiable randomness, as shown in \autoref{fig:selection}.

To choose responsible nodes for a chunk, \sys first uses a cryptographic hash of the chunk to locate candidates on a distributed hash table (DHT)~\cite{chash,chord,kademlia}.
The \emph{candidate set} includes nodes who are in proximity to the chunk hash on the hash ring.
\sys ensures randomness of the candidate set by generating node IDs using a cryptographic hash of their public key~\cite{kademlia}.
%Second, property of rateless coding implies that each fragment in the symbol sequence, and by extension its candidate set, is randomly distributed on the ring.
Note that \sys does not require consensus on the candidate set; each node can use the chunk hash to locate an approximation of the set.

%We impose two restrictions on peer selection from a candidate set: The selection process is fully decentralized, and the selection result is publicly verifiable.
%\sys applies verifiable random function (VRF) to address both challenges.
Each node in the candidate set independently feeds the chunk hash to a publicly-known VRF to generate a random hash and a proof.
Selection outcome is derived from the generated hash, the node ID, and the chunk hash, with the selection probability inversely proportional to the hash distance from the chunk.
The selected nodes present their VRF outputs as a selection proof, which can be publicly verified by any participant of the system.

Storage device failures and node churns can lead to permanent loss of encoding fragments, resulting in violation of the durability invariant.
Similar to prior storage systems, \sys performs \emph{repair} by regenerating new encoding fragments when the number of alive fragments drops below a threshold.
Chunk repair in \sys is fully decentralized.

Nodes storing encoding fragments for the same chunk form a \emph{chunk group}.
Chunk group members periodically broadcast their fragments to other, potentially new, members verified by the selection process.
Once a new member receives enough fragments, it decodes the original chunk, generates a new encoding fragment, and joins the group.
As argued in \autoref{sec:approach:code}, properties of our rateless code facilitate lazy and consensus-free repair, both critical conditions for effective repairs in an asynchronous, decentralized network.

\subsubsection{Durability of the inner-code}

The durability of our protocol hinges on the invariant that at least $k$ fragments in each group will persist after some bounded time $T$. The resultant number of persistent fragments varies from time due to the innate randomness of the system.

The durability of each group can be analyzed by a continuous-time Markov chain (CTMC) model.

It is important to note that if a group dips below $k$ fragments, it might never recover. These group states are therefore impossible transition out of and typically referred to as \textit{absorbing states}, \textit{non-absorbing states} are referred to as \textit{transient states}.

As $T\rightarrow\infty$, the probability a group reaches an \textit{absorbing state} converges to 1. However, we can assert that with some system parameters the groups will reach an absorbing state in $T=t$ steps with a negligible probability.

\begin{lemma}
    For a single data object, the probability that all groups injectively responsible for $K+R$ chunks, being durable at $T=t$ can be bounded by:
    \begin{gather}
        1-(1-\sum_{T=1}^{t} (I \Theta^{T})_{n-k+1})^{K+R}
    \end{gather}
    Where $I$ is the initial state matrix and $\Theta$ is a stochastic matrix.
\end{lemma}

In the CTMC model, we first express the set of initial states of our system and the probabilities associated with those states as a $(n-k+1 \times 1)$ initial probability vector $I$. Since our group identities must be unique, $I$ can be constructed utilizing the hypergeometric distribution PMF.

We then construct a $(n-k+1 \times n-k+1)$ stochastic matrix $\Theta = (\theta_{i,j})$ representing the transition probabilities of one state to another. Where the rows represent the starting states and the columns representing the transitioned state. Where \textit{transient to transient} states and \textit{transient to absorbing} states are a function of the churn rate as well as an eviction parameter. Whilst intuitively, \textit{absorbing to absorbing} states are expressed as a $(1 \times n-k+1)$ vector of zeros with the $(n-k+1)^{th}$ element being $1$.

With the stochastic matrix, we perform the sum and exponent to derive the probability any group of a data object reaching an absorbing state at $T=t$ as (1).

With our given system parameters, if the probability is negligible ($\leq 2^{-128}$), durability for the whole data object is guaranteed within $T=t$.

\subsubsection{Durability of the outer-code}

Suppose we have an adversary that has the capability to receive accurate reports on every possible group's membership and possess the ability to forcefully disconnect $\phi$ nodes from the system. The adversary could thus force a group to pre-maturely enter an \textit{absorbing state}.

The purpose of the outer-code is to deter such targeted attacks.
More precisely, we ensure that if it does succeed, there is high probability it will not compromise the durability of any data object.

\begin{lemma}
    Suppose, each node can hold at most $\mu$ fragments.
    The probability of an attacker successfully attacking a data object is bounded by:
    \begin {gather}
        1-
        \left(
        1-\prod_{i=1}^{R}\frac{K+R-i}{\Omega(K+R)-i}
        \right)^{\binom{\Phi*\mu}{R+1}}
    \end{gather}

\end{lemma}

To draw an upper-bound on the attackers' success, we assume that it can successfully compromise a maximum of $\Phi = \phi$ groups or chunks out of a total $\Omega*(K+R)$ chunks, where $\Omega$ is the total number of data objects.
This upper-bound is simply an extension to the birthday attack problem.

Similarly, with the correct system parameters, we can ensure the adversaries' probability of success to be negligible, ensuring durability with high probability.

VRF generates a hash $h$ and a proof $\pi$.
By dividing $h$ by the total hash space, Kleroterion interprets the VRF output as a random real number between 0 and 1.

To simplify protocol exposition, we assume each node having exactly one unit of stake.
If a user possesses $n$ units of stake, it creates $n$ virtual nodes, each with a single unit of stake.
To randomly select $K$ nodes out of $S$ total nodes ($S$ is the total units of stake in the system), we set a boolean value $c$ to true if the interpreted VRF output falls below $\frac{K}{S}$.
Once a node is selected, Kleroterion uses the VRF output hash modulo $2^D$, where $D$ is the width of the total encoding space, to assign the index of the fragment $\var{idx}$ within the encoding stream.
Due to the large encoding space, randomness of VRF ensures negligible fragment collision rate across eligible nodes.

Nodes periodically disseminate persistence proofs of their stored fragments.
To verify that a node is selected by Kleroterion to store a fragment in epoch $e$, the \fn{VerifyFrag} procedure feeds the public key of the node, the claimed hash and proof generated by the VRF, and the concatenated object hash $oh$ and $e$ into the \fn{VerifyVRF} function.
If the verification passes, the procedure uses the same way to calculate $c$ and $\var{idx}$.
It then calculates the fragment hash from the object hash $\var{oh}$ and the index $\var{idx}$, and checks if it matches the persistence proof.
Note that deriving the fragment hash from the object hash alone --- without the full object --- requires \emph{homomorphic hashing}.
We apply the same homomorphic hashing scheme designed in \cite{homo_hash}.

\paragraph{Handling gossip messages.}

\begin{algorithm}[t]
    \begin{algorithmic}[1]
        \Procedure{RecvMsgObj}{$\var{hash}$}
            \State $\langle h, \pi, c, idx \rangle \gets \fn{Kleroterion}(\var{hash}, 0)$
            \If{$c$}
                \State $\var{obj} \gets$ retrieve object from source
                \State $\fn{ConstrFrag}(\var{obj}, \var{hash}, h, \pi, \var{idx}, 0)$
            \EndIf
        \EndProcedure
        \Procedure{RecvMsgFrag}{$\var{oh}, e, h, \pi, \var{fh}, \var{pk}$}
            \If{$\neg \fn{VerifyFrag}(\var{oh}, e, h, \pi, \var{fh}, \var{pk})$}
                \Return
            \EndIf
            \If{$\var{oh} = \var{pnd.hash}$}
                \State $\var{pnd.frags} \gets \var{pnd.frags} \cup \set{\var{fh}}$
            \EndIf
            \State $\langle h, \pi, c, idx \rangle \gets \fn{Kleroterion}(\var{oh}, e + 1)$
            \If{$c$}
                \State $\var{next[oh].proof} \gets \langle e + 1, h, \pi, \var{idx}\rangle$
                \State $\var{next[oh].alive} \gets \var{next[oh].alive} \cup \set{\var{fh}}$
                \State $\var{frag} \gets$ fetch fragment from source node
                \State $\var{next[oh].frags} \gets \var{next[oh].frags} \cup \set{\var{frag}}$
            \EndIf
        \EndProcedure
    \end{algorithmic}
    \caption{Procedures to handle gossip messages}
    \label{alg:gossip-handler}
\end{algorithm}

An \sys node receives two type of gossip messages, \mtype{obj} and \mtype{frag}.
A client sends \mtype{obj} when storing an object, while \mtype{frag} is a fragment persistence proof sent by nodes periodically.

As shown in \autoref{alg:gossip-handler}, when a node receives a \mtype{obj}, it invokes Kleroterion to determine if it is chosen to store a fragment for the object in the initial epoch.
Chosen nodes fetch the object from the requesting client, and then invoke \fn{ConstrFrag} to construct and store their responsible fragments.
Details of \fn{ConstrFrag} will be introduced later.

When a \mtype{frag} is received, the node first verifies the correctness of the persistence proof by invoking \fn{VerifyFrag}.
Invalid fragments are immediately rejected.
If the fragment matches the inflight client request, the node adds the fragment hash to the pending list.
It then invokes Kleroterion, similar to the \mtype{obj} handler, to determine its eligibility for storing the object in the subsequent epoch.
If the node is responsible, it fetches and stores the fragment from the source, and starts monitoring persistence proofs of the object.

Periodically, \sys nodes broadcast persistence proofs of its store fragments, and check if they need to generate new encoding fragments.
The procedure is shown in \autoref{alg:monitor}.
In a periodic timer handler, for each fragment $f$ currently stored in its local storage, the node disseminates a persistence proof for $f$ through the gossip protocol.
Then for each object which the node is chosen by Kleroterion for the subsequent epoch, the node invokes \fn{RequireRepair} on the current alive fragments to determine if it needs to generate new encoding fragment.
The procedure checks if the node is aware of $k_p$ alive fragments in the \emph{same epoch}.
We add the epoch constraint to defend against Byzantine nodes generating persistent proofs in advance.
If regeneration is required, the node invokes \fn{ConstrFrag}.
\fn{ConstrFrag} uses the rateless erasure code to produce the corresponding encoding.
It then stores the new fragment locally, together with the persistence proof, and subsequently update the DHT for subsequent \query operations.

\subsection{Optimizations}
\label{sec:protocol:optimization}

\paragraph{Repair booster to reduce repair traffic.}
One problem with \sys is that it can suffer from amplified network traffic caused by repair.
Each responsible peer needs to individually fetch $k + \epsilon$ fragments before generating one fragment.
This issue can be addressed by a set of repair booster peers, who fetch fragments, decode objects, and generate fragments on behalf of responsible peers.
Thanks to VRF, booster peers can independently verify the responsibility of peers.
And with homomorphic hashing, peers can verify the fragments generated by booster peers.
Booster nodes perform best-effort caching after recovering data objects.
When another fragment needs to be generated later for the same object, the node avoids fetching the fragments again.
This can significantly reduce repair traffic.
Any peer participating in \sys can behave as a booster node, but heuristically the node who recently has been chosen for an object is a good choice.

Note that faulty booster nodes has no effect on object durability, but can only increase network usage.

\paragraph{Batching gossip messages.}
We can batch gossip messages to further reduce network traffic.
Persistence proof are usually tiny messages, approximately 100 bytes.
Nodes can delay and send a batch of messages in single gossip, reducing the bandwidth requirement of gossip significantly.
Thanks to lazy repair, the timer interval is long, normally from several hours to up to once per day, so a small delay on gossip will not induce unnecessary repairs.

\paragraph{Reduce redundancy caused by bursty repair.}
Since every node individually monitors objects without explicit coordination, when repair threshold is reached, several nodes' may simultaneously regenerate encoding fragments.
To ameliorate this issue, when a node checks for object persistence, it can filter out fragments with hash values lower than the local one.
