This section gives a detailed description of the \sys protocol we overviewed in \autoref{sec:approach}.

\subsection{System Model and Assumptions}
We consider a decentralized system in which nodes can freely join and leave.
Each node maintains finite local storage, and the entire set of participants collectively implements a storage system.
\sys exposes a \textit{synchronous} object storage interface with two API calls: \query and \store.
\store takes an object and an expiration time, and returns an ID when the object is successfully stored;
\query takes an object ID and returns the object if it exists in the system.
%\lijl{Should we clarify that object ID is the hash of the object here?}
%\sgd{If we do clarify, we can also mention verifiable result by comparing hashes.}
Objects are immutable --- \sys does not provide an explicit interface to update existing objects.
Similar to IPFS, \sys uses content addressing, i.e., an object ID uniquely identifies the content of the object stored.
Issuing a new \store with different object content, therefore, is equivalent to an object update.
Consistently mapping client objects to \sys issued IDs is out of the scope of the paper.

\sys guarantees \textit{data durability}.
Once a \store successfully returns, all subsequent \query{}s for the generated ID return the original object until is object is expired.
As \sys does not support explicit object update, our data durability definition directly implies linearizability~\cite{linearizability} of client \query{}s and \store{}s.

We assume two types of failures that relate to data losses -- storage device failures and Byzantine failures.
Storage device failures lead to unrecoverable data loss of the entire or part of a device.
They are stochastic events: The failure probability of a device is modeled after annualized failure rate (AFR), which depends on factors such as device makes, models, and years of usage~\cite{disk_failure}.
A node exhibiting Byzantine failure can deviate arbitrarily from the protocol, including losing or modifying any data stored locally.
For other types of node failures that are recoverable such as crashes or power failures, we treat them as transient faults.
Permanent node failures are equivalent to nodes leaving the system.

We consider a strong Byzantine fault model in which adversaries can collude with each other and generate arbitrary node identities.
We, however, assume a stake-based system, and that adversaries do not possess more than $1/3$ of the system stakes in aggregate, a standard assumption made in proof-of-stake protocols.
Note that using stake is not an inherent part of the protocol.
\sys only leverages stake to defend against strong Sybil attacks; other approaches such as proof-of-work or permissioned settings can also be applied.
We also assume that adversaries have enough computational power to launch targeted attacks (e.g., DDoS attack) on \XXX \% of the nodes in the system.
These attacks can partition the victims from the network during the attack period.

We also make standard cryptography assumptions, i.e., the probability of subverting cryptographic hash functions or public-key cryptography algorithms we used in the protocol is negligible.

\subsection{Design Overview}

\sys uses two layers of erasure coding to ensure durability of stored objects.
It first applies a fixed-rate erasure code to encode each object into a set of \emph{encoded chunks}.
\lijl{Does it matter if we use fixed-rate or rateless code for outer code?}
\sgd{A fixed-rate code will generate finite enumerable fixed-content fragments, which could be used to trace data object by attackers.}
For each chunk, \sys then uses a publicly-known rateless erasure code to generate an infinite stream of \emph{encoding fragments}.
The encoding fragments for a chunk are stored on a dynamic set of \sys nodes, collectively termed a chunk group.
As introduced in \autoref{sec:background:code}, an encoded chunk can be reconstructed from any $k + \epsilon$ distinct encoding fragments with overwhelmingly high probability, and any $k$ distinct encoded chunks can recover the original object.
To guarantee data durability, \sys enforces the following invariant: \lijl{should we use different k for each definition}

\begin{invariant}
At any time $t$ after a \store for object $o$ is completed and until $o$ expires, at least $k$ encoded chunks of $o$ are \emph{recoverable} with overwhelmingly high probability.
An encoded chunk is recoverable if at least $k + \epsilon$ encoding fragments of the chunk are stored on non-faulty nodes which are free from targeted attacks.
\end{invariant}

\paragraph{Chunk repair.}
Storage device failures and node churns can lead to permanent loss of encoding fragments, resulting in violation of the durability invariant.
Similar to prior storage systems, \sys performs \emph{repair} by regenerating new encoding fragments when the number of alive fragments for a chunk drops below a threshold.
To avoid relying on a centralized trusted service, chunk repair in \sys is fully decentralized.
Each node in a chunk group periodically sends \emph{persistence proof} of its stored fragments to other peers in the group.
When repair condition is met, nodes in the chunk group selects new peers who generate and store new encoding fragments of the chunk.

\paragraph{Randomized peer selection.}
Peer selection is critical to the safety of \sys.
If not done carefully, adversaries can collude and claim persistence of enough fragments for a chunk such that less than $k + \epsilon$ fragments are stored on honest nodes.
Once those adversaries discard their local fragments, the chunk is permanently lost.

\sys implements a decentralized peer selection protocol with verifiable randomness to address the issue.
%The protocol leverages two sources of randomness: a cryptographic hash of the fragment and randomness from a verifiable random function (VRF).
When selecting peers to store the next fragment, nodes in the group use a cryptographic hash of the fragment to locate candidates on a distributed hash table (DHT)~\cite{chash,chord,kademlia}.
The \emph{candidate set} includes nodes whose IDs are close to the fragment hash on the DHT hash ring.
\sys ensures randomness of the candidate sets through two mechanisms.
First, nodes are randomly distributed on the hash ring by generating IDs using a cryptographic hash of their public key~\cite{kademlia}.
Secondly, property of rateless coding implies that each fragment in the encoding sequence, and by extension its candidate set, is randomly distributed on the ring.
Note that \sys does not require group peers to reach consensus on the candidate set.
Each peer can independently derive the \emph{same} fragment hash and locate an approximation of the set.

We impose two restrictions on peer selection from a candidate set: The selection process is fully decentralized, and the selection result is publicly verifiable.
\sys applies verifiable random function (VRF) to address both challenges.
Upon request, a node in the candidate set independently runs a publicly known VRF to generate a selection proof.
The selection probability is inversely proportional to its distance to the fragment on the hash ring.
The selection proof is unforgeable and verifiable.
This decentralized process may lead to selection of zero or more than one peers, both of which are easily handled by our storage scheme.
Randomness of both the candidate set and the peer selection process ensures that every node has equal probability of participating in a chunk group.

\paragraph{Double-layer encoding to tolerate targeted attacks.}
Fragment repair, unfortunately, reveals node identities of a chunk group.
Adversaries can launch targeted attacks to the entire group which breaks recoverability of the chunk.
\sys leverages the \emph{irreversibility} property of the outer-layer erasure coding to tolerate such attacks.
Specifically, when encoding an object to a set of chunks, the client never reveals the membership of the set.
It either keeps the hash of each chunk as a secret, or reconstructs the hashes upon object retrieval using homomorphic hashing schemes~\cite{homo_hash}.
\sys nodes, including the adversaries, can only observe identities of individual encoded chunks but are incapable of identifying which chunks belong to the same object.
Consequently, adversaries can not do better than launching targeted attacks to a small random selection of chunks in the system.
With a limited attack capability (\XXX\% of the nodes), \sys only requires low redundancy for its outer-layer erasure coding to ensure that enough encoded chunks can be retrieved to reconstruct the original object.

\paragraph{Retrieving objects.}
To retrieve an object, a client needs to recover $k$ of its chunks, each of which requires reading $k + \epsilon$ distinct encoded fragments.
Locating alive encoded fragments for a chunk is more challenging in \sys given the dynamic nature of chunk group membership.
To facilitate object lookup, \sys nodes register a \emph{fragment pointer} in the DHT (using chunk hash as the key) when storing a new fragment, and deletes the pointer when the fragment is garbage collected.
To reconstruct a chunk, the requesting node queries the DHT to retrieve $k + \epsilon$ distinct pointers and fetches the respective encoding fragments.
Fragment pointer registration, however, is only best-effort.
If less than $k + \epsilon$ pointers for a chunk are found in the DHT, \sys applies another level of indirection.
Since \sys nodes monitor fragment persistence of other peers in a group, chunk group membership can be retrieved by contacting just a few nodes in the group.
In the worst case where no fragment pointer is found, the requesting node either performs a linear search of the encoding fragment stream, or disseminates a chunk query request using a gossip protocol.

            \State \Return $\var{frags}$
        \EndProcedure
    \end{algorithmic}
    \caption{\sys client protocol}
    \label{alg:client}
\end{algorithm}

\autoref{alg:client} lists the client side protocol of \sys.
Being a decentralized peer-to-peer system, client operations are issued on participating nodes, though they can also serve as proxies for light-weight clients.
We use \textit{client} to denote the peer node that issues a client operation.

To store an object, a client uses the outer layer encoding function to generate a set of encoded chunks.
For each chunk, the client applies the inner layer code to get a stream of fragments.
It stores $k_{inner}$ of them at responsible peers.
Peer selection for a fragment is performed by the $\fn{Locate}()$ procedure, which we further elaborate in \autoref{sec:protocol:detail:ps}.
If no responsible peer is found, the client skips the fragment and continues down the stream, until $k_{inner}$ fragments are properly stored.
As there is no dependency among the different chunks and fragments, the client can perform peer selection and store request for all fragments in parallel.
Once enough fragments are stored, the client also forwards the chunk group membership to each peer in the group.

To query an object, requesting client reconstructs $k_{outer}$ encoded chunks from its list of chunk hashes.
For each chunk hash, the client first queries the DHT to retrieve a list of fragment pointers.
It contacts the pointed nodes and requests for the corresponding fragment.
If the contacted node is still an active member of the chunk group, it also returns its view of other alive group members to the client, who can request for additional fragments.
The process terminates when $k_{inner}$ fragments are collected.
If not enough fragments are collected, the client enters a slow path to linearly search for additional fragments.
It uses homomorphic hashing of the inner layer code to generate a stream of fragment hashes, and requests each fragment from responsible peers using the $\fn{Locate}()$ function.
As the rear end of the membership window slides at fixed time interval, the client can start the search at an estimated stream index of the current chunk group.

This reduces the search time from linear to constant in the common case.
Once $k_{inner}$ fragments are retrieved, the client uses the inner layer decoding function to reconstruct the chunk.
Finally, the original object is recovered by applying the outer layer decoding on $k_{outer}$ reconstructed chunks.

\subsubsection{Peer Selection}
\label{sec:protocol:detail:selection}

\begin{algorithm}[t]
    \begin{algorithmic}[1]
        \Procedure{Locate}{$\var{hash}$}
            \State $\var{candidates} \gets \fn{DHT-Lookup-Nodes}(\var{hash})$
            \State $\var{nodes} \gets \set{}$
            \ForAll{$\var{c} \in \var{candidates}$}
                \State $\langle r, \pi, s \rangle \gets \fn{SelectionProof}_{c}(\var{hash})$
                \If{$s \land \fn{VerifySelection}(\var{hash}, r, \pi, \var{pk}_{c})$}
                    \State $\var{nodes} \gets \var{nodes}$ $\cup$ $\set{\var{c}}$
                \EndIf
            \EndFor
            \State \Return $\var{nodes}$
        \EndProcedure
        \Procedure{SelectionProof}{$\var{hash}$}
            \State $\var{db} \gets \fn{DistanceBucket}(\var{hash}, \var{ID})$
            \State $\langle \var{r}, \pi \rangle \gets \fn{VRF}_{sk}(\var{hash})$
            \State $s \gets r < 2^{hashlen - \var{db}}$
            \State \Return $\langle \var{r}, \pi, s \rangle$
        \EndProcedure
        \Procedure{VerifySelection}{$\var{hash}, r, \pi, \var{pk}$}
            \If{$\neg \fn{VerifyVRF}_{pk}(r, \pi, \var{hash})$}
                \Return false
            \EndIf
            \State $\var{nID} \gets \fn{NodeID}(\var{pk})$
            \State $\var{db} \gets \fn{DistanceBucket}(\var{hash}, \var{nID})$
            \State \Return $r < 2^{hashlen - \var{db}}$
        \EndProcedure
        \Procedure{DistanceBucket}{$\var{a}, \var{b}$}
            \State \Return $\frac{|a - b|}{\var{BucketSize}} + 1$
        \EndProcedure
    \end{algorithmic}
    \caption{\sys peer selection protocol}
    \label{alg:selection}
\end{algorithm}

As shown in \autoref{alg:selection}, \sys uses verifiable randomness to select nodes to store encoding fragment in a decentralized manner.
The procedure first invokes $\fn{DHT-Lookup-Nodes}()$ to get a list of candidate nodes.
The function is a simple variant of the original DHT lookup~\cite{chord} and returns the $N$ immediate successor nodes of the hash value on the ring.
\sgd{closest nodes}
Note that each lookup may return a different candidate set due to the dynamic and decentralized nature of DHT.
However, all final selection will include an unforgeable selection proof, and the protocol tolerates multiple responsible nodes for a fragment.
\lijl{I think that's fine. Might need to argue that somewhere.}

For each candidate in the set, the caller requests the node for a \emph{selection proof} for the fragment.
The selection probability of a node is inversely proportional to its distance to the fragment hash.
To do so, \sys divides the hash ring into \emph{buckets}, each with hash length $BucketSize$.
The requested node first calculates its distance in unit of buckets to the fragment hash.
It then feeds its secrete key $sk$ and the fragment hash into a public-known VRF.
The VRF outputs a random hash $r$ and a proof $\pi$.
Properties of VRF ensure that $r$ is uniformly distributed between $0$ and $2^{hashlen}-1$.
By comparing $r$ to a fraction of the total hash space exponential to the distance, the probability of the node being selected drops exponentially with each bucket away from the fragment hash.
\lijl{We need to empirically verify the likelihood of finding a responsible peer for a fragment.}

Once the caller receives a selection proof, it inputs the random hash $r$, the proof $\pi$, the fragment hash, and the public key of the prover to the $\fn{VerifyVRF}$ function.
The function verifies that the random hash is properly generated by the prover using the same fragment hash input.
If $\fn{VerifyVRF}()$ passes, the caller follows the same procedure in $\fn{SelectionProof}()$ to verify node selection.
The $\fn{NodeID}()$ function derives the ID of the node, by calculating a SHA256 hash of its public key.

\subsubsection{Chunk Group Maintenance}
\label{sec:protocol:detail:group}

\begin{algorithm}[t]
    \begin{algorithmic}[1]
        \Procedure{MembershipTimer}{}
            \For{$i \in (\wl$ $..$ $\wh)$}
                \If{$\var{group}.contains(i)$}
                    \If{$\var{group}[i]$ not lived}
                        \State $\var{group} \gets \var{group} \setminus \set{\var{group}[i]}$
                    \EndIf
                \Else
                    \State $\var{fhash} \gets \fn{InnerEncodeHash}(\var{chash}, i)$
                    \State $\var{nodes} \gets \fn{Locate}(\var{fhash})$
                    \ForAll{$\var{n} \in \var{nodes}$}
                        \If{$\fn{QueryHasFrag}(\var{fhash})$}
                            \State $\var{group} \gets \var{group} \cup \set{n}$
                            \State break
                        \EndIf
                    \EndFor
                \EndIf
            \EndFor
        \State $\fn{UpdateWmarkH}()$
        \If{$|group[\wl $ $..$ $\wh]| < n_{inner}$}
            \State $\fn{RepairChunk}(\var{chash})$
        \EndIf
        \EndProcedure
        \Procedure{HeartbeatTimer}{$\var{frag}, \var{i}$}
            \State $\var{fhash} \gets \fn{Hash}(\var{frag})$
            \State $\langle r, \pi, s \rangle \gets \fn{SelectionProof}(\var{fhash})$
            \ForAll{$\var{n} \in \var{group}$}
                \State $\fn{Send}(\msg{HeartBeat}{\var{chash, fhash, i, \langle r, \pi, s \rangle}})$
            \EndFor
        \EndProcedure
        \Procedure{RecvHeartBeat}{$\var{fhash}, i, \langle r, \pi, s \rangle$}
            \If{$\neg \var{chash} \in \var{store}$}
                \State \Return
            \EndIf
            \If{$i < \wl$}
                \State \Return
            \EndIf
            \If{$s \land \fn{VerifySelection}(\var{fhash}, r, \pi, \var{pk}_{sender})$}
                \State $\var{group} \gets \var{group} \cup \set{sender}$
                \State // refresh sender peer liveness
            \EndIf
        \EndProcedure
        \Procedure{UpdateWmarkH}{}
            \State $\var{nAlive} \gets 0$
            \For{$i \in (\wl$ $..$ $\wh)$}
                \If{$\var{group}.contains(i)$}
                    \State $\var{nAlive} \gets \var{nAlive} + 1$
                    \If{$\var{nAlive} \ge n_{inner}$}
                        \State $\wh \gets i$
                        \State \Return
                    \EndIf
                \EndIf
            \EndFor
        \EndProcedure
        \Procedure{UpdateWaterLTimer}{}
            \State $\var{group} \gets \var{group} \setminus \set{\var{group}[\wl]}$
            \State $\wl \gets \wl + 1$
        \EndProcedure
    \end{algorithmic}
    \caption{Procedures to maintain group membership}
    \label{alg:membership}
\end{algorithm}

For each stored fragment, a node maintains a local view of the current chunk group membership (the $\var{group}$ state in \autoref{fig:node-state}).
The inaugural group peers receive the membership from the client issuing the \store (\autoref{alg:client}).
However, peers may fail to receive client issued membership.
Temporary network asynchrony can also lead to divergence in membership views across peers.
To handle such cases, each peer periodically calls $\fn{MembershipTimer}()$ (\autoref{alg:membership}) to \emph{eventually} synchronize on membership views.
The procedure linearly search the fragment hash stream of the chunk from \wl to \wh, and for each missing member, it attempts to locate a responsible peer that currently stores the corresponding fragment.
When new members are located, the node also updates \wh ($\fn{UpdateWmarkH}()$) according to the following invariant: the number of unique fragments between \wl and \wh is at most $k_{inner}$.
\sgd{unique fragments that be holden by unique peers.}
A corollary is that \wh may drop when new peers are added to the membership.
We, however, do not remove peers beyond the updated \wh from the view; those peers effectively serve as extra redundancy, and this approach reduces unnecessary repairs due to view divergence.
If the number of alive peers in the membership windows drops below a threshold, the procedure starts the repair process which we elaborate in \autoref{sec:protocol:detail:repair}.

To detect failures in a chunk group, group members periodically broadcast fragment persistence claims to other peers in the group ($\fn{PeriodicHeartbeatTimer}()$).
The persistence claim includes the hash of the chunk and the fragment, the index of the fragment within the encoding stream, and the selection proof generated by the node.
To reduce the cost of generating fragment hashes and selection proofs every timer interval, nodes can store them alongside the fragment.

When a node receives a heartbeat message, it ignores the message if it is not part of the chunk group or the sender is below \wl.
Otherwise, the node refreshes the sender's liveness in its local view.
The sender may not be in the node's local view in a few scenarios: the node's local view is not complete; temporary network partition between the nodes caused by asynchrony; the sender is a new member, but the node was not informed.
In any case, the node verifies the selection proof, adds the sender to its local membership view, and updates \wh.

Adversary nodes can arbitrarily extend their membership (with or without holding their fragments).
Since honest nodes eventually leave or fail, if we allow nodes to stay in a chunk group indefinitely, the group may eventually be occupied by enough faulty nodes such that \emph{recoverability} is violated.
To ensure recoverability, \sys enforces that a node has a bounded lifetime in a chunk group.
To do so, each node periodically removes peer at the \wl position in a group, and increments \wl.

\subsubsection{Repairing Encoded Chunks}
\label{sec:protocol:detail:repair}

\begin{algorithm}
    \begin{algorithmic}[1]
        \Procedure{RepairChunk}{$\var{chash}$}
            \State $\wh \gets \wh + 1$
            \If{$\neg \var{group}.contains(\wh)$}
                \State $\var{fhash} \gets \fn{InnerEncodeHash}(\var{chash}, i)$
                \State $\var{nodes} \gets \fn{Locate}(\var{fhash})$
                \ForAll{$n \in \var{nodes}$}
                    \State $\fn{Send}(\msg{RepairRequest}{\var{chash}, \var{fhash}, i, \var{group}})$
                \EndFor
            \EndIf
        \EndProcedure
        \Procedure{RecvRepairRequest}{$\var{chash}, \var{fhash}, \var{i}, \var{g}$}
            \If{$\var{store}.contains(\var{chash})$}
                \State \Return
            \EndIf
            \If{$\fn{InnerEncodeHash}(\var{chash}, i) \ne \var{fhash}$}
                \State \Return
            \EndIf
            \State $\langle \var{r}, \pi, s \rangle \gets \fn{SelectionProof}(\var{fhash})$
            \If{$\neg s$}
                \State \Return
            \EndIf
            \State $\fn{MergeView}(g)$
            \State $\fn{StartRepairTimer}(\var{chash}, i)$
        \EndProcedure
        \Procedure{MergeView}{$g$}
            \ForAll{$n \in g$}
                \If{$n.i \ge \wl \land \neg \var{group}.contains(n.i) \land n.s \land \fn{VerifySelection}(\var{n.fhash}, n.r, n.\pi, \var{pk}_{n})$}
                    \State $\var{group} \gets \var{group}$ $\cup$ $\set{sender}$
                \EndIf
            \EndFor
        \EndProcedure
        \Procedure{RepairTimer}{$\var{chash}, i$}
            \ForAll{$n \in \var{group}$}
                \If{$\neg \var{rfrags}.contains(n.i)$}
                    \State $\var{frag} \gets \fn{RequestFrag}(\var{chash}, n.i, \langle \var{r}, \pi, s \rangle)$
                    \State $\var{rfrags} \gets \var{rfrags} \cup \set{\var{frag}}$
                \EndIf
            \EndFor
            \If{$|\var{rfrags}| \ge k_{inner}$}
                \State $\var{chunk} \gets \fn{InnerDecode}(\var{rfrags})$
                \State $\var{frag} \gets \fn{InnerEncode}(\var{chunk}, i)$
                \State $\var{store} \gets \var{store} \cup \set{\var{frag}}$
                \State $\fn{StopRepairTimer}(\var{chash}, i)$
            \EndIf
        \EndProcedure
    \end{algorithmic}
    \caption{Protocol to repair encoded chunk}
    \label{alg:repair}
\end{algorithm}

The core of \sys centers around a \emph{decentralized} repair protocol that ensures the durability of encoded chunks.
As listed in \autoref{alg:repair}, when a node detects that repair is necessary for a chunk, it calculates the next fragment hash in the encoding stream as marked by \wh.
If the node's local view includes extra redundancy at \wh, the repair process can be skipped.
It then invokes $\fn{Locate}()$ to find the responsible peers for the fragment, and sends them a \mtype{RepairRequest} message.
The message includes the chunk hash, the repair fragment hash and its index in the stream, as well as the node's local membership view.

Upon receiving a \mtype{RepairRequest}, the node verifies that the fragment hash is correct, and that it is responsible for the fragment.
\lijl{Probably also need to check requester is a legitimate peer?}
The later can be checked by invoking $\fn{SelectionProof}()$.
It then merges the incoming view with its local chunk membership, adding in peers who have correct selection proofs.
The node then starts the repair process.
Specifically, it requests fragments from each group member in its local view.
Each request includes its selection proof for verification.
Once the node receives $k_{inner}$ or more encoding fragments, it uses the inner decoding function to recover the original chunk, then applies the rateless encoding function to construct its responsible fragment, completing the repair process.
Note that the node may not find enough fragments initially due to incomplete membership view or network asynchrony.
Subsequent \mtype{RepairRequest}{}s from other peers initiating repair will update the membership view through $\fn{MergeView}()$.
The node also periodically runs $\fn{MembershipTimer}()$ to find new peers that are alive.
By repeatedly invoking $\fn{RepairTimer}()$, the node will eventually receive enough fragments to complete the repair process.


\subsection{Correctness}

Typically, the durability of a storage system is analyzed by continuous-time Markov chain (CTMC) model.
In a CTMC model system states are enumerated that include all possible numbers of persistent fragments.
The system starts from the state with expected replication factor, and an enter-only \textit{dead} state indicates data lost where no sufficient fragments left for recovering.
Random processes are defined to transition among states, i.e., it takes a random amount of time to transition from one state to another, distributed exponentially.
And finally, the model is used to solve the probability $\textbf{Pr}_{f}(t)$ which is the probability of reaching the \textit{dead} state after $t$ of time.
And important metrics such as MTTDL can be derived from it.

However, for \sys such analysis can be simplified by the inductive observation of the essential epoch change strategy.
\sys loses data if any epoch change fails, i.e., the invariant of at least $k + \epsilon$ fragments persist breaks after that epoch change.
The sets of responsible peers of different epochs are disjoint \footnotemark{}, so the failure of one epoch change is independent to any other epoch change.
Also, every epoch change has the same failure probability, because the number of Byzantine faulty peers of one epoch has no effect on the number of Byzantine faulty peers of the next epoch.
Given the fact that in every epoch the number of Byzantine faulty peers follows the same random distribution, so as the failure rate of random failure of honest peers, the failure rate of every epoch change must be the same with all identical inputs.
Thus, we can simply calculate the failure probability $p_f$ of single epoch change, and $1 - (1 - p_f)^E$ will be an upper bound of the probability for data lost where $E$ is the maximum epoch number before data goes expired.
It is feasible to construct a Markov chain for a single epoch change, but in this sketch of proof, simpler method is enough for inferring a satisfied estimation.

\footnotetext{Because the system contains limited number of peers, given enough number of epochs, one peer will eventually be responsible for multiple epochs.
However, since only a small portion of peers are responsible in each epoch, we can safely assume that with reasonable AFR all peers leave the system before they get selected twice.}

An epoch change will take at most $T_e = 2T_g + T_r$ time, where $T_g$ is gossip interval and $T_r$ is the upper bound of time to repair.
%\sgd{Should we define all these symbol all in once somewhere?}
% At the beginning of this interval, there are at least $k + \epsilon = k_p - b = k_p - K/3$ fragments persist, or the epoch change will start even earlier.
The epoch change cannot fail as long as both
(a) the peers of next epoch can successfully recover the object, i.e. collect $k + \epsilon$ fragments, which is always the case because of
(b) by the end of the epoch change, at least $k_p = k + \epsilon + b$ peers of this epoch is still alive, so there are enough honest nodes from this epoch to support nodes of next epoch to recover the object.
This means that at most $K - k_p$ peers die in the $T_e$ interval.
Given AFR of honest peers, we can derive the probability of over this number of peers dead and cause epoch change fails.
Then in turn derive data lost rate during \store and expiration.

The core of \sys centers around participating nodes storing and generating encoding fragments throughout the lifetime of data objects.
It involves subprotocols to randomly choose nodes responsible for encoding fragments, to verify fragment persistence proofs, to handle gossip messages, and to monitor persistence of data objects.

\paragraph{Kleroterion node selection protocol.}

As shown in \autoref{alg:kleroterion}, to determine if a node is chosen to store an encoding fragment for an object in epoch $e$, the node feeds its secrete key $sk$ and the hash of the object, concatenated with $e$, into the VRF function.
VRF generates a hash $h$ and a proof $\pi$.
By dividing $h$ by the total hash space, Kleroterion interprets the VRF output as a random real number between 0 and 1.

To simplify protocol exposition, we assume each node having exactly one unit of stake.
If a user possesses $n$ units of stake, it creates $n$ virtual nodes, each with a single unit of stake.
To randomly select $K$ nodes out of $S$ total nodes ($S$ is the total units of stake in the system), we set a boolean value $c$ to true if the interpreted VRF output falls below $\frac{K}{S}$.
Once a node is selected, Kleroterion uses the VRF output hash modulo $2^D$, where $D$ is the width of the total encoding space, to assign the index of the fragment $\var{idx}$ within the encoding stream.
Due to the large encoding space, randomness of VRF ensures negligible fragment collision rate across eligible nodes.

Nodes periodically disseminate persistence proofs of their stored fragments.
To verify that a node is selected by Kleroterion to store a fragment in epoch $e$, the \fn{VerifyFrag} procedure feeds the public key of the node, the claimed hash and proof generated by the VRF, and the concatenated object hash $oh$ and $e$ into the \fn{VerifyVRF} function.
If the verification passes, the procedure uses the same way to calculate $c$ and $\var{idx}$.
It then calculates the fragment hash from the object hash $\var{oh}$ and the index $\var{idx}$, and checks if it matches the persistence proof.
Note that deriving the fragment hash from the object hash alone --- without the full object --- requires \emph{homomorphic hashing}.
We apply the same homomorphic hashing scheme designed in \cite{homo_hash}.

Chosen nodes fetch the object from the requesting client, and then invoke \fn{ConstrFrag} to construct and store their responsible fragments.
Details of \fn{ConstrFrag} will be introduced later.

When a \mtype{frag} is received, the node first verifies the correctness of the persistence proof by invoking \fn{VerifyFrag}.
Invalid fragments are immediately rejected.
If the fragment matches the inflight client request, the node adds the fragment hash to the pending list.
It then invokes Kleroterion, similar to the \mtype{obj} handler, to determine its eligibility for storing the object in the subsequent epoch.
If the node is responsible, it fetches and stores the fragment from the source, and starts monitoring persistence proofs of the object.

\subsection{Optimizations}
\label{sec:protocol:optimization}

\paragraph{Repair booster to reduce repair traffic.}
One problem with \sys is that it can suffer from amplified network traffic caused by repair.
Each responsible peer needs to individually fetch $k + \epsilon$ fragments before generating one fragment.
This issue can be addressed by a set of repair booster peers, who fetch fragments, decode objects, and generate fragments on behalf of responsible peers.
Thanks to VRF, booster peers can independently verify the responsibility of peers.
And with homomorphic hashing, peers can verify the fragments generated by booster peers.
Booster nodes perform best-effort caching after recovering data objects.
When another fragment needs to be generated later for the same object, the node avoids fetching the fragments again.
This can significantly reduce repair traffic.
Any peer participating in \sys can behave as a booster node, but heuristically the node who recently has been chosen for an object is a good choice.

Note that faulty booster nodes has no effect on object durability, but can only increase network usage.

\paragraph{Batching gossip messages.}
We can batch gossip messages to further reduce network traffic.
Persistence proof are usually tiny messages, approximately 100 bytes.
Nodes can delay and send a batch of messages in single gossip, reducing the bandwidth requirement of gossip significantly.
Thanks to lazy repair, the timer interval is long, normally from several hours to up to once per day, so a small delay on gossip will not induce unnecessary repairs.

\paragraph{Reduce redundancy caused by bursty repair.}
Since every node individually monitors objects without explicit coordination, when repair threshold is reached, several nodes' may simultaneously regenerate encoding fragments.
To ameliorate this issue, when a node checks for object persistence, it can filter out fragments with hash values lower than the local one.
