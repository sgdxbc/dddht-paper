\section{\sys Protocol}
\label{sec:protocol}

We now propose \sys, a decentralized storage system design that provides strong durability guarantee.

\subsection{System Model}
\label{sec:protocol:model}

\sys operates in a permissionless setting.
Nodes can join or leave the system at any time.
A node rejoining the system is equivalent to a transient node failure.
Each node maintains $S$ amount of storage capacity.
For participants with higher capacity, they divide their storage into ``virtual'' nodes~\cite{chord} each with storage capacity $S$.

We assume that at most $\frac{1}{3}$ of the overall system storage capacity is controlled or compromised by adversaries.
Since each node has a fixed storage capacity, the model is equivalent to a maximum of $\frac{1}{3}$ of the nodes being adversarial, similar to prior BFT works.
Adversaries can deviate arbitrarily from the protocol;
all other nodes are honest.
Tolerating Sybil attacks is out of the scope of our work.

We assume a partially synchronous~\cite{partial_synchrony} network, \ie, there exists an unknown Global Stabilization Time (GST)~\footnote{
We assume the GST is shorter than the lifetime of storage devices;
otherwise the system cannot guarantee data durability.
Given typical disk MTTF values (\eg, more than one million hours), this is a conservative assumption.
}, after which the network exhibits synchrony.
Honest nodes can fail.
However, only permanent failures (\eg, nodes leaving and device failures) and adversarial behaviors can lead to data losses.
All other recoverable failures (\eg, nodes rebooting after a kernel crash) are equivalent to transient failures.

\subsubsection{\fn{Put} Protocol}

When a node $c$ invokes $\fn{Put}(\var{obj})$, it broadcasts a message \msig{StoreRequest}{\var{obj}, h}{c}, where $h$ is the hash of $\var{obj}$.
\lijl{For now, just broadcast the entire object.
The design is not practical anyway.}
Once a node $s$ receives the message, it validates the signature, and generates $\frac{3(k + \epsilon)}{N}$ random coding indices.
The node can apply additional access control checks;
details of access control policies are not within the scope of the paper.
For each generated index $idx$, the node produces a fragment $f$ by invoking $\fn{encode}(\var{obj}, \var{idx})$, allocates a storage location $\var{pos}$, appends $\langle \var{idx}, \var{pos} \rangle$ into $\var{frags}[h]$, and flushes the fragment to local disk by calling $\fn{store}(\var{pos}, f)$.
After all fragments are stored, $s$ sends a message \msig{StoreReply}{h}{s} to $c$.
Once $c$ collects $\frac{2}{3N}$ unique acknowledgements for $h$, it considers the \fn{Put} call has completed.
Since at most $\frac{1}{3N}$ of the received \mtype{StoreReply} are from adversaries, the remaining $\frac{1}{3N}$ honest nodes who replied have stored a total of $k + \epsilon$ fragments.
This ensures recoverability of the object.
If $c$ fails to receive sufficient \mtype{StoreReply} after a timeout, it re-broadcasts the \mtype{StoreRequest}.

\subsubsection{\fn{Get} Protocol}

When a node $c$ calls $\fn{Get}(\var{h})$, where $h$ is the hash of the object it intends to read, $c$ broadcasts a \msg{ObjRecover}{h} to the network.
Upon receiving and validating the request, a node $s$ queries its local state $\var{frags}$.
If $h$ is present, for each mapped $\langle \var{idx}, \var{pos} \rangle$, $s$ reads the fragment from storage by issuing $\fn{load}(\var{pos})$.
\sloppy
Once all stored fragments $f_1, f_2, \dots$ are retrieved, $s$ replies a \msg{FragReply}{h, f_1, f_2, \dots} to $c$.
When $c$ receives a new \mtype{FragReply} with matching $h$, it buffers the fragments, and calls $\fn{decode}(f_1, f_2, \dots)$ with all buffered fragments.
The \fn{Get} invocation terminates when the hash of the returned object matches $h$.
$c$ removes all buffered fragments, and ignores subsequent \mtype{FragReply}.
Note that nodes do not sign \mtype{FragReply} messages;
the collecting node validates the received fragments by checking the final object hash.

\subsubsection{Node Joining and Leaving}
\label{sec:protocol:reconfig}

Periodically, each node approximates the current $N$.
We elaborate the details of this mechanism in \autoref{sec:optz}.
If the new $N$ deviates from the previous estimation by a margin, the node readjusts its stored fragments for each object to $\frac{3(k + \epsilon)}{N}$:
If the fragment count decreases (indicating more nodes have joined the system), it simply deletes randomly selected fragments;
when the count increases, \ie, the system size has reduced, the node generates more fragments.
To do so, it broadcasts a \mtype{ObjRecover}, recovers the object, generates and stores new fragments with random indices, similar to the \fn{Get} protocol.

When a new node joins the system, it queries a few randomly selected nodes to learn the hash of the objects stored in the system.
Next, the node initializes each learned object with an empty list in \var{frags}.
It then performs the above estimation protocol immediate, which builds and stores the desired fragments for all objects.
Nodes leaving the system has no immediate impact on the remaining participants.

We consider this more ``lazy'' approach for two rationales.
First, eagerly reacting to membership changes creates significant network traffic, particularly for a system with high churn.

Second, many node failures are recoverable;
by delaying fragment generation, the protocol avoids performing unnecessary work due to transient behaviors~\cite{carbonite}.

\subsubsection{Node Recovery}

When a node rejoins the network, either after a crash, rebooting, or temporary leaving the system, it recovers its in-memory $\var{frags}$ state by reading from local storage.
Details of the storage layout are discussed in \autoref{sec:optz}.
Next, the node performs $N$ estimation (\autoref{sec:protocol:reconfig}), and then resumes normal protocol processing.
If the node has lost its local storage data, it performs the same joining protocol as a fresh node.

\subsection{Proof}

The \sys maintains the following invariant:
for each stored data block, at any time since the \fn{Put} operation finishes, any set of $N - f$ honest nodes hold at least $k + \epsilon$ fragments for the block.

\section{Making \sys Practical}
\label{sec:optz}

The base \sys protocol guarantees object durability while permitting the system to scale in storage capacity.
However, the protocol, in the current design, incurs impractical overheads for large-scale deployments.
In this section, we propose protocol and design optimizations that significantly improve the system efficiency.

\subsection{Optimal Regeneration Code}
In the base \sys protocol, the repair process requires first reconstructing the original object, before generating new fragments.
This procedure is universal for all storage systems that deploy erasure codes, but its network bandwidth and computation overheads are especially problematic for our \sys design.
\sys distributes fragments of each object widely, to all storage nodes.
Reconstructing an object, therefore, requires full-network-scale data transmission.
Moreover, when a new node joins \sys, it has to reconstruct \emph{all existing objects} stored in the system.
The traffic and computational cost would be overwhelming for any non-trivial deployments.

To address this issue, we develop a new erasure coding scheme, termed optimal regeneration code (\code).
\code is based on the Luby Transform (LT) rateless codes~\cite{ltcodes}.
The original LT codes divide the original data into equal-sized chunks.
To generate an encoded fragment, LT codes perform XOR on $d$ \emph{randomly} chosen data chunks.
Critically, the number $d$, called the degree of a fragment, follows a robust soliton distribution~\cite{ltcodes}.
To recover the original data, LT codes collect $k + \epsilon$ encoded fragments.
If a fragment has degree 1, it directly reveals an original data chunk.
A lower degree fragment $f$ can be XORed with a higher degree fragment $f'$ that contains it to reduce the degree of $f'$.
The process continues until all the original data chunks are revealed.
The original paper proves that, with overwhelming probability, LT codes can decode the original data with any $k + \epsilon$ unique fragments.

Generating a new fragment using LT codes, however, still requires recovering the original data.
To reduce the repair cost, we perform a \emph{transformation} on the LT codes to derive our \code code.
To encode a fragment, \code similarly samples a degree $d$ from a degree distribution, and chooses $d$ random data chunks.
Instead of performing XOR, \code directly stores a ``flattened view'' of the original $d$ data chunks in the fragment.
When decoding the original data, \code similarly collects $k + \epsilon$ encoded fragments.
Since each fragment contains $d$ original data chunks, no XOR is required in the decoding process.
In the original LT codes, any $k + \epsilon$ unique fragments contain all the original data chunks (some of which are XORed).
By following the same selection distribution and representing fragments as flattened data chunks, \code automatically provides the same guarantee.
As such, any $k + \epsilon$ unique \code fragments can recover the original data with overwhelming probability.
Note that by avoiding XORing the original data chunks, \code can use the more efficient ideal soliton distribution~\cite{ltcodes} to ensure recoverability, which has a smaller mode that the robust soliton distribution in LT codes.
\sgd{what is "mode"? the average degree is indeed smaller.}

The key benefit of \code is improved efficiency in object repair.
To generate a new encoded fragment, \code does not require reconstructing the original object.
The repairing node samples $d$ random data chunk indices.
By the recoverability property of \code, each of the $d$ data chunks is stored on at least one non-failure node in the system (possibly combined with other chunks to form a fragment).
The repairing node simply broadcasts a repair request with the object hash and the $d$ chunk indices.
Next, it receives the requested data chunks from existing storage nodes, and ``merge'' them to form the new fragment.
It is easy to see that the procedure is equivalent to reconstructing the object and generating the fragment in sequence.
We name \code ``optimal'' since the regeneration process only transmits fragment-sized data, which is optimal~\footnote{The procedure does transmit extra metadata (\eg, chunk indices), but the size is negligible compared to fragment sizes.}.

Our \code trades off repair efficiency with redundancy.
Compared to LT codes, \code scales up the size of each fragment by its degree $d$.
Nevertheless, the extra redundancy is \emph{constant}, given the ideal Soliton Distribution.
Specifically, the average degree of the distribution is $10.98$.
This constant redundancy overhead does not violate our design goal.

\subsection{Self-Certifying Fragments}
\lijl{Describe how we use Merkle tree and root hashes to validate each chunk.}
Transmitting \code fragments instead of the original data block raises a new challenge: verifying for integrity.
Unlike the data blocks which are naturally self-certifying because the network identifies the blocks with their hashes, the \code fragments that are encoded by remote nodes are not trusted, and the naive way to validate them is to reconstruct and block and encode again, which is obviously unacceptable.

To address this challenge, \sys leverages the flattened view representation described above, and certifies each chunk individually.
Upon \fn{Put} operation, \sys computes the hash of every chunk of the data block, and construct a Merkle tree for all the chunks.
Then each chunk is equipped with its Merkle proof, and the root hash of the Merkle tree is used to identify the data block.

With this extra facility, when \sys node receiving \code fragments encoded by remote nodes, the Merkle proofs sent along with the fragments can show the inclusion of the fragments to the Merkle tree root hashes, which means the fragments are valid for the blocks.
\sgd{Seems no way to prove the index is correct, at least node can deduplicate locally.}

This Merkle tree exposes a constant storage overhead.
Our specific \code utilizes a 15-layer Merkle tree, which results in a Merkle proof of 480 bytes.
The overhead is negligible compare to the chunk size \ie 32KB.

\subsection{Fragment Distribution with Constant Redundancy}
\lijl{Discuss how are the fragments being initially distributed, how $n$, $k$ being decided.}

One limitation of \sys is the $k$ must be statically decided ahead of time.
It's a challenging task to cooperate with ever-changing number of nodes with a fixed $k$.
To address this problem, \sys choose a sufficient large $k$ (\ie $2^{15}$) to handle potentially giant system scale.
When the storage network is initiated with a small set of nodes, each node stores multiple fragments.
For example, with $N$ = 10K nodes in the system, each node stores 10 fragments for each block, so that $N/3$ honest nodes store $33340 > k + \epsilon$ fragments that is sufficient for reconstructing the block.
When the system scales up, \ie the number of nodes increases, the unnecessary redundancy are discarded by the random eviction during the periodical estimation of $N$, ensuring the constant redundancy.

\subsection{Local Storage Design}

\lijl{Describe local storage organization and optimization.}
The local storage of the storage nodes follows a straightforward file structure.
Every block corresponds to a directory, and every stored chunk of the block corresponds to a subdirectory, which consists of two files: the chunk content and the Merkle proof.
Notice of the lack of fragment level directory: if fragments contain overlapping chunks (though the chance is rare considering large number of different chunks), the storage is automatically deduplicated.
In conclusion, the local storage keeps minimal metadata and encodes it into file system as much as possible.

In practice, we notice that sometimes the file system may be stressed: when the node is concurrently storing multiple high-degree fragments, it may create large number of files.
To mitigate this situation, \sys adapts a lightweight bundling solution: all the directories and files belongs to the same block are aggregated into a single ZIP file.
The ZIP files are maintained in stored (\ie uncompressed) mode to minimize the computation overhead.
In practice, we observe near zero cost of this bundling, and a significant speed up in the file system interaction.
