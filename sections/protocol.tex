\lijl{
    We should first define the system model and the objectives.
    Here is one example:

    The system consists of $T$ of total storage capacity.
    At most $\frac{T}{3}$ of storage space is controlled or compromised by adversaries.
    For simplicity, we assume the storage capacity on each storage node is $t$.
    There are therefore $\frac{T}{t}$ storage nodes, and at most $\frac{T}{3t}$ nodes are controlled by adversaries.

    Durability goal:
    Any stored object can be recovered, even if \emph{any} $\frac{T}{3t}$ of storage nodes permanently lose all their data.

    Capacity goal:
    The total object storage capacity (number of object stored) increases linearly with the number of storage nodes in the system.

    Other goals:
    The system should avoid BFT consensus protocols.
    The system should adapt to dynamic changes in system size (with adversarial power changes accordingly).
}

\lijl{
    Possible solutions:

    Solution 1:
    Store copies of each object on $\frac{T}{3t} + 1$ storage nodes.
    The solution satisfies the durability goal.
    However, suppose each object has size $o$, the total object storage capacity is roughly $\frac{t}{o} * 3$, which does not increase with more storage nodes.
    The solution also requires BFT consensus to decide which $\frac{T}{3t}$ storage nodes to store copies of an object.
    (Alternatively, can statically assign object hashes to nodes.)

    Solution 2:
    Encode each object into $n = k + r$ symbols, where $r = \frac{T}{3t}$.
    The $n$ symbols are stored on $n$ storage nodes.
    The solution satisfies the durability goal.
    The redundancy level is $\frac{r}{k}$.
    To satisfy the capacity goal, $k$ needs to increase proportionally to $r$.
    Challenge: the solution requires large $k$ and $r$ values for large deployments.
    Do practical erasure codes efficiently support large $k$ and $r$?
    Is there any theoretical limitation?
    Is there any performance implication of larger $k$ and $r$?

    Solution 2A:
    Use a fixed-rate code, \eg, RS code.
    Challenge: the code generates fixed $k + r$ distinct symbols.
    To ensure durability, each of the $n$ nodes needs to store a unique symbol.
    The initial distribution can be done by the client (too much client overhead?).
    However, recovery still requires some form of BFT consensus to ensure unique symbol distribution, which violates our goals.

    Solution 2B:
    Use a rateless code, \eg, fountain code.
    The code generates an infinite symbol sequence.
    Each of the $n$ nodes can randomly pick a symbol in the sequence with negligible collision probability.
    This should be the target solution.
}

We now propose \sys, a decentralized storage system design that provides strong durability guarantee.

\subsection{System Model}
\label{sec:protocol:model}

\sys operates in a permissionless setting.
Nodes can join or leave the system at any time.
A node rejoining the system is equivalent to a transient node failure.
Each node maintains $S$ amount of storage capacity.
For participants with higher capacity, they divide their storage into multiple nodes, each with storage capacity $S$.

We assume that at most $\frac{1}{3}$ of the overall system storage capacity is controlled or compromised by adversaries.
Since each node has a fixed storage capacity, the model is equivalent to a maximum of $\frac{1}{3}$ of the nodes being adversarial, similar to prior BFT works.
Adversaries can deviate arbitrarily from the protocol;
all other nodes are honest.
Tolerating Sybil attacks is out of the scope of our work.

We assume a partially synchronous~\cite{partial_synchrony} network, \ie, there exists an unknown Global Stabilization Time (GST), after which the network exhibits synchrony.
Honest nodes can fail.
However, only permanent failures (\eg, nodes leaving and device failures) and adversarial behaviors can lead to data losses.
All other recoverable failures (\eg, nodes rebooting after a kernel crash) are equivalent to transient failures.

\subsubsection{$\fn{Put}$ Protocol}

When a node $c$ invokes $\fn{Put}(\var{obj})$, it broadcasts a message \msg{ObjStore}{h}, where $h$ is the hash of $\var{obj}$.
Once a node $s$ receives the request, it generates a random number $idx$, and sends a \msg{FragRequest}{h, \var{idx}} to $c$.
\lijl{What is the range of $idx$?
How many fragments should $s$ request?
Even when $\frac{1}{3}$ of the nodes fail, the remaining nodes should store at least $k + \epsilon$ fragments.
If we can accurately estimate $N$, each node should store at least $\frac{3(k + \epsilon)}{2N}$.}
$c$ then produces the requested fragment $f$ by invoking $\fn{encode}(\var{obj}, \var{idx})$, and replies $s$ with \msg{FragReply}{h, \var{idx}, f}.
Upon receiving the reply, $s$ allocates a storage location $\var{pos}$, appends $\langle \var{idx}, \var{pos} \rangle$ into $\var{frags}[h]$, and flushes the fragment to local disk by calling $\fn{store}(\var{pos}, f)$.
\lijl{$s$ should also check for duplicates.
How does $s$ allocate storage space?
This should be fixed-size allocation.
Allocation map and frags metadata should be written to disk as well.}
Next, $s$ signals successful fragment store by sending \msg{FragAck}{h, \var{idx}} to $c$.
Once $c$ collects \XXX unique acknowledgements for $h$, it completes the $\fn{Put}()$ call.
\lijl{How many ACKs should $c$ collect?
$c$ needs to ensure that at least $k + \epsilon$ fragments are stored on honest nodes.
Also discuss retries and retransmissions.}
\lijl{In this base design, the client node performs all fragment calculation.
The client needs to transmit at least object-sized data;
however, in the base design, the client also transmits redundant information.

\subsubsection{$\fn{Get}$ Protocol}

When a node $c$ calls $\fn{Get}(\var{h})$, where $h$ is the hash of the object it intends to read, $c$ broadcasts a \msg{ObjRecover}{h} to the network.
Upon receiving the recover request, a node $s$ queries its local state $\var{frags}$.
If $h$ is present, for each mapped $\langle \var{idx}, \var{pos} \rangle$, $s$ reads the fragment $f$ from storage by issuing $\fn{load}(\var{pos})$, and replies a \msg{FragReply}{h, \var{idx}, f} to $c$.
Once $c$ receives enough \mtype{FragReply}, it recovers the original object by calling $\fn{decode}(f_1, f_2, \dots)$ and checks that the hash of the object matches $h$.
\lijl{In this base design, the client receives redundant data.
An optimized design could apply some form of streaming-based design to stop transmission once receives enough data.}
\lijl{Another issue: the client cannot verify the correctness of each received fragment.
It needs to try all combination of $k + \epsilon$ fragments.}

\subsubsection{Node Joining and Leaving}

When a node $j$ joins the system, it broadcasts a \msg{NodeJoin}{\var{id}} message.
Upon receiving a \mtype{NodeJoin}, a node $n$ queries its local $\var{frags}$, and replies to $j$ with \msg{JoinReply}{h_1, h_2, \dots}, where $h_1, h_2, \dots$ is a list of object hashes in $\var{frags}$.
For each unique object hash $h$ in any received \mtype{JoinReply}, $j$ issues a \msg{ObjRecover}{h} to recover the original object $\var{obj}$, similar to the $\fn{Get}$ protocol.
$j$ then generates a random $idx$, encodes a fragment $\var{frag}$ by invoking $\fn{Encode}$, updates $\var{frags}$, and stores $\var{frag}$ in local storage.
\lijl{Similar to the $\fn{Put}$ protocol, the new node should store at least $\frac{3(k + \epsilon)}{2N}$ fragments.
Since $N$ increases, existing nodes can safely discard some random fragments.
However, they shouldn't do it eagerly (to amortize cost, to avoid doing unnecessary work, and to reduce impact on transient behaviors).
We can use a unified, periodic protocol to do $N$ estimation, and to discard or acquire fragments based on the new $N$.}

Nodes leaving the system has no immediate impact on the remaining participants.
Periodically, each node approximates the current $N$, \ie, the total number of alive participants.
Approximation is done by sending alive-check messages to sampled nodes on the consistent hashing ring.
\lijl{Alternative approaches:
dedicated nodes periodically broadcast to collect ACKs;
a BFT service: each node periodically reports to the service;
other prior work.}
If the new $N$ deviates from the previous estimation by a margin, the node readjust its stored fragments for each object according to $\frac{3(k + \epsilon)}{2N}$.
If the fragment count decreases (indicating more nodes have joined the system), the node simply drops randomly selected fragments;
when the fragment count increases (the system size has reduced), the node generates more fragments, similar to the protocol when a new node joins the system.
We consider this more ``lazy'' approach for two rationales.
First, eagerly reacting to membership changes creates significant network traffic, particularly for a system with high churn.
\lijl{Add some concrete evaluation to demonstrate this?}
Second, many node failures are recoverable;
by delaying re-adjusting stored fragments, the protocol avoids doing unnecessary work due to transient behaviors.

\subsubsection{Node Recovery}

When a node $r$ rejoins the network (either after a crash, rebooting, or temporary leaving the system), it recovers its in-memory $\var{frags}$ state by reading from local storage.

Next, $r$ performs $N$ estimation, and then resumes normal protocol processing.
If $r$ has lost its local storage data, it performs the same joining protocol as a fresh node.
