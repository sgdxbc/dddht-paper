This section gives a detailed description of the \sys protocol we overviewed in \autoref{sec:approach}.
We provide implementation details of the protocol in the following section.

\subsection{System Model and Assumptions}
We consider a decentralized system in which nodes can freely join and leave.
Each node maintains finite local storage, and the entire set of participants collectively implements a storage system.
\sys exposes a \textit{synchronous} object storage interface with two API calls: \query and \store.
\store takes an object and an expiration time, and returns an ID when the object is successfully stored;
\query takes an object ID and returns the object if it exists in the system.
%\lijl{Should we clarify that object ID is the hash of the object here?}
%\sgd{If we do clarify, we can also mention verifiable result by comparing hashes.}
Objects are immutable --- \sys does not provide an explicit interface to update existing objects.
Similar to IPFS, \sys uses content addressing, i.e., an object ID uniquely identifies the content of the object stored.
Issuing a new \store with different object content, therefore, is equivalent to an object update.
Consistently mapping client objects to \sys issued IDs, however, is out of the scope of the paper.
%Update can be done by issuing a \del followed by a \store to overwrite the entire object.
%Note that in this case, the \store will return a different object ID for the updated object.

\sys guarantees \textit{data durability}.
Once a \store successfully returns, all subsequent \query{}s for the generated ID return the original object until is object is expired.
%\del is best-effort in \sys: After a completed \del, a \query may still return the object.
Combined with the fact that \sys does not support explicit object update, our data durability definition also implies linearizability~\cite{linearizability} of client \query{}s and \store{}s.

We assume two types of failures that relate to data losses -- storage device failures and Byzantine failures.
Storage device failures lead to unrecoverable data loss of the entire or part of a device.
They are stochastic events: The failure probability of a device is modeled after annualized failure rate (AFR), which depends on factors such as device makes, models, and years of usage~\cite{disk_failure}.
A node exhibiting Byzantine failure can deviate arbitrarily from the protocol, including losing or modifying any data stored locally.
For other types of node failures that are recoverable such as crashes or power failures, we treat them as transient faults.
Permanent node failures are equivalent to nodes leaving the system.

We consider a strong Byzantine fault model in which Byzantine participants can collude with each other and generate arbitrary node identities.
We, however, assume a stake-based system, and that the Byzantine participants do not possess more than $1/3$ of the system stakes in aggregate, a standard assumption made in proof-of-stake protocols.
Note that using stake is not an inherent part of the protocol.
\sys only leverages stake to defend against strong Sybil attacks; other approaches such as proof-of-work or permissioned settings can also be applied.
\sgd{Candidate statement of threat model: no honest node can get compromised after they start to store fragments.}

We also make standard cryptography assumptions, i.e., the probability of subverting cryptographic hash functions or public-key cryptography algorithms we used in the protocol is negligible.

\sys nodes communicate through both point-to-point channels and a gossip protocol.
Point-to-point channels are \textit{reliable}.
They can be implemented using protocols such as TCP and Reliable User Datagram Protocol (RUDP).
The gossip protocol is best-effort and only provides weak guarantees: If a node sends a message through the protocol indefinitely, eventually all non-faulty nodes receive the message.
%\sgd{We probably want a (although very lossy) synchronous guarantee on gossip, i.e., message should be received before sender crashes.}

\sys uses a publicly-known rateless erasure code to encode each stored object into an infinite stream of fragments.
As introduced in \autoref{sec:background:code}, any $k + \epsilon$ distinct encoding fragments can be used to reconstruct the original object with overwhelmingly high probability.
To guarantee data durability, \sys enforces the following \textit{invariant}: at any time $t$ after a \store is completed,
%\sgd{and before it expires}
at least $k + \epsilon$ encoding fragments of the object are present on non-faulty nodes.

\autoref{fig:node-state} shows the local state maintained by each \sys node.
Each node generates a (\textit{sk}, \textit{pk}) key pair, and stores the secret key \textit{sk} locally.
%\sgd{According to Algorand there are certain limitations on generating secret keys or the randomization may be vulnerable. Mention we are aware of this somewhere if necessary.}
Public keys are assumed to be known by all nodes in the system.
Each node locally stores a set of fragments generated from our rateless erasure encoding.
Once a node learns that it is chosen to store fragments for an object in the next epoch, it starts monitoring live fragments for that object through the gossip protocol.

Storage device failures and node churns can lead to permanent loss of encoding fragments, resulting in violation of the durability invariant.
To avoid relying on a centralized trusted service to detect fragment losses, each node periodically broadcasts \textit{persistence proof} of its stored fragments through the gossip protocol.
By monitoring the persistence proofs, \sys nodes can independently generate and store new encoding fragments when the number of alive fragments is below a threshold.

Naively implementing the above scheme has two issues.
Firstly, tracking and maintaining all persistence proofs on each node scales poorly.
Second, Byzantine nodes can collude and claim persistence of enough fragments for an object, such that less than $k + \epsilon$ fragments are stored on honest nodes.
Once those Byzantine nodes discard their local fragments, the object is permanently lost.

\sys implements a decentralized node selection protocol, Kleroterion, to address both issues.
Kleroterion partitions the lifetime of an object into virtual \textit{epochs}.

VRF ensures that each node can independently generate a selection proof, the selection probability of a node is proportional to the fraction of stakes it owns, and that the selection proof is publicly verifiable.
The selection proof is attached to each persistence proof.

Placing encoding fragments at dynamically set of randomly selected nodes complicates object lookup.
\sys leverages efficient gossip protocols~\cite{kadcast} to disseminate \query requests, which ensures sufficient ($k + \epsilon$) encoding fragments can be located.
This naive approach, however, leads to additional gossip traffic and degraded \query latency.
\sys addresses this issue with another level of indirection using distributed hash table (DHT).
When a node stores a new fragment for an object, it registers a \textit{fragment pointer} in the DHT.
To handle a \query, the requesting node queries the DHT to retrieve $k + \epsilon$ distinct fragment pointers, fetches the respective encoding fragments, and reconstructs the original object.
Fragment pointer registration, however, is best-effort.
To handle the case where less than $k + \epsilon$ pointers are found in the DHT, \sys nodes also store a maximum of $log(k)$ \textit{fragment links} alongside each locally stored fragment.
A fragment link points to another node that stores a fragment for the same object in the same epoch.
A traversal of fragment links increases the probability to recover all $k + \epsilon$ fragments.

\subsection{Protocol Details}

\subsubsection{\sys Client Protocols}

\begin{algorithm}[t]
    \begin{algorithmic}[1]
        \State $\var{pnd} \gets \langle \bot, \set{}\rangle$ \Comment{pending op. hash and fragments}
        \Procedure{\store}{$\var{obj}$}
            \State $\var{hash} \gets \fn{Hash}(\var{obj})$
            \State $\var{pnd} \gets \langle \var{hash}, \set{} \rangle$
            \State $\fn{Gossip}(\msg{obj}{\var{hash}})$
            \State wait until $|\var{pnd.frags}| \ge k_p$
            \State \Return $hash$
        \EndProcedure
        \Procedure{\query}{$\var{id}$}
            \State $\var{fp} \gets \fn{DHT-Get}(\var{id})$
            \If{$|\var{fp}| > 0$}
                \State $\var{frags} \gets$ retrieve fragments from $\var{fp}$
                \While{$|\var{frags}| < k + \epsilon$}
                    \State $\var{frags} \gets \var{frags} \cup$ traverse links in $\var{frags}$
                    \State // if timeout, goto the else branch
                \EndWhile
            \Else
                \State $\var{pnd} \gets \langle \var{hash}, \set{} \rangle$
                \State wait until $|\var{pnd.frags}| \ge k + \epsilon$
                \State $\var{frags} \gets$ retrieve fragments from $\var{pnd.frags}$
            \EndIf
            \State \Return \fn{Decode}($\var{frags}$)
        \EndProcedure
    \end{algorithmic}
    \caption{\sys client protocol}
    \label{alg:client}
\end{algorithm}

\autoref{alg:client} lists the client side protocol of \sys.
Being a decentralized peer-to-peer system, client operations are issued on participating nodes, though they can also serve as proxies for light-weight clients.
We use \textit{client} to denote the peer node that issues a client operation.

To store an object, the client calculates the hash of the object and writes the hash into a local request pending list.
As we explain in subsequent protocols, when a node receives fragment persistence proofs through gossip, it adds verified proofs to the pending list if it matches the object.
The node waits until it collects more than $k_p$ proofs.
$k_p$ is calculated as $k + \epsilon + b$ where b is the expected number 
\sgd{upper bound with high probability}
of Byzantine nodes selected by Kleroterion in an epoch.
Given our system model, $b$ is
\sgd{$\sim$}
$\frac{K}{3}$, where $K$ is the total number of fragments in an epoch.

To retrieve an object, the requesting client first queries the DHT using the object ID.
If the DHT contains fragment pointers of the object, the client fetches $k + \epsilon$ fragments through the pointers, traversing fragment links if necessary.
If no pointers are found or the procedure times out, the client registers the object in the local pending list, similar to the \store protocol.
It then waits until $k + \epsilon$ proofs are collected, and fetches fragments from the corresponding nodes.
In either case, the client uses the rateless code decoding function to reconstruct the original object from the fragments.

\subsubsection{Storing and Generating Encoding Fragments}

The core of \sys centers around participating nodes storing and generating encoding fragments throughout the lifetime of data objects.
It involves subprotocols to randomly choose nodes responsible for encoding fragments, to verify fragment persistence proofs, to handle gossip messages, and to monitor persistence of data objects.

\paragraph{Kleroterion node selection protocol.}

\begin{algorithm}[t]
    \begin{algorithmic}[1]
        \Procedure{Kleroterion}{$\var{hash}, e$}
            \State $\langle \var{h}, \pi \rangle \gets \fn{VRF}_{sk}(\var{hash} \parallel e)$
            \State $c \gets \frac{h}{2^{hashlen}} < \frac{K}{S}$
            \State $\var{idx} \gets h \bmod 2^D$
            \State \Return $\langle \var{h}, \pi, c, idx \rangle$
        \EndProcedure
        \Procedure{VerifyFrag}{$\var{oh}, e, h, \pi, \var{fh}, \var{pk}$}
            \If{$\neg \fn{VerifyVRF}_{pk}(h, \pi, \var{oh} \parallel e)$}
                \Return false
            \EndIf
            \State $c \gets \frac{h}{2^{hashlen}} < \frac{K}{S}$
            \If{$\neg c$}
                \Return false
            \EndIf
            \State $\var{idx} \gets h \bmod 2^D$
            \State \Return $\var{fh} = \fn{FragHash}(oh, idx)$
        \EndProcedure
    \end{algorithmic}
    \caption{Kleroterion node selection protocol}
    \label{alg:kleroterion}
\end{algorithm}

As shown in \autoref{alg:kleroterion}, to determine if a node is chosen to store an encoding fragment for an object in epoch $e$, the node feeds its secrete key $sk$ and the hash of the object, concatenated with $e$, into the VRF function.
VRF generates a hash $h$ and a proof $\pi$.
By dividing $h$ by the total hash space, Kleroterion interprets the VRF output as a random real number between 0 and 1.

To simplify protocol exposition, we assume each node having exactly one unit of stake.
If a user possesses $n$ units of stake, it creates $n$ virtual nodes, each with a single unit of stake.
To randomly select $K$ nodes out of $S$ total nodes ($S$ is the total units of stake in the system), we set a boolean value $c$ to true if the interpreted VRF output falls below $\frac{K}{S}$.
Once a node is selected, Kleroterion uses the VRF output hash modulo $2^D$, where $D$ is the width of the total encoding space, to assign the index of the fragment $\var{idx}$ within the encoding stream.
Due to the large encoding space, randomness of VRF ensures negligible fragment collision rate across eligible nodes.

Nodes periodically disseminate persistence proofs of their stored fragments.
To verify that a node is selected by Kleroterion to store a fragment in epoch $e$, the \fn{VerifyFrag} procedure feeds the public key of the node, the claimed hash and proof generated by the VRF, and the concatenated object hash $oh$ and $e$ into the \fn{VerifyVRF} function.
If the verification passes, the procedure uses the same way to calculate $c$ and $\var{idx}$.
It then calculates the fragment hash from the object hash $\var{oh}$ and the index $\var{idx}$, and checks if it matches the persistence proof.
Note that deriving the fragment hash from the object hash alone --- without the full object --- requires \emph{homomorphic hashing}.
We apply the same homomorphic hashing scheme designed in \cite{homo_hash}.

\paragraph{Handling gossip messages.}

\begin{algorithm}[t]
    \begin{algorithmic}[1]
        \Procedure{RecvMsgObj}{$\var{hash}$}
            \State $\langle h, \pi, c, idx \rangle \gets \fn{Kleroterion}(\var{hash}, 0)$
            \If{$c$}
                \State $\var{obj} \gets$ retrieve object from source
                \State $\fn{ConstrFrag}(\var{obj}, \var{hash}, h, \pi, \var{idx}, 0)$
            \EndIf
        \EndProcedure
        \Procedure{RecvMsgFrag}{$\var{oh}, e, h, \pi, \var{fh}, \var{pk}$}
            \If{$\neg \fn{VerifyFrag}(\var{oh}, e, h, \pi, \var{fh}, \var{pk})$}
                \Return
            \EndIf
            \If{$\var{oh} = \var{pnd.hash}$}
                \State $\var{pnd.frags} \gets \var{pnd.frags} \cup \set{\var{fh}}$
            \EndIf
            \State $\langle h, \pi, c, idx \rangle \gets \fn{Kleroterion}(\var{oh}, e + 1)$
            \If{$c$}
                \State $\var{next[oh].proof} \gets \langle e + 1, h, \pi, \var{idx}\rangle$
                \State $\var{next[oh].alive} \gets \var{next[oh].alive} \cup \set{\var{fh}}$
                \State $\var{frag} \gets$ fetch fragment from source node
                \State $\var{next[oh].frags} \gets \var{next[oh].frags} \cup \set{\var{frag}}$
            \EndIf
        \EndProcedure
    \end{algorithmic}
    \caption{Procedures to handle gossip messages}
    \label{alg:gossip-handler}
\end{algorithm}

An \sys node receives two type of gossip messages, \mtype{obj} and \mtype{frag}.
A client sends \mtype{obj} when storing an object, while \mtype{frag} is a fragment persistence proof sent by nodes periodically.

As shown in \autoref{alg:gossip-handler}, when a node receives a \mtype{obj}, it invokes Kleroterion to determine if it is chosen to store a fragment for the object in the initial epoch.
Chosen nodes fetch the object from the requesting client, and then invoke \fn{ConstrFrag} to construct and store their responsible fragments.
Details of \fn{ConstrFrag} will be introduced later.

When a \mtype{frag} is received, the node first verifies the correctness of the persistence proof by invoking \fn{VerifyFrag}.
Invalid fragments are immediately rejected.
If the fragment matches the inflight client request, the node adds the fragment hash to the pending list.
It then invokes Kleroterion, similar to the \mtype{obj} handler, to determine its eligibility for storing the object in the subsequent epoch.
If the node is responsible, it fetches and stores the fragment from the source, and starts monitoring persistence proofs of the object.

Periodically, \sys nodes broadcast persistence proofs of its store fragments, and check if they need to generate new encoding fragments.
The procedure is shown in \autoref{alg:monitor}.
In a periodic timer handler, for each fragment $f$ currently stored in its local storage, the node disseminates a persistence proof for $f$ through the gossip protocol.
Then for each object which the node is chosen by Kleroterion for the subsequent epoch, the node invokes \fn{RequireRepair} on the current alive fragments to determine if it needs to generate new encoding fragment.
The procedure checks if the node is aware of $k_p$ alive fragments in the \emph{same epoch}.
We add the epoch constraint to defend against Byzantine nodes generating persistent proofs in advance.
If regeneration is required, the node invokes \fn{ConstrFrag}.
\fn{ConstrFrag} uses the rateless erasure code to produce the corresponding encoding.
It then stores the new fragment locally, together with the persistence proof, and subsequently update the DHT for subsequent \query operations.

\subsection{Correctness}

Typically, the durability of a storage system is analyzed by continuous-time Markov chain (CTMC) model.
In a CTMC model system states are enumerated that include all possible numbers of persistent fragments.
The system starts from the state with expected replication factor, and an enter-only \textit{dead} state indicates data lost where no sufficient fragments left for recovering.
Random processes are defined to transition among states, i.e., it takes a random amount of time to transition from one state to another, distributed exponentially.
And finally, the model is used to solve the probability $\textbf{Pr}_{f}(t)$ which is the probability of reaching the \textit{dead} state after $t$ of time.
And important metrics such as MTTDL can be derived from it.

However, for \sys such analysis can be simplified by the inductive observation of the essential epoch change strategy.
\sys loses data if any epoch change fails, i.e., the invariant of at least $k + \epsilon$ fragments persist breaks after that epoch change.
The sets of responsible peers of different epochs are disjoint \footnotemark{}, so the failure of one epoch change is independent to any other epoch change.
Also, every epoch change has the same failure probability, because the number of Byzantine faulty peers of one epoch has no effect on the number of Byzantine faulty peers of the next epoch.
Given the fact that in every epoch the number of Byzantine faulty peers follows the same random distribution, so as the failure rate of random failure of honest peers, the failure rate of every epoch change must be the same with all identical inputs.
Thus, we can simply calculate the failure probability $p_f$ of single epoch change, and $1 - (1 - p_f)^E$ will be an upper bound of the probability for data lost where $E$ is the maximum epoch number before data goes expired.
It is feasible to construct a Markov chain for a single epoch change, but in this sketch of proof, simpler method is enough for inferring a satisfied estimation.

\footnotetext{Because the system contains limited number of peers, given enough number of epochs, one peer will eventually be responsible for multiple epochs.
However, since only a small portion of peers are responsible in each epoch, we can safely assume that with reasonable AFR all peers leave the system before they get selected twice.}

An epoch change will take at most $2T_g + T_r$ time, where $T_g$ is gossip interval and $T_r$ is the upper bound of time to repair.

At the beginning of this interval, there are at least $k_0 - b$ fragments persist, or the epoch change will start even earlier.
The epoch change cannot fail as long as both (a) at least $k + \epsilon$ peers of previous epoch are still alive,
and (b) at least $k_0$ out of the total $k_r$ peers that are selected to be responsible in the following epoch are still alive, at the end of this interval.
(The (b) requirement can be further relaxed if we don't care about overlapping epoch change.)
