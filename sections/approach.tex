\section{The \sys Approach}
\label{sec:approach}

So far, we have discussed two general approaches to provide durability in prior decentralized storage systems.
Selective replication is effective when failures within each placement group are independent.
However, we have shown in \autoref{sec:background:loss} that adversaries can break the failure independence assumption and compromise data durability deterministically.
Full replication addresses this durability issue by storing all objects on all the nodes.
Even if adversaries can compromise a significant proportion of the system, the remaining honest nodes can still recover all objects.

The obvious downside of full replication is \emph{scalability}.
Since each node stores all the objects, the system storage capacity is bounded by that of a single node, \ie, adding more nodes to the system does not scale the overall capacity.
Such limitation makes the full replication approach impractical for most storage scenarios, except rare cases like the blockchain~\cite{bitcoin,ethereum}.
Even in the blockchain case, the approach prohibits storing large data on-chain, and both Ethereum and Bitcoin are facing storage capacity issues.

Note that a partitioning scheme does not fundamentally solve the issue;
it merely transforms the system to a selective replication approach, which shares the same durability challenge as above.

\subsection{Durability without Compromising Scale}

Is the trade-off between strong durability and scalability fundamental in decentralized storage systems?
In this work, we challenge this hypothesis by proposing a radical design, \sys.
To guarantee durability, each object is distributed to \emph{all} the storage nodes.
By defining a single placement group for the entire system, \sys eschews any reliance on failure correlation prediction, which has been shown to be unreliable in decentralized deployments~\cite{carbonite}.
Moreover, even when a significant proportion of the system is Byzantine, the approach can ensure durability in the presence of strong adversarial behaviors, similar to existing BFT protocols.

How does \sys scale the system storage capacity if every object is stored on all the nodes?
Our key insight is to \emph{decouple redundancy from data distribution}.
Traditionally, redundancy of an object and the placement group size are strongly correlated.
To handle more failures, prior solutions increase the redundancy level and the placement group size \emph{simultaneously}:
in a replication system, the system creates more object replicas;
if erasure coding is applied, more encoded fragments are generated.
These additional redundancies are then distributed to the larger placement group.

We, however, argue that redundancy and placement groups of a system could be designed \emph{independently}.
The redundancy level of an object should only depend on the \emph{fault tolerance degree} of the placement group, and more specifically, the \emph{proportion} of storage devices that can fail simultaneously in the group.
Redundancy, therefore, should be \emph{constant}, regardless of the placement group size.
To ensure data durability, the system should \emph{evenly distribute} the object and its constant redundancy among all nodes in the placement group.
Intuitively, even when the adversaries compromise an arbitrary subset of the group, up to the attack limit, the remaining redundancy can still recover the original object.
In the case of \sys, since there exists a single placement group, \sys evenly distributes an object and its constant redundancy among all the storage nodes.

\subsection{The Decentralized Durability Challenge}
\label{sec:approach:challenge}

How to maintain data durability in the presence of server and device failures?
The standard approach is data replication and erasure coding.
It is well-studied how \emph{redundancy} can mask failures -- including Byzantine ones -- of individual components.
The approach is particularly effective in centralized settings, where system participants and failure distributions are managed by a single entity.
For instance, the central administrator have full control over placement groups such that out of the $n$ nodes storing a data object, at most $n-r$, where $r$ is the level of redundancy, of them may fail concurrently.

The formula changes completely in an open, decentralized system.
Nodes are free to join and leave the system at any time.
There is no centralized control over who are the participants and their trustworthiness.
In these systems, adversarial behaviors are the \emph{common case}, not the exception.
Adversaries might also possess strong attacking power.
They can partition regions of the network using BGP poisoning or launch distributed denial-of-service (DDoS) attacks;
they can collude with each other and compromise honest nodes;
they can create and change identities in a highly dynamic fashion.

A direct implication of a decentralized environment is that failure assumptions made by prior storage systems no longer hold.
Adversaries can launch Sybil attacks such that they control more than $n-r$ copies or erasure code symbols of an object;
once they locate more than $n-r$ nodes responsible for an object, they can also launch targeted attacks to compromise their systems.
Data durability is violated under these attack scenarios.

Existing blockchain systems face similar attack vectors.
Decentralized storage, however, are particularly vulnerable, given their scale and redundancy constraints.
In large scale deployments, the size of the system, which can reach beyond 100K nodes~\cite{ipfs}, easily overwhelms the replication factor of each storage object, which is typically below 20~\cite{kademlia}.
This is in contrast to a blockchain, in which on-chain data is replicated on every participant.
Similar to distributed storage, minimizing redundancy is a key metric to improve the overall storage efficiency.
With smaller redundancy, effectiveness of adversarial attacks grows exponentially, even when the adversaries account for a small percentage of the entire system.

Another challenge faced by open, decentralized systems is that consensus and coordination are \emph{costly}.
To safely confirm a transaction, Bitcoin requires a confirmation latency of around one hour;
even the faster Ethereum network incurs a finality latency of over 12 seconds.
Besides latency, both networks also suffers low consensus throughput -- 7 transaction per second (TPS) for Bitcoin and 20 TPS for Ethereum -- and high transaction fees.
Decentralized storage designs that rely on frequent consensus are impractical in such settings.

\subsection{Principles of Data Durability}
\label{sec:approach:principles}

Given the above challenges, we identify two key principles in providing data durability in our targeted deployment scenario.
These principles guide us in the concrete design of a durable decentralized storage system; we elaborate our main approaches to materialize the principles in \autoref{sec:approach:code} and \autoref{sec:approach:random}.

\subsubsection{\textbf{Information Asymmetry}}

Launching targeted attacks enables adversaries to erase data blocks stored on selected peers in the network.
One critical property of such attacks is that adversaries can choose targets based on any \emph{public information} in the network.
Such strong adversarial power could be detrimental to a storage system.
Metadata information about stored objects in existing systems are effectively public.
Any peer or external identities can learn the location of stored objects.
Take IPFS as an example.
Any peer in the network can query the identity of providers for a stored object through the DHT.
A key observation is that this location information is completely \emph{symmetrical} between an honest node and an adversary.
The reasoning behind this symmetry is simple: location information is critical for system functionality (data retrieval), and there is no reliable way to identify adversaries.
Adversaries can leverage this symmetrical information to concentrate their attack power on specific set of provider nodes to break durability.
To guarantee durability, the system thus needs to use redundancy level strictly higher than the \emph{aggregated} adversarial power, which can be prohibitively high.

It is not hard to see that if all metadata information is symmetrical, the system can do no better than applying overwhelming redundancy to tolerate targeted attacks.
Taking the contrapositive of the statement, we arrive at our first durability principle:

\begin{principle}[Information Asymmetry]
    To tolerate targeted adversarial behaviors without increasing redundancy, some metadata information needs to be \emph{asymmetrical}.
    \label{principle:asymmetry}
\end{principle}

\subsubsection{\textbf{Data Uniformity}}

%\footnote{We assume there is no pre-established trust in the system, which is a common assumption of decentralized systems}

Durability of an object is maintained when redundancy of the object on non-faulty nodes stays above the recovery threshold.
To ensure durability of the entire system, the above invariant needs to be true for all stored objects.
Given that identities of faulty nodes are unknown, probability of data durability is maximized when redundancy of each object is distributed \emph{uniformly random} across the storage peers.
Intuitively, for any other distribution, certain nodes in the system will store a greater proportion of data redundancy.
Failures (either adversarial or fail-stop) of such nodes will result in higher probability of object redundancy dropping below the recovery threshold, as compared to a uniformly random distribution.
Note that the reasoning above assumes completely \emph{unpredictable} faulty behaviors.
This is a common property of decentralized systems with minimum trust;
in a centralized deployment, the operator instead has perfect information on the failure domains and probabilities.
This line of argument leads to our second durability principle:

\begin{principle}[Data Uniformity]
    Probability of data durability is maximized when object redundancy is \emph{uniformly distributed} across all storage nodes ad infinitum.
    \label{principle:uniformity}
\end{principle}

Replicating each object on every node, \eg, a blockchain, is an extreme case that follows this principle.
Such scheme indeed maximizes data durability, but at the expense of excessively high storage cost.

\subsection{Dual Layer Rateless Code For Information Asymmetry}
\label{sec:approach:code}

Following \autoref{principle:asymmetry} demands adding asymmetry in the storage metadata.
In a permissionless setting, participating peers are treated equally given the system model;
creating asymmetrical information among the egalitarian storage nodes is therefore challenging.
We instead push the asymmetry requirement to clients:
when storing data, the client holds some \emph{private} information unknown to any storage node.

Private information commonly protects confidentiality and authenticity of data.
How to apply it to metadata to enforce durability?
We leverage a special class of erasure coding, the rateless codes, to design such a scheme.

\paragraph{\textbf{Rateless code primer.}}
Rateless codes are a family of erasure codes that have two special properties.
Firstly, a rateless code generates an \emph{infinite sequence} of encoding symbols from $k$ source blocks.
Any $k+\epsilon$ encoding symbols can be used to reconstruct the original source data.
This differs from traditional maximum distance separable (MDS) codes, such as Reed-Solomon codes, which produces $n$ fixed encoding symbols from the $k$ source blocks.
Second, rateless codes work well with large $(n, k, r)$ parameters, where $n$, $k$, $r$ represents the number of total, original, and redundant symbols respectively.
Real deployment of $(1200, 1000, 200)$ rateless code has been shown to be efficient~\cite{liquid}.
Such parameters are two orders of magnitude larger than practical MDS codes used in production systems.

\paragraph{\textbf{Applying rateless code to defend targeted attacks.}}
We leverage the \emph{infinite} symbol sequence of a rateless code to ``encode'' client private information into storage metadata.
Specifically, when storing an object, the client applies rateless code, and uses its \emph{private information} (e.g., its private key) to pick $n$ random symbols in the encoding sequence.
The client then stores these selected symbols as opaque data chunks into the storage system.
A key property is that these opaque chunks from any object appears \emph{indistinguishable} to the adversaries.
Consequently, targeted attacks can do no better than compromising randomly selected chunks in the system.
This is even true if the adversaries possess information about the object content.
With enough objects in the system, the chance of simultaneously attacking more than $r$ out of $n$ chunks of a particular object becomes negligible.
As such, only the client who holds the private information can recover the original object with overwhelming probability.

\paragraph{\textbf{A second layer rateless code for decentralized repair.}}
Metadata asymmetry, however, causes an undesirable side effect.
Since no storage nodes have the mapping between encoded chunks and the original object, they cannot perform repair (which requires reading $k+\epsilon$ unique encoded symbols) when the stored chunks are lost due to failures, eventually leading to data loss.
To address this issue, we add another layer of erasure coding on the encoded chunks to guarantee their durability with minimum redundancy overhead.

In theory, we can use any erasure code for this ``inner layer'' encoding.
Surprisingly, we again identify rateless code as the optimal coding choice given its unique properties.
Firstly, rateless codes are \emph{lazy repair friendly}.
Using traditional erasure codes with a small value of $r$, the storage system needs to quickly regenerate encoding symbols when just a few stored symbols are lost due to failures.
Delayed repairs risk losing the source data permanently.
However, decentralized systems exhibit high degree of asynchrony:
Network conditions vary both spatially and temporally;
there exists large deviations in processing speeds across nodes;
transient unreachabilities are also prevalent.
Strict timing requirement for detection and recovery of encoding symbols is therefore impractical in such environment.
On the other hand, large values of $r$ in rateless codes tolerate bursty encoding failures without losing the source data.
It thus permits the system to repair at a steady average rate.
Such property is more favorable in a highly aynchronous environment.
For instance, a $(1200, 1000, 200)$ code can tolerate 200 simultaneous symbol failures, while losing 3 symbols will result in permanent data loss when deploying a $(12, 10, 2)$ code.
Note that the increase in $r$ in rateless codes does not lead to higher redundancy.
The redundancy rate of the above two codes are identical.

Secondly, rateless codes enable \emph{consensus-free repair}.
MDS codes with small values of $(n, k, r)$ necessitate participants to coordinate to agree on the assignment of symbols.
Uncoordinated symbol generation may lead to insufficient \emph{unique} symbols to recover the original data, an issue analogous to the coupon collector's problem \cite{ccp}.
Rateless codes eschew this issue completely.
The \emph{infinite} encoding space enables participants to generate unique symbols with high probability without explicit coordination.

\autoref{principle:uniformity} requires that the encoded data chunks are distributed \emph{uniformly random} across all storage nodes.
The following scheme satisfies this requirement: for each data chunk, a randomly selected storage node is responsible for storing the chunk.
The challenge of such a scheme is to perform this random selection without centralized, trusted entity, while being resilient to adversaries.

We design a fully decentralized node selection scheme leveraging \emph{verifiable random functions} (VRF)~\cite{vrf}.
A verifiable random function takes an input string and the prover's private key, and produces a deterministic hash value plus a short proof.
The output hash is indistinguishable from a random value.
Using the proof and the prover's public key, anyone can verify that the hash is correctly generated by the prover, and the prover only, from the input string.
This public verifiability enables \sys nodes to independently generate checkable \emph{selection proofs}.
Specifically, for each encoding symbol, a candidate node generates a VRF hash, and \sys defines publicly-known rules to calculate selection probability \emph{inversely proportional} to the node's distance to the symbol on the hash ring~\cite{chash,chord}.
The ``winning'' hash values serves as \textit{unforgeable tokens} to store the encoding symbols, which can be publicly verified using the VRF proof.
