\subsection{Distributed Hash Tables}
\label{sec:bg:dht}

% This section first introduces the basics of distributed hash tables, and then explains how they are used now in decentralized storage networks.

The fundamental principle of distributed hash tables is consistent hashing~\cite{chash}, which is implemented in industrial-scale storage systems like Ceph~\cite{weil2006ceph}, Cassandra~\cite{lakshman2010cassandra}, and Dynamo~\cite{decandia2007dynamo}, and is extensively researched for application in distributed databases~\cite{shu2020th,liu2019distcache,chung2019lightstore}, network load balancers~\cite{eisenbud2016maglev}, and cloud infrastructures~\cite{nakatani2021structured,wu2019autoscaling}.
Consistent hashing provides an effective method for allocating and balancing workload across key-value and block storage systems.
Given $m$ keys and $n$ nodes, a consistent hashing algorithm assigns $k$ nodes to each key and ensures a uniform distribution, where each node is expected to manage $\frac{km}{n}$ keys.
% Employing consistent hashing, a hash function uniformly maps both keys and storage nodes to the same hash domain, and values are assigned to one or more nodes based on their relative positions within this domain.
% For instance, certain consistent hashing schemes arrange the hash domain as a ring, and keys are assigned to the initial node(s) encountered by traversing the ring in a clockwise direction.
These designated nodes constitute the \emph{placement groups} for the keys.
% Consistent hashing ensures that during resizing, only a minimal quantity of keys (specifically, the average number of keys per node) will, on average, be reassigned to a different node.
% This attribute renders consistent hashing a desirable placement strategy in environments with dynamic node changes or fault tolerance requirements.
% Consistent hashing is investigated in datacenter storage solutions due to its independence from a central controller or metadata server.
% \lijl{This claim is probably too strong. Most datacenter storage still uses metadata service.}\gd{Done.}
% Nodes and clients can independently determine data locations, enhancing both performance and resilience.

% In highly dynamic or asynchronous environments, such as public peer-to-peer (P2P) networks with frequent node failures, maintaining an updated list of online nodes can be challenging for individual participants.
% Furthermore, systems may expand to encompass tens or hundreds of thousands of nodes, making it impractical for every individual node to store all node identities and contact information (\eg IP addresses)~\cite{trautwein2022design}.
Distributed hash tables (DHTs)~\cite{maymounkov2002kademlia,chord,rowstron2001pastry} are constructed upon consistent hashing to address the challenges brought by public peer-to-peer (P2P) networks.
P2P networks features highly dynamic nodes asynchronous network condition and may expand to encompass tens or hundreds of thousands of nodes~\cite{trautwein2022design}, rendering impractical for the nodes to maintain updated contacts of all currently online nodes.
Utilizing DHT protocols, nodes can dynamically \emph{discover} the current placement groups of keys while locally storing contact details for only a small fraction of the nodes.
Consequently, DHTs are favored by major DSNs like FileCoin~\cite{filecoin} and BitTorrent~\cite{wang2013measuring,xinxing2016measurement}, and various DSN research including Glacier~\cite{haeberlen2005glacier}, OceanStore~\cite{kubiatowicz2000oceanstore}, CFS~\cite{dabek2001wide}, and PAST~\cite{druschel2001past}.
FileCoin is empowered by IPFS~\cite{benet2014ipfs,trautwein2022design}, who employs Kademlia DHT to store the providing records and supports provider discovery by content addressing~\cite{ratnasamy2001scalable}.
Recent research~\cite{cortes2024scalability} proposes the use of Kademlia DHT in Ethereum~\cite{ethereum} to discover validators storing blob shards, enabling privacy-preserving data availability sampling~\cite{hall2023foundations} against the blob storage network.
More recently, Swarm~\cite{team2021swarm} presents an innovative DSN that reliably manages data through a hybrid strategy combining DHT and replication to achieve high availability.

% Fundamentally, DHT protocols organize nodes into an \emph{overlay network} that directs keys to their respective placement groups.
% Behind the scene, DHTs distribute node records, associating node identities with their contact information, across the network.
% DHT protocols incorporate a record retention policy, where nodes determine which records to store locally, and a lookup protocol that iteratively identifies the nodes forming the placement group for a given key.
% DHT protocols promote efficient network and storage utilization.

Kademlia~\cite{maymounkov2002kademlia} is the most prevalent DHT protocol, and serves as the primary focus of our investigation.
Kademlia ensures logarithmic network and storage overhead.
Within a network of $N$ nodes, each node maintains $O(\log{N})$ records, and key lookups are expected to conclude after consulting $O(\log{N})$ nodes.
The consistent hashing algorithm employed by Kademlia is straightforward.
Given a key $k$ and a node with identity $id$, the \emph{distance} $d$ between them is the unsigned integer derived from the bitwise exclusive OR operation of $k$ and $id$\footnote{For brevity, \emph{key} and \emph{identity} are used to denote their respective mapped hash values, which reside within the same hash domain and possess identical length.}
\[
    d(k,id)=k\ \texttt{xor}\ id
\]
Subsequently, the key is assigned for storage to the set of nodes $G_k$ exhibiting the smallest distances to the key
\[
    G_k=\{n_i\mid{}d(k,ID[n_i])<d(k,ID[n]),n\in{}\mathfrak{N}\setminus{}G_k,i\in{}[1,\dots,r]\}
\]
where $ID$ represents the mapping from nodes to their identities, $\mathfrak{N}$ denotes the set of all nodes, and $r$ signifies the configurable \emph{redundancy rate} of the network, corresponding to the size of the placement groups.
% In practice $r$ is usually set to $20$ to tolerate frequent node churning and failures in permissionless systems.
Readers are directed to the original publication~\cite{maymounkov2002kademlia} for detailed Kademlia specification.

Kademlia uniformly distribute keys across the nodes, in the spirit of consistent hashing.
Given that both keys and node identities are uniformly distributed throughout the hash value domain\footnote{
    While users can theoretically select arbitrary keys for storing data, which may not be uniformly distributed (and some prior work has leveraged this), this approach is not readily applicable to permissionless and untrusted environments.
}.
The probability of any given node being included in the placement group of a key is equal for all nodes, leading to the same expected number of placement group memberships for every node.

% Conceptually, each node possesses a comprehensive understanding of its immediate ``neighbors'' while having limited knowledge of more distant peers.
% To locate a key, nodes initialize a candidate list with the locally stored records that exhibit the smallest distance to the target key and subsequently query each candidate.
% The queried nodes respond by providing the closest records from their own local storage, and the querying node updates its candidate list accordingly.
% This querying node then iteratively contacts subsequent candidates until the list stabilizes at a fixed set of nodes, which constitutes the placement group for the key.
% For detailed information, readers are directed to the original publication~\cite{maymounkov2002kademlia}; the key insight is that this iterative process is proven to converge to the globally closest records to the key, aligning with the key's placement equation presented earlier.
% Consequently, the node can either store or modify the value associated with the key on these identified nodes or retrieve a previously stored value from them.

\subsection{Revisiting DHT with Heterogeneous Bounded Loads}
\label{sec:bg:problem}

% While IPFS and BitTorrent store only indexing metadata in DHTs, resulting in minimal storage consumption (several megabytes) per node, DSNs that directly use DHTs for data placement can store significant amounts of data on individual nodes under reasonable utilization, potentially reaching their storage capacity limits.
% \lijl{Should we also discuss limitations of using DHT only for metadata?}
Unlike the typically homogeneous machines with centrally planned capacities in datacenters, DSNs can include nodes with vastly different storage capacities, from mobile devices offering tens of gigabytes of spare storage to professional storage clusters providing terabytes of dedicated capacity.
Meanwhile, DSNs~\cite{haeberlen2005glacier,kubiatowicz2000oceanstore,dabek2001wide,druschel2001past} commonly use DHTs for data placement to benefit from the inherent probabilistic availability provided by DHT's randomized placement groups.
This leads to an equal storage load being placed on every node, as demonstrated earlier.
Assigning equal storage load to such heterogeneous nodes can result in large-capacity nodes being significantly underutilized, while, more critically, the smallest-capacity nodes can become overwhelmed at relatively low overall utilization levels.
Even worse, this situation cannot be easily resolved by migrating data from full nodes and globally reconfiguring placement groups due to the absence of a central controller in DSNs.

Previous DSN research has not adequately addressed this specific issue.
For instance, Glacier simply rejects storage requests when nodes within the designated placement group have reached their storage limits.
Swarm proposes an economic eviction policy where nodes discard stored data with the lowest bid value when they run out of space, thus failing to provide a strict guarantee of data availability.

The consequence of this oversight is a significant detrimental impact on the usability and availability of DSNs.
To illustrate this effect, we simulate a DSN composed of heterogeneous storage nodes with uniformly randomly generated identities. The specific parameters of this simulated network are detailed in \autoref{sec:overview}.
In this simulation, we continuously attempt to store uniformly random data within the network.
If the designated placement group for the data includes any node that has reached its storage capacity, the DSN must either reject the storage request or randomly evict previously stored data from that node's storage, mirroring the approaches of Glacier and Swarm, respectively.
\autoref{fig:overwhelm} depicts the outcomes of both these choices.
Under a rejection policy, the rejection rate escalates to over 90\%, and the storage network becomes largely unable to accept further requests when only approximately 10\% of the total capacity is utilized.
Under an eviction policy, the storage network begins evicting data at a mere 6\% overall utilization and starts to experience data loss shortly thereafter.
In summary, the network is forced to choose between a loss of usability or availability, or to compromise between the two.

Compounding the issue, DSNs can experience a loss of availability even without external operations.
When a node churns from the network, for each piece of data it stores, the DHT reassigns another node to the placement group according to the consistent hashing algorithm and relocates that data to the new node.
If the reassigned node lacks sufficient free storage to accommodate the transferred storage load, it is compelled to discard either its existing data or the incoming data.
In situations where the entire network scales down, potentially due to normal fluctuations or temporary network partitioning, such data discarding can occur on a massive scale. Any data loss resulting from this process is irreversible, even if the network typically scales back up shortly thereafter.

\paragraph{Problem settings.}
Motivated by this undesirable situation, our goal in this work is to optimize the \emph{effective overall utilization} of DSNs.
We aim to utilize the maximum possible aggregated storage across the network, but only in an \emph{effective} manner, ensuring that \emph{no} individual storage node reaches its capacity limit and compromises usability or availability.
Given the difficulty DSNs face in efficiently migrating data away from overloaded nodes, the fundamental capability required for DHTs to achieve this goal is the ability to allocate placement groups while considering the heterogeneous storage capacities, thereby directing more storage requests towards nodes with greater available space.
As detailed in the following section, previous research has not successfully equipped DHTs with this essential capability.

\subsection{Previous Studies}
\label{sec:bg:works}

The most direct method to address this problem involves employing \emph{virtual nodes}~\cite{chord,dabek2001wide,zhu2005efficient, zhang2010novel}.
% The original work proposing Chord~\cite{chord} mentions deploying $O(\log{N})$ virtual nodes per physical node to significantly mitigate probabilistic nonuniform identity allocation.
% CFS also considers the heterogeneous processing capacity of nodes and suggests allocating virtual nodes proportionally.
% Subsequent works~\cite{zhu2005efficient, zhang2010novel} further explore the virtual node approach for load balancing in DHTs.
Virtual nodes associated with the same physical node can share underlying hardware resources and mitigate probabilistic imbalances~\cite{chord}.
Additionally, assigning a varying number of virtual nodes to physical nodes can effectively apply weighted workload distribution~\cite{schindelhauer2005weighted}.

However, the virtual node approach is not a panacea for the problem settings in this work.
Firstly, employing virtual nodes proportionally scales the consumption of \emph{all} resource types concurrently.
While creating more virtual nodes can enhance storage utilization on nodes with ample storage, it also proportionally increases network overhead, and these storage-rich nodes may not necessarily possess equally abundant network resources~\cite{karger2004simple}.
More critically, virtual nodes introduce \emph{hidden failure correlation}.
Virtual nodes supported by the same physical node have a high probability of failing simultaneously.
\gd{Updated.}
On the other hand, DSNs usually make assumption that each node is an individual \emph{failure domain} that independently fail with each other.
Only with this assumption, replicating to distinct nodes means increased resiliency and makes sense.
The violation of this assumption can result in catastrophic consequences.
For example, a 1623 TB data loss happened to FileCoin~\cite{filecoin_loss} was caused by the redundancy hosted by multiple nodes was physically located in the same datacenter.
Prior research~\cite{schindelhauer2005weighted} also discusses other limitations of the virtual node approach, which we will not detail here.

Beyond the virtual node approach, several solutions address heterogeneous nodes or nodes with bounded load, but none perfectly align with our problem.
Early research~\cite{karger2004simple,misra2004clash} investigated load (re)balancing schemes for DHTs shortly after their inception.
These works concentrated on nonuniform key access workloads rather than nonuniform resources across nodes.
While effective in balancing load on homogeneous nodes under varying access frequencies to stored data, they are not designed to apply appropriate loads that \emph{correspond} to the capacities of heterogeneous nodes.
Furthermore, as they address nonuniform per-key load, they are more relevant to balancing bandwidth and computational demands rather than storage demands, given that per-key storage load is constant\footnote{

}.

\paragraph{The DHT approach.}
Other DSNs directly control the placement groups of contents.
Storj~\cite{storj2018storj} centrally tracks the behavior of storage providers, and allocates the placement group based on the trust level of the storage providers.
Swarm~\cite{team2021swarm} replaces the centralized allocator with DHT~\cite{maymounkov2002kademlia} and allocates placement groups with consistent hashing.
The DHT randomly samples storage providers to form placement groups.
Since the sampling on storage providers is independent, the placement group contains at least certain number of honest storage providers with high probability.
Any faulty redundancy is detected by proof of storage and repaired timely.

In Kademlia DHT~\cite{maymounkov2002kademlia} every content and node have an \vid.
The \vid is usually the hash of the content or the node's public key to enable self-certifying contents and nodes.
Then we can calculate the \texttt{xor} distance between node and content \vid{}s.
A content is assigned to the $r$ nodes whose \vid{}s are the closest ones to the content's \vid, which becomes the content's placement group, and $r$ is the targeted redundancy level.
Kademlia provides an operation \ffind(\var{k}, \var{r}) to the nodes, which can discover the \var{r} closest nodes to \var{k} in the network.
The \ffind operation is implemented in an iterative approach that is expected to finish in $\log(N)$ steps where $N$ is the number of nodes.
To tolerate node failures and churns, the storage nodes periodically re-discover the placement group of the stored contents, and re-replicate the contents if the discovered nodes are different.
\lijl{Who initiates re-replication? If two \ffind return different results, would it lead to extra redundancy?}
\gd{Resolved. It leads to extra redundancy if \ffind result is unstable, but that is too subtle.}

Because the node and content's \vid{}s are uniformly distributed in the \vid{}'s domain space, the placement groups of contents can be considered as $r$ random samples of storage nodes that are uniformly distributed across all nodes without replacement.
So the probability of data loss in a time unit $\epsilon$ can be derived from the failure rate $f$, \ie, the probability for a storage node to fail in the time unit, and the redundancy level $r$
\[ \epsilon = f^r \]
If the failure rate is set to $f=\frac{1}{3}$, a redundancy level $r=13$ yields $1-\epsilon>99.9999\%$ \ie the durability is over ``six nines''.
The mean time to data lost (MTTDL) can further be derived as $\frac{1}{\epsilon}$ time units, which are about 4368 years when a time unit equals one day or 182 years when equals to an hour.

DHT relives the burden of the storage nodes by taking the responsibility of placing contents on them, so it becomes critical that how well DHT can make proper placement decisions.
Since the network \emph{pushes} storing requests to the storage nodes, it's hard for the storage nodes to reject the requests or hand off to other nodes.
This is because DHT's consistent hashing is symmetrically applied to \fput and \fget{}: no matter whether the requested nodes store the contents or not, the following retrieval will be routed to them nonetheless.
The lack of stored metadata means that the outcomes of \fput cannot affect the later \fget.
\lijl{Why is this the case?}
\gd{Explained.}
However, as previously mentioned, DHT randomly samples the nodes in a uniform manner.
This means that similar amount of storing requests are pushed to every node.

The durability guarantees of traditional DHTs assume that the storage nodes always accept store requests.
The assumption is valid for metadata service like IPFS, where the actual content is stored external to the DHT, and only MB-scale data is stored on each node.
However, it's not the case for DSNs like Swarm which directly utilize DHT as content storage, and the durability guarantee may be broken because of this.
The storage capacity on the nodes may be exhausted.
We measure how far the storage nodes are from exhausted with \emph{available capacity}, the number of contents a node can hold with its unused storage capacity.
\footnote{In this work we only consider fixed-size contents and state that varied-size contents can be split into fixed-size chunks.}
A node with zero AC is considered \emph{overwhelmed}.
The overwhelmed nodes cannot serve any further storing request, and may cause serious durability problems if DHT keeps pushing storing requests to them.
\lijl{One way to rephrase this point: guarantees of traditional DHT assume that each node always accepts a store request. Violating that assumption will break the guarantees.}
\gd{Updated.}

we simulate Swarm to provide a comprehensive study on the available capacities of storage nodes in a DHT storage network.
The setup details of the simulation are stated in \autoref{sec:overview}.
As shown in \autoref{fig:ac-distr}, the AC of storage nodes in DHT scatters across the wide range.
For the nodes with the same size, their AC distributes across 10 different magnitudes (of the powers of two).
And the average AC of nodes of different sizes monotonically increases as the node sizes, ranging in 9 magnitudes even though the node sizes only spans across 7 magnitudes.
This is because the expected \emph{utilized} capacity of every node is the same, regardless of the storage node size.
And that same utilized capacity would bring the AC of smaller nodes more magnitudes down than the larger ones.
As the result, while some of the smallest ($2^{10}$) nodes have already hit zero AC and been overwhelmed, the largest $2^{17}$ nodes also utilized around $2^{10}$ which is less than 1\% of their capacities, and the overall utilization is just single digit percentages.

\paragraph{The virtual node approach is not effective.}
In this approach, a storage node spawns variable number of virtual nodes, which participant into DHT normally.
In this case each virtual node receives similar workload, and the storage nodes that spawn more virtual nodes can receive more workload and utilize more capacity.

Unfortunately, the virtual node approach is not as promising as it looks like.
Our simulation (\autoref{fig:ac-distr}) shows that the AC distribution of nodes of the same size still varies a lot.
Although the virtual nodes that belong to the same storage node can share their underlying capacities, the small storage nodes with few virtual nodes are still easily overwhelmed.
Furthermore, the AC of storage nodes are still not balanced even if the AC of virtual nodes is balanced, as the storage nodes that spawn more virtual nodes will have a higher aggregated AC.
And lastly, the virtual node approach introduce extra implication of correlations among the virtual nodes.
As DHT is not aware of the ownership of the virtual nodes, it may accidentally allocate redundancy of the same content to different virtual nodes of the same storage node.
This results in a weaker durability than expected.
