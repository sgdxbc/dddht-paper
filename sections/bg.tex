\section{Background}
\label{sec:bg}

\subsection{Distributed Hash Tables}
\label{sec:bg:dht}

In this section we first introduce the elementary on distributed hash tables, and then elaborate in their recent usages in decentralized storage networks.

The core of distributed hash tables is consistent hashing~\cite{chash}.
Consistent hashing is an efficient solution for assigning and balancing workload in various key-value stores or block stores.
Given $m$ keys and $n$ nodes, a consistent hashing algorithm assign $k$ nodes for each key and guarantees a balanced assignment, \ie, each node is expected to be assigned with $\frac{km}{n}$ keys.
By applying consistent hashing, a hash function universally maps the keys and the storage nodes on to the same hash domain, and the values are assigned to one or more nodes based on their relations after mapping.
For example, some consistent hashing organizes the hash space into a ring (by wrapping around), and the values are assigned to the first node(s) encountered by clockwise walking on the ring.
The assigned nodes are called the \emph{placement groups} of the values.

Consistent hashing guarantees that during resizing, only minimal number of keys (\ie, the average number of keys per node) will be remapped to a new node on average.
This property enables consistent hashing to become a desirable placement solution in dynamical node or fault tolerate scenarios.
Consistent hashing is preferred in data center storage because it does not rely on a centralized controller or metadata server.
Nodes and clients can locate the data independently, which improves performance and fault tolerance.
Consistent hashing is adopted by industrial-level storage systems like Ceph~\cite{weil2006ceph}, Cassandra~\cite{lakshman2010cassandra} and Dynamo~\cite{decandia2007dynamo} and is extensively studied for applying in distributed database~\cite{shu2020th,liu2019distcache,chung2019lightstore}, network load balancer~\cite{eisenbud2016maglev} and cloud infrastructures~\cite{nakatani2021structured,wu2019autoscaling}.

In some highly dynamical and/or asynchronous scenarios such as in public peer-to-peer (P2P) networks and/or with high failure-rate nodes, there may be difficulties for every node to fetch the up-to-date view of currently online nodes.
Also, the systems may scale up to tens or even hundreds of thousands of nodes, rendering impractical to record all node identities and contacts (\eg IP addresses) on every individual node.
Distributed hash tables (DHT)~\cite{maymounkov2002kademlia,chord,rowstron2001pastry} are built around consistent hashing to cope with these issues.
With DHT protocols, nodes can ad-hoc \emph{discover} the current placement groups of keys while locally maintaining the contacts for only a small subset of the nodes.
Essentially, DHT protocols assemble the nodes into an \emph{overlay network}, which routes the keys to their placement groups.
Underneath, DHT distributes the node records which pair node identities with their contacts across the nodes.
DHT protocols feature a record retaining policy where the nodes decide which records to preserve locally, and a lookup protocol that iteratively look up the node(s) composing the placement group of the keys.
DHT protocols ensure efficient network and storage consumption.

The most prevalent DHT protocol is Kademlia~\cite{maymounkov2002kademlia}, and our study is mainly performed around it.
Kademlia guarantees logarithm network and storage consumption.
In a network consists of $N$ nodes, each node store $O(\log{N})$ records, and the lookups of keys are expected to terminate in $O(\log{N})$ message steps.
The consistent hashing algorithm of Kademlia is simple.
Given a key $k$, the \emph{distance} $d$ between the key and a node whose identity is $id$ is the unsigned integer represented by the \texttt{xor} of $k$ and $id$\footnote{For brevity, we use \emph{key} and \emph{identity} to refer the mapped hash values of them, and they should be mapped into the same hash space (\ie has same length).}
\[
    d(k,id)=k\ \texttt{xor}\ id
\]
then, the key is assigned to the nodes $G_k$ who have the smallest distances to the key for storing
\[
    G_k=\{n\mid{}d(k,ID[n_i])<d(k,ID[n]),n\in{}\mathfrak{N}\setminus{}G_k,i\in{}[1,\dots,r]\}
\]
where $ID$ is the mapping from nodes to their identities, $\mathfrak{N}$ is the set of all nodes and $r$ is the configurable \emph{redundancy rate} of the network, \ie, the size of the placement groups.
In practice $r$ is usually set to $20$ to tolerate frequent node churning and failures in permissionless systems.

In Kademlia, each node keeps a set of node records that are effectively randomly sampled from all nodes.
The density of the sampled nodes depends on the distance between identities of the storing node and the record.
Nodes sample more record from the near records, and the sampling rate decreases exponentially to the distance.
For looking up a key, nodes initialize a candidate list with the locally-stored records that are the closest one to the key, and query each of the candidates.
The queried nodes respond with the closest records according to their local stores, and the querying node update the candidate list accordingly.
The querying node then iteratively query subsequent candidates until the list converges to a fix point and get finalized as the placement group for the key.
Readers can refer to the original work~\cite{maymounkov2002kademlia} for details.
The takeaway is that this iterative procedure is proved to terminate with the records that are globally closest in the key, matching the key's placement equation above.
Then the node can either store or update the value associated for the key on those recorded nodes, or it can retrieve the previously-stored value from them.

Since its emergence in early 2000s, DHT protocols have been widely adopted in P2P storage networks~\cite{kubiatowicz2000oceanstore,ratnasamy2001scalable,benet2014ipfs,trautwein2022design,haeberlen2005glacier}, for its desirable functionality in such permissionless settings.
These storage networks are modernized into the concept of decentralized storage network (DSN) and gaining wide attention, influenced by the recent progress in decentralized technologies~\cite{bitcoin,ethereum}.
One of the most well-known DSNs is FileCoin~\cite{filecoin}, which is building upon the decentralized file-discovery network IPFS~\cite{benet2014ipfs,trautwein2022design}.

In IPFS, files and directories are represented as Merkle directed acyclic graphs (DAG), and the contacts of the \emph{providers}, \ie, the storage nodes who store the content of DAG vertexes, are stored in a Kademlia DHT.
The client can look up the DAG vertexes in the DHT to discover their providers\footnote{
    Notice that this is a different kind of discovery to the placement group discovery of DHT.
    In essence, looking up the DHT is discovering the placement group of the provider contacts, and by retrieving the contacts from the placement groups, the providers are discovered.
} and subsequently download the content from them.
Similarly, BitTorrent uses Mainline DHT~\cite{wang2013measuring,xinxing2016measurement} to perform peer discovery since 2005, which is a variant of Kademlia DHT.
A recent work~\cite{cortes2024scalability} proposes to use Kademlia DHT in Ethereum~\cite{ethereum} to discover the validators that store the blob shards in order to perform data availability sampling~\cite{hall2023foundations} against the blob storage network in a privacy-preservation way.

While these DSNs use DHTs to orchestrate for storing the contacts of the storage nodes, most of the storage systems directly issue the data placement with DHT protocols, that is, storing the actual data \emph{as} the values associated to the keys.
These works include various DSNs including Glacier~\cite{haeberlen2005glacier}, OceanStore~\cite{kubiatowicz2000oceanstore}, CFS~\cite{dabek2001wide} and PAST~\cite{druschel2001past}.

More recently, Swarm~\cite{team2021swarm} is a novel DSN that reliably manages data with a hybrid approach mixing DHT and replication.
All nodes join a Kademlia overlay network and can discover each other with it, and the nodes whose distances to each other is smaller than a threshold (\ie their identities has a common prefix of certain length) compose a ``neighborhood'', the members of whom fully replicate the data stored by each other.
Essentially, Kademlia assigns the data to the neighborhoods, and the assigned neighborhoods replicate the data within to ensure high availability.

While in centrally-managed environment consistent hashing is deployed mostly for performance reason or eliminating single point of failure, in permissionless DSNs DHT protocols could be the substantial machinery to overcome the restrictions brought by the highly-dynamical and P2P nature, enforcing decent data placement that are well-balanced distributed across the nodes who lack central coordination.

\subsection{Revisiting DHT with Heterogeneous Bounded Loads}
\label{sec:bg:problem}

While IPFS and BitTorrent dump only indexing metadata into DHT, incurring trivial storage consumption (several MBs) on each node, the DSNs that directly rely on DHT for data placement can put tons of data on to individual nodes under a decent utilization, potentially reaching the storage capacity limits of the nodes.
Actually, data placement of DSNs is much harder than one of centrally-managed systems on keeping the storage utilization of individual nodes within their capacity budgets.
Firstly, the nodes are not centrally managed, orchestrated or monitored, so it's hard to predict the load of the nodes without knowing the nodes' capacities (reliably) and a global view of nodes' real time status.
Secondly, unlike the centrally managed machines which are usually homogeneous, in DSNs, different nodes can have dramatically diverse storage capacities, ranging from mobile devices contributing 10s of GBs of spare storage, to professional storage clusters that provision TBs of dedicated storage capacities.
If we assign these nodes with equal storage load, at low overall utilization the giant nodes will be almost idle; and even worse, at a slightly higher overall utilization, the tiniest nodes will be overwhelmed.

Surprisingly, the data placement of DHTs is indeed uniform across the nodes regardless of their storage capacities, and previous DSNs have overlooked this issue.
In Kademlia, the keys and the identities are uniformly distributed across the hash value space.
As the result, the placement groups of the keys include every node with the same probability, so the expected number of placement groups that a node is included is the same for every node.
The crux is that Kademlia, along with other aforementioned DHTs, does not take the \emph{heterogeneity} of nodes into the considerations of its consistent hashing algorithm, while realizing the storage heterogeneity is crucial for efficiently or even correctly utilizing the available storage capacity.
This particular issue has not been (carefully) covered by the previous DSN works.
For example, Glacier will simply reject the store request when the nodes in the placement group have exhausted their storage.
Swarm purposes an economic policy that the nodes evict the stored data with the least bidding value when running out of space.
Thus, it does not provide strict availability guarantee.

This issue can significantly affect the responsiveness or the availability of DSNs.
To demonstrate its effect, we simulate a DSN with heterogeneous storage nodes whose identities are generated with uniform randomness. 
The detailed parameters of the simulated network are presented in \autoref{sec:overview}.
In the simulation, we continuously attempt to store uniformly random data into the network.
If the placement group of the data contains any node that has exhausted its storage space, then it can either reject the store request or randomly evict a previously stored data from its storage, similar to Glacier's and Swarm's approach, respectively.
\autoref{fig:overwhelm} shows the consequences of both choices.
With rejection, the rejection rate already increase to more than 90\% and the storage network hardly accepts any further requests when only about 10\% of overall capacity is utilized.
With eviction, the storage network starts to evict at only 6\% of overall utilization, and starts to lose data soon after that.
In conclusion, the network has to pick one from the loss of responsiveness or availability or trade off between them.

Even worse, availability can be lost even without any external activity.
When nodes churn from the network, DHT reallocates its stored data on to another node according to the consistent hashing algorithm.
If the reallocated node has no spare storage space to receive the transferred storage load, it has no choice but to discard either its own or incoming data.
In the case of the whole network scaling down, which may just be caused by ordinary fluctuation or transient network partitioning, such discarding will massively happen, and any data loss caused by it cannot be reverted afterward when the network soon scales up back to its original.

\paragraph{Problem settings.}
In summary, we show the problem of combining a DHT that homogeneously distributes the storage load and the storage nodes with heterogeneous storage capabilities.
The ultimate goal is to optimize for the \emph{effective overall utilization}: the faction of the aggregated storage capacity of the nodes that a DSN can utilize before it exhausts the storage space of individual storage nodes and suffers from responsiveness and/or availability degradation.
The primary ability required for DHTs to achieve the goal is to allocate placement groups respecting to the storage heterogeneity, forwarding more store requests to the nodes with more storage.
As we discuss in the following section, previous works fail to enhance DHTs with such ability.

\subsection{Previous Studies}

The most straightforward way to approach the problem is employing \emph{virtual nodes}.
In the work originally proposing Chord~\cite{chord}, the work mentions to deploy $O(\log{N})$ virtual nodes per physical nodes to significantly counter the probabilistic nonuniform identity allocation.
CFS also considers the heterogeneity of the processing capacity of the nodes and suggests allocating virtual nodes accordingly.
Later works~\cite{zhu2005efficient, zhang2010novel} also study the virtual node approach to load balance in DHT.
The virtual nodes that reside on the same physical node can share their underlying hardware resources and hedge the probabilistic offsets, and spawning more virtual nodes can effectively increase the storage load landing on the physical node.

However, virtual node is not the elixir for the problem.
Firstly, virtual node scales the consumption of \emph{all} kinds of resources simultaneously.
While spawning more virtual node can increase storage utilization on storage-rich nodes, it also increases the network overhead proportionally and the nodes may not be network-rich as well~\cite{karger2004simple}.
More importantly, virtual node introduces \emph{hidden failure correlation}.
The virtual nodes backed by the same physical node are highly likely to fail together.
While these nodes are unlikely to engage in the same placement group, DSNs usually split large file content into multiple segments and assign individual placement groups for each of them (like the Merkle DAG approach mentioned before), and eventually associate the file with tremendous nodes.
The DSNs assume these placement groups are independent to each other, and this assumption is invalid if the virtual nodes of the same physical node join multiple placement groups of the same file content.
The crux is that DSN is unaware of the underneath correlation pattern of the virtual nodes, and cannot considerately choose security parameters (\eg redundancy rate) with such unawareness.
Previous work~\cite{schindelhauer2005weighted} also argue for other weaknesses of virtual node, which we will not detail here.

Other than virtual node, there are various solutions targeting heterogeneous nodes or nodes with bounded load, but none of them completely aligns the problem.
Early works~\cite{karger2004simple,misra2004clash} study the load balance schemes for DHT soon after DHT itself is proposed.
These works focus on the nonuniform key-accessing workload instead of nonuniform resources on the nodes.
The works can ensure a balanced load on homogeneous nodes when the accessing load of the stored data is different, but they are not for applying proper loads that \emph{match} the capacities of heterogeneous nodes.
Also, as they concern nonuniform per-key load, they are helpful on balancing bandwidth and computation demand rather than storage demand, since per-key storage load is constant\footnote{
    In this work we consider fixed-length values/data blocks, and assume large data is split into segments like ~\cite{benet2014ipfs}.
}.
On the other hand, weighted DHT~\cite{schindelhauer2005weighted} purposes to assign weights to the nodes according to certain heterogeneity aspects, which seems to fit the problem settings.
However, the semantic of \emph{weighted} is subtly different from the desired \emph{bounded}.
Specifically, the load should be distributed proportional to the remaining available storage spaces of the nodes instead of their total storage capacities.
We will elaborate on this difference in \autoref{sec:overview}.
Also, the work requires spawning multiple virtual nodes, so it does not suit the storage heterogeneity as discussed previously.

Recently, \cite{mirrokni2018consistent} designs a consistent hashing scheme that respects bounded loads.
It considers node overwhelming similar to \emph{hash collision} and resolves it with linear probing like a simple hash table.
Random jump consistent hashing\cite{chen2021revisiting} improves on it by resolving the cascaded overflow phenomenon.
While these works exactly target the bounded load setting and can be applied to heterogeneous storage nodes, they assume a centrally-managed environment where every node can easily contact each other based on its local information.
Without an efficient DHT design, the works cannot be applied to DSNs.

\paragraph{The DHT approach.}
Other DSNs directly control the placement groups of contents.
Storj~\cite{storj2018storj} centrally tracks the behavior of storage providers, and allocates the placement group based on the trust level of the storage providers.
Swarm~\cite{team2021swarm} replaces the centralized allocator with DHT~\cite{maymounkov2002kademlia} and allocates placement groups with consistent hashing.
The DHT randomly samples storage providers to form placement groups.
Since the sampling on storage providers is independent, the placement group contains at least certain number of honest storage providers with high probability.
Any faulty redundancy is detected by proof of storage and repaired timely.

In Kademlia DHT~\cite{maymounkov2002kademlia} every content and node have an \vid.
The \vid is usually the hash of the content or the node's public key to enable self-certifying contents and nodes.
Then we can calculate the \texttt{xor} distance between node and content \vid{}s.
A content is assigned to the $r$ nodes whose \vid{}s are the closest ones to the content's \vid, which becomes the content's placement group, and $r$ is the targeted redundancy level.
Kademlia provides an operation \ffind(\var{k}, \var{r}) to the nodes, which can discover the \var{r} closest nodes to \var{k} in the network.
The \ffind operation is implemented in an iterative approach that is expected to finish in $\log(N)$ steps where $N$ is the number of nodes.
To tolerate node failures and churns, the storage nodes periodically re-discover the placement group of the stored contents, and re-replicate the contents if the discovered nodes are different.

\gd{Resolved. It leads to extra redundancy if \ffind result is unstable, but that is too subtle.}

Because the node and content's \vid{}s are uniformly distributed in the \vid{}'s domain space, the placement groups of contents can be considered as $r$ random samples of storage nodes that are uniformly distributed across all nodes without replacement.
So the probability of data loss in a time unit $\epsilon$ can be derived from the failure rate $f$, \ie, the probability for a storage node to fail in the time unit, and the redundancy level $r$
\[ \epsilon = f^r \]
If the failure rate is set to $f=\frac{1}{3}$, a redundancy level $r=13$ yields $1-\epsilon>99.9999\%$ \ie the durability is over ``six nines''.
The mean time to data lost (MTTDL) can further be derived as $\frac{1}{\epsilon}$ time units, which are about 4368 years when a time unit equals one day or 182 years when equals to an hour.

DHT relives the burden of the storage nodes by taking the responsibility of placing contents on them, so it becomes critical that how well DHT can make proper placement decisions.

This means that similar amount of storing requests are pushed to every node.

The durability guarantees of traditional DHTs assume that the storage nodes always accept store requests.
The assumption is valid for metadata service like IPFS, where the actual content is stored external to the DHT, and only MB-scale data is stored on each node.
However, it's not the case for DSNs like Swarm which directly utilize DHT as content storage, and the durability guarantee may be broken because of this.
The storage capacity on the nodes may be exhausted.
We measure how far the storage nodes are from exhausted with \emph{available capacity}, the number of contents a node can hold with its unused storage capacity.
\footnote{In this work we only consider fixed-size contents and state that varied-size contents can be split into fixed-size chunks.}
A node with zero AC is considered \emph{overwhelmed}.
The overwhelmed nodes cannot serve any further storing request, and may cause serious durability problems if DHT keeps pushing storing requests to them.
\lijl{One way to rephrase this point: guarantees of traditional DHT assume that each node always accepts a store request. Violating that assumption will break the guarantees.}

we simulate Swarm to provide a comprehensive study on the available capacities of storage nodes in a DHT storage network.
The setup details of the simulation are stated in \autoref{sec:overview}.
As shown in \autoref{fig:ac-distr}, the AC of storage nodes in DHT scatters across the wide range.
For the nodes with the same size, their AC distributes across 10 different magnitudes (of the powers of two).
And the average AC of nodes of different sizes monotonically increases as the node sizes, ranging in 9 magnitudes even though the node sizes only spans across 7 magnitudes.
This is because the expected \emph{utilized} capacity of every node is the same, regardless of the storage node size.
And that same utilized capacity would bring the AC of smaller nodes more magnitudes down than the larger ones.
As the result, while some of the smallest ($2^{10}$) nodes have already hit zero AC and been overwhelmed, the largest $2^{17}$ nodes also utilized around $2^{10}$ which is less than 1\% of their capacities, and the overall utilization is just single digit percentages.

\paragraph{The virtual node approach is not effective.}
In this approach, a storage node spawns variable number of virtual nodes, which participant into DHT normally.
In this case each virtual node receives similar workload, and the storage nodes that spawn more virtual nodes can receive more workload and utilize more capacity.

Unfortunately, the virtual node approach is not as promising as it looks like.
Our simulation (\autoref{fig:ac-distr}) shows that the AC distribution of nodes of the same size still varies a lot.
Although the virtual nodes that belong to the same storage node can share their underlying capacities, the small storage nodes with few virtual nodes are still easily overwhelmed.
Furthermore, the AC of storage nodes are still not balanced even if the AC of virtual nodes is balanced, as the storage nodes that spawn more virtual nodes will have a higher aggregated AC.
And lastly, the virtual node approach introduce extra implication of correlations among the virtual nodes.
As DHT is not aware of the ownership of the virtual nodes, it may accidentally allocate redundancy of the same content to different virtual nodes of the same storage node.
This results in a weaker durability than expected.
