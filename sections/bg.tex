DSNs are under the same critical attack vector as the blockchains.
By utilizing DSNs, the durability of DSNs becomes part of the safety guarantee of blockchains themselves.
Proof of storage can rapidly detect faults and allows DSNs to repair (relatively) timely.

\paragraph{Threat model.}
\lijl{People might be confused if we start the thread model with storage proofs. Maybe summarize the different faulty behaviors. Storage proofs address one of them, i.e., claiming objects are stored but actually not.}
Time is divided into \emph{proof periods}.
Storage nodes submit proof of storage for the contents they stored in every proof period.
The proofs attest:
\begin{enumerate*}
    \item the stored contents are durable with sufficient redundancy, which enables external auditing, and
    \item the utilized capacities of storage nodes.
\end{enumerate*}
\lijl{How to prove utilized capacity?}
The storage capacity must be correctly utilized in a proof period, even if it belongs to a Byzantine faulty storage provider, as long as a proof of storage is submitted for it.
On the other hand, any faulty storage capacity can only be detected at the end of the proof period for the lack of proof of storage.
We also assume that in a proof period the system is able to finish repairing for any repairable faults.
\lijl{We didn't discuss repair in the intro. Do we use the same repair strategy in DHT? Any additional consideration given our new DHT model?}
For a system that only employs replication as redundancy, a fault is repairable means not all copies of the data are lost.
As the result, a DSN is durable as long as it can preserve some copies of every stored data in every proof period.

We assume that at most $\frac{1}{3}$ of the storage capacity can be faulty in a proof period.
This includes innocent faults, \eg, disk failure and node churning, and Byzantine faults.
\lijl{We still need to define what Byzantine fault means for storage capacity. Probably the node controlling the capacity is Byzantine, which is similar to other BFT work.}
The faulty capacity can be arbitrarily distributed across the faulty nodes.

We assume Sybil attack is mitigated through mechanism like staking, so the number of Byzantine nodes is limited.

\paragraph{Alternative DSN approaches.}
We have different kinds of DSNs curated in \autoref{tab:dsn}.
We compare the DSNs in three metrics: whether they require explicitly maintaining metadata about contents \emph{placement group} i.e. where to find them, whether they put storage nodes into a competitive environment and whether they can efficiently achieve durable, that is, the data size that they are durably stored versus the total storage supply.
\lijl{What is a competitive environment?}

Some DSNs do not control the placement groups of contents.
Filecoin and Sia provide a storage market and on-chain storage contracts and storage nodes bid for storage tasks.
Arweave and EthStorage do not use explicit contract, instead all storage nodes that store a content share the profit.
Both rely on storage nodes to discover profitable storage tasks (storage contracts with high reward or the contents that have fewer copies and are more risky to lose).
Requires frequent polling on the blockchain.
In Filecoin nodes moreover competes for lowest storage cost and the winner wins all.
In Arweave, though there is no direct competition among nodes, it has no control on how many copies are stored results in inefficient utilization of storage supply.

The common property is that in these DSNs storage nodes are under a competitive environment, each storage node can only rely on its own.
Encourage fewer, more powerful storage providers, increase the centralization of the system.

\paragraph{The DHT approach.}
Other DSNs directly control the placement groups of contents.
Storj centrally tracks the behavior of storage providers, and allocates the placement group based on the trust level of the storage providers.
Swarm replaces the centralized allocator with DHT and allocates placement groups with consistent hashing.
The DHT randomly samples storage providers to form placement groups.
Since the sampling on storage providers is independent, the placement group contains at least certain number of honest storage providers with high probability.
Any faulty redundancy is detected by proof of storage and repaired timely.

In Kademlia DHT every content and node have an \vid.
The \vid is usually the hash of the content or the node's public key to enable self-certifying contents and nodes.
Then we can calculate the \texttt{xor} distance between node and content \vid{}s.
A content is assigned to the $r$ nodes whose \vid{}s are the closest ones to the content's \vid, which becomes the content's placement group, and $r$ is the targeted redundancy level.
Kademlia provides an operation \ffind(\var{k}, \var{r}) to the nodes, which can discover the \var{r} closest nodes to \var{k} in the network.
The \ffind operation is implemented in an iterative approach that is expected to finish in $\log(N)$ steps where $N$ is the number of nodes.
To tolerate node failures and churns, Kademlia periodically re-discover the placement group of the content, and re-replicate the content if the discovered nodes are different.
\lijl{Who initiates re-replication? If two \ffind return different results, would it lead to extra redundancy?}

Because the node and content's \vid{}s are uniformly distributed in the \vid{}'s domain space, the placement groups of contents can be considered as $r$ random samples of storage nodes that are uniformly distributed across all nodes without replacement.
So the probability of data loss in a time unit $\epsilon$ can be derived from the failure rate $f$, \ie, the probability for a storage node to fail in the time unit, and the redundancy level $r$
\[ \epsilon = f^r \]
If the failure rate is set to $f=\frac{1}{3}$, a redundancy level $r=13$ yields $1-\epsilon>99.9999\%$ \ie the durability is over ``six nines''.
The mean time to data lost (MTTDL) can further be derived as $\frac{1}{\epsilon}$ time units, which are about 4368 years when a time unit equals one day or 182 years when equals to an hour.

The DHT approach is the most ideal one for DSN with lightweight storage nodes.
There's no metadata management, so no need to introduce centralized controller or require storage nodes to frequently query the blockchain to update the metadata.
\lijl{Decentralized metadata is the key problem here. IPFS address how to store metadata in a decentralized network, but it doesn't solve how the assignment metadata is generated in a decentralized manner. The other approaches help, but their assignment strategies still have issues.}
The DSN is responsible for allocating storing tasks to storage nodes, and DHT uniformly allocates tasks to random storage nodes.
The nodes cannot and do not need to compete for the tasks.

\subsection{The Problem with DHT}
\label{sec:bg:problem}

DHT relives the burden of the storage nodes by taking the responsibility of placing contents on them, so it becomes critical that how well DHT can make proper placement decisions.
Since the network \emph{pushes} storing requests to the storage nodes, it's hard for the storage nodes to reject the requests or hand off to other nodes.
\lijl{Why is this the case?}
However, as previously mentioned, DHT actually randomly samples the nodes in a uniform manner.
This means that similar amount of storing requests are pushed to every node.

However, storage nodes are heterogeneous.
They may provide different storage capacities, and they may already be holding different size of contents: because of probabilistic fluctuation or the contents have different expiration duration.
So the abilities of the storage nodes to serve storing requests are different.
We measure this ability with \emph{available capacity}, the number of contents a node can hold with its unused storage capacity.
\footnote{In this work we only consider fixed-size contents and state that varied-size contents can be split into fixed-size chunks.}
A node with zero AC is considered \emph{overwhelmed}.
The overwhelmed nodes cannot serve any further storing request, and may cause serious problems if DHT keeps pushing storing requests to them.
\lijl{One way to rephrase this point: guarantees of traditional DHT assume that each node always accepts a store request. Violating that assumption will break the guarantees.}

We simulate Swarm to provide a comprehensive study on the available capacities of storage nodes in a DHT storage network.
The setup details of the simulation are stated in \autoref{sec:overview}.
As shown in \autoref{fig:ac-distr}, the AC of storage nodes in DHT scatters across the wide range.
For the nodes with the same size, their AC distributes across 10 different magnitudes (of the powers of two).
And the average AC of nodes of different sizes monotonically increases as the node sizes, ranging in 9 magnitudes even though the node sizes only spans across 7 magnitudes.
This is because the expected \emph{utilized} capacity of every node is the same, regardless of the storage node size.
And that same utilized capacity would bring the AC of smaller nodes more magnitudes down than the larger ones.
As the result, while some of the smallest ($2^{10}$) nodes have already hit zero AC and been overwhelmed, the largest $2^{17}$ nodes also utilized around $2^{10}$ which is less than 1\% of their capacities, and the overall utilization is just single digit percentages.

\paragraph{Problem with overwhelmed nodes.}
If DHT still pushes storing requests to an overwhelmed node, it can only choose to either reject the requests or evict previously-stored contents.
\autoref{fig:overwhelm} shows the consequences of both choices.
With rejection, the storage network hardly accepts any further requests when only about 10\% of overall capacity is utilized, and the rejection rate already increase to more than 90\%.
With eviction, the storage network starts to evict at only 6\% of overall utilization, and starts to lose data soon after that.

And even worse, the durability can be affected even when no new request is coming externally.
When the nearby nodes churn, internal re-replication may be pushed to overwhelmed nodes as well.
Not to mention in the case of network scaling down, which could due to the normal fluctuation or simply false positive caused by transient network partitioning, the redundancy kept by the left nodes ``collapses'' on the remaining nodes.
In such case, the overwhelmed nodes have no choice but to evict (either previously-stored or re-replicated contents), which leads to irreversible data loss.

\paragraph{The virtual node approach is not effective.}
The previous works \xxx{cite} widely use the virtual node approach to load balance in DHT.
In this approach, a storage node spawns variable number of virtual nodes, which participant into DHT normally.
In this case each virtual node receives similar workload, and the storage nodes that spawn more virtual nodes can receive more workload and utilize more capacity.

In conclusion, while today's DHT can \emph{balance} well across homogeneous nodes, it fails to \emph{differentiate} well across heterogeneous nodes.
