\section{A New Fault Model for Decentralized Storage}
\label{sec:model}

In this section, we present a new fault model that properly captures the failure characteristics of a decentralized system.
We provide key rationales and formal definitions of the model.
Using this new model, we run simulations to evaluate durability guarantees of prior approaches.

\subsection{Failure Characteristics of Decentralized Storage Systems}
\label{sec:model:character}

The durability guarantee of a storage system hinges on the failure characteristics of its deployment: An object is \emph{permanently lost} once the number of data fragments (or copies) on non-failing storage devices drops below a threshold~\footnote{We only consider permanent failures.
Recoverable failures only impact data availability, not durability.}.
A critical such characteristic is the \emph{failure domains} of the deployment.
Devices within a failure domain are subjected to correlated failures, \ie, failure events that impact all devices in the domain simultaneously.
A storage system therefore need to place object fragments into multiple, independent failure domains to avoid data losses induced by correlated failures.
Independent failures, on the other hand, are easier to handle.

How to determine the failure domains of a storage system?
In centrally managed systems, the administrators has complete knowledge about the deployment: makes, models, and batches of disks, identity of servers that reside in the same rack/pod/cluster, the network topology, power distribution and redundancy, etc.
They can, therefore, derive a good estimation of all the failure domains and their relative failure probability.
For instance, servers within the same rack have a higher correlated failure rate than those from distinct racks;
disks from the same make and model are more likely to fail simultaneously than those from different vendors.

In contrary, a decentralized system lacks such centralized, accurate information to deduce failure correlation.
Participants are from distinct administrative and management domains;
for security and privacy concerns, they do not expose sensitive information such as location, identities, and system configurations.
Consequently, no single entity in the system has complete, prior knowledge about the failure domains of all storage devices.
For instance, two nodes might locate within the same rack or reside in two continents;
no system participant, however, can \emph{reliably} determine the true case.
Failure correlations are only revealed after simultaneous failures actually occur.
Unfortunately, such information is already \emph{too late} to prevent durability violations.

\subsection{A Fault Model for Decentralized Storage}
\label{sec:model:model}

A fault model that reflects characteristics of real decentralized deployments is critical to reason about the durability guarantee of a decentralized storage system.
As discussed in \autoref{sec:model:character}, failure domains are not known \emph{a priori} in such environment.
Prior decentralized storage solutions~\cite{} essentially shunned issue, and assume that node and device failures are effectively independent.
\lijl{The claim is probably too strong.
They still try to apply some mechanisms to make failures independent, but just not enough.
Might want to clarify this point.}
Such optimism, however, can easily lead to data losses in practice: The placement policy may select nodes with strong failure correlation, which is unknown to the policy, for storing a critical number of fragments of an object.
\lijl{We might want to illustrate this point using an example or diagram.}

How do we properly model failure domains, given that they are unpredictable and unknown?
The answer is intuitive: We rely on a \emph{probabilistic} failure domain model.
To our best knowledge, ours is the first work that considers such a model for decentralized storage.
As demonstrate later, our new definition accurately models realistic decentralized deployments, and reveals poor durability guarantees of prior systems.

\subsubsection{Failure domain definition}

The model assigns a failure domain to \emph{every combination} of nodes which ever join the system.
For instance, if there are three nodes $n_1, n_2, n_3$, the model considers $3! = 6$ failure domains ($\lbrace n_1 \rbrace$, $\lbrace n_2 \rbrace$, $\lbrace n_3 \rbrace$, $\lbrace n_1, n_2 \rbrace$, $\lbrace n_2, n_3 \rbrace$, $\lbrace n_1, n_3 \rbrace$, $\lbrace n_1, n_2, n_3 \rbrace$).
Note that failure domains can overlap --- $n_1$ belongs to four failure domains.
This is consistent with failure correlations in real deployments: a device might reside in the same rack with other devices, but also share the same make and model with another group of devices.
The model also accounts for nodes joining and leaving the system.
A failure domain is only considered \emph{active} if all its nodes are alive.
\lijl{Alternatively, all other failure domains have failure rate 0.}
For example, when $n_1$ initially joins the system, the only active failure domain is $\lbrace n_1 \rbrace$.
Once $n_2$ joins the system, the set of active failure domains extends to $\lbrace n_1 \rbrace$, $\lbrace n_2 \rbrace$, and $\lbrace n_1, n_2 \rbrace$.

\subsubsection{The failure generator.}

Each failure domain, as defined above, has a different failure rate.
Correlated failures that impact large number of devices are less likely than those of smaller scales;
devices within the same rack have higher chance to failing simultaneously than those geographically distributed;
servers that share the same vulnerabilities are more likely to experience correlated failures than those with distinct defense mechanisms.
\lijl{Should provide some evidences and citations here.}
Given their complex nature, accurate reasoning or prediction of the failure rate of a domain is challenging, particularly in decentralized deployments~\cite{irisstore}.

To account for failure domain heterogeneity, we define a generic \emph{failure generator} $f_g$ in our model.
The generator is a function that assigns the failure rates of each failure domain:
$$
P(d) = f_g(d), d = \lbrace n_1, n_2, \dots \rbrace
$$
where $d$ is a failure domain consisting of $n_1, n_2, \dots$, and $P(d)$ denotes the probability that all nodes in $d$ fail simultaneously~\footnote{``Simultaneous'' here means failing within a short time interval.
Critically, the interval is too short for participants to perform recovery actions.}.
\lijl{Why is $P(d)$ on the left side of the equal sign?
Are we not defining $f_g(d)$?}
The generator could assign failure rate $0$ to a failure domain, indicating that simultaneous failure of the entire domain is impossible.
Note that the generator is time-independent.
In a real deployment, failure rate of a domain changes over time.
For instance, the failure probability and the lifetime of storage devices are positively correlated;
adversaries may choose victims to compromise based on runtime information.
We leave time-dependent failure generators as future work.

\subsubsection{Putting things together}

With our definition of failure domains and failure generators, we can define an \emph{operational model} for storage networks.
The model consists of an infinite number of nodes and a failure generator $f_g$.
Initially, the model assigns $N$ nodes to join the system.
In each time unit, the model enumerates all \emph{active} failure domains, and samples domains to fail based on probability given by the failure generator.
The set of failed nodes is the union of all the sampled failure domains.
Note that independent failures are also modeled: The set of failure domains includes the singleton set.
For simplicity, new nodes immediately join the system, so that the system size remains constant at $N$.

\paragraph{Constant failure generator.}

\subsubsection{Why not Markov model?}

As illustrated in \autoref{sec:background}, the protocol for fault tolerate in a storage system is essentially a chasing and escaping between data loss and data repairment: the repairment must be timely enough so that the data can always escape from (will be) failed nodes and keep in safe places.
\sgd{TODO illustrate}
The temporal correlations, \ie ``how much the data gets closer/further from being lost because of what happened in the last time unit'', has been the main topic being studied ever since.
The studies are usually conducted by modeling the system with a temporal Markov state machine, where different states represent the data redundancy is lost to different extent, and the system probabilistically transitions among the states over the time.

While such methodology precisely models the temporal characteristics of the failures (and their interactions with repairs), it is not good at modeling the correlations we discussed in \autoref{sec:background}.
In a Markov state machine, a transition from a state to another state with $x$ less encoded fragments persisting corresponds to a correlated failure of \emph{at least} $x$ storage nodes.
The \emph{at least} comes from the possibility of more nodes correlated failed, but the others are not storing the encoded fragments for the studied data object.
What probability we should assign to this transition?
It should be the net probability of all failure domains that holding exact $x$ encoded fragments, but we don't know which those failure domains are, since the state machine does not encode any location information about the fragments.

Actually, the Markov state machine based reasoning makes strong assumption on \emph{system uniformity}: it assumes all storage nodes has the same probability to correlated failed with some number of other nodes (and when the number is zero it becomes an independent failure).
Only so that it doesn't matter which storage nodes are actually holding the fragments, so we don't have to model it.
As discussed above, such assumption is not valid in the studied decentralized systems.

Our fault model, while expanding the ability of reasoning realistic correlated failures (as shown later), simplify the temporal reasoning to maintain practical complexity.
Specifically, we assume no temporal correlation: whatever failure(s) happened in the predecessor time unit, as long as recoverable, will be fully recovered before the current time unit.
The effect of a recoverable failure is not carried across time units at all.

We believe this simplification is reasonable because: a. our proposed storage system, like all the other prior P2P systems, incurs long maintenance periods ranging in minutes to hours scale.
The network latency is expected to be shorter in orders of magnitude, so the network activities for repairment are probably finalized long before the next maintenance period starts.
b. this work targets the P2P networks with relatively low churn rates \ie the node failures happen in a single time unit is on average limited.

(Note that this does not rule out large scale correlated failures.)
In such networks it is feasible to tweak the responsiveness of failures to match our assumption with acceptable overhead \eg network bandwidth.

Nevertheless, in the future more sophisticated temporal reasoning can always be integrated back to our model.
