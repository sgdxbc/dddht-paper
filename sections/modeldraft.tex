\subsection{Threat Model}

We follow a typical decentralized network model.
We presume a churn rate of participant nodes, i.e., a known distribution of node exiting probability versus online time.
We don't model transient failure (e.g. network partitioning) specially.
Instead, we divide transient failure into two categories.
If the failure duration is negligible compare to expected node online time, then it should also be negligible compare to
system parameters (e.g. heartbeat interval) and is ignored.
Otherwise, we consider the node as exiting the system at the beginning of the failure and contribute it into the churn
rate.

We define a hybrid threat model that assumes both attacks from internal and external sources.
At any time, there could be at most $f$ proportion of nodes to behave faulty.
These nodes hold legal and fixed identities (e.g. by staking), and it is economically impractical to create more than
$f$ proportion of faulty nodes.
At the same time, at most $f'$ proportion of nodes may suffer from degraded performance because of external attack, 
e.g., denial of service, network partitioning, etc.
Attackers may target any node and change the victims at any time, but there are at most $f'$ proportion of the nodes to 
be targeted at once, and these nodes will not have Byzantine behavior (if they are not the $f$ proportion faulty nodes 
from the beginning).

Finally, we assume attacker can access to the clear text of stored data objects.

\subsection{System Model}
Assuming an external authorization service, providing interfaces 
\begin{itemize}
    \item AUTH(pk, ..) $\rightarrow$ tk to register certain guarantee of a unit of fresh storage (for now using staking 
    as a placeholder) to be associated with a public key, return a token
    \item VERIFY(tk) $\rightarrow$ pk to check for token's validity, return owner
\end{itemize}

Using DHT as a routing mechanism, providing interfaces
\begin{itemize}
    \item PUBLISH(tk, addr) to announce an authorized token joining the system with expiration. Only accept the 
    publishing by token's owner
    \item FIND(h) $\rightarrow$ addr to look for the publically dialable address of the token that is globally closest
    to a hash, i.e., should be responsible for storing the corresponding fragment
\end{itemize}

Client starts putting new data object by encoding it into encoded objects with a $(n', k', r')$ code that ensures both
$k'/n' > 1-(f'+f)$, and no connection can be built from the context of $n'$ encoded objects to the original data object.
\sgd{incur both $f$ here because a data object can be attacked internally and externally at the same time}
A suitable choice is to use rateless erasure coding with random fragment indexes.
Another choice is to encrypt the data object with different secrets.
The client then must persist the hashes of $n'$ encoded objects, in order to query the data object later.

Then for each encoded object, client generates encoded fragments by splitting encoded object into $k$ parts and 
generating the rateless erasure coding fragments with indexes from $1$ to $n$.
Client then FIND hash of each encoded fragment, and forms the initial committee for the encoded object.
Client sends STORE(encoded object fingerprint, fragment, committee) messages to every node of the committee with 
corresponding fragment. 
The fingerprint includes encoded object's hash, create time and expected live time, signed with client's identity.
The committee field is a mapping from node addresses to fragment indexes.
After sufficient number of nodes of the committee acknowledged the STORE message for every encoded object, client can
conclude the putting.

Upon receiving a verified STORE message, node should store the fragment and periodically broadcast 
HEARTBEAT(encoded object fingerprint, high index) messages to other nodes in the committee.
The high index field is initiated as self's fragment index, which is the highest index of fragment whose responsible 
node has been attempted to contact from the node.
Node keeps track of the encoded object's high index as the highest value that is less or equal to the high index of a
majority of committee's heartbeats.
It updates its local high index if that is less than object's one.
The committee calculates a low watermark of acceptable fragment index which is proportional to the elapsed time since
encoded object's create time.
If the encoded object's expected live time has expired or local fragment index is below the low watermark the node can
stop sending HEARTBEAT and drop the fragment.
If a node does not receive heartbeat with fragment index between watermark and high index from sufficient other nodes 
during a period, it will increase the high index. 
It then derives the hash of the fragment with the new high index, either through homomorphic hashing (with encoded 
object hash and index as input), or fetch fragments from committee, recover the object, then generate the fragment and
get the hash.
It then FIND the responsible node and send STORE same as the client above.
