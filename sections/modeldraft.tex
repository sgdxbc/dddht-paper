\subsection{Threat Model}

At most \XXX percent of identities are faulty, besides, attackers can partition \XXX identities for any duration.
The goal is to build a system that is provable that, the best strategy for a faulty identity is to keep silence.
And the best strategy for an external attacker is to randomly select victims.
If attacker is able to partition more than $k + \epsilon$ victim peers, it could cause data lost if those peers happen to be responsible for the same data object in the same epoch.
This is unavoidable, but the attacker cannot target a specific data object.
We believe the economic inefficiency will prevent such attacking to be conducted.

We don't rely on special networking mechanism, e.g., Tor, to hide peers' identities.
They talk to each other directly.

Data objects have public content.
For example, the hash of original data object is always available to attackers.

Transient failure, churn rate, message eventually delivered, etc.
One consequence is that we cannot "unify" data objects by encryption.
Because if we encrypt data object on one of the peers, then if the peer has left upon retrieval, the data object cannot be decrypted.
If we encrypt data object before pushing it to any peer, then according to the previous rule, the encrypted object is available to attackers.
That means, it is possible for attackers to capture the full content of the encrypted object, derive its hash, and identify responsible peers by looking for peers who send messages contain the hash.

\subsection{Semantic}

The system provides \emph{one-shot read} functionality.
Every data object can only be read at most once after it is stored.
The read can happen at any time before the data object expires, and the system guarantees that the read will be successful.
If read after the expiration, or read more than once, the result is unspecified.
The system assumes certain external mechanism to authenticate the read.

The ration of allowing only one-time read is that, after the read, attacker can monitor all peers that participants the read operation and partition them long enough until none of them are still online.
So it is impossible to keep object safe ever since it is read once.
Anyway, client can store the object again after reading it out, effectively make the system supports multiple reads.
