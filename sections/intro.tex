We are witnessing a technological paradigm shift to move away from service centralization, a hallmark of the cloud computing and web services industries in the past two decades.
This \emph{decentralization} movement is catalyzed by the growing concern over content censorship~\cite{twitter_censorship}, data misuse~\cite{fb_misuse}, monopolistic practices~\cite{google_antitrust}, and single point of organization failure~\cite{ftx_debacle}.
Following the success of the Bitcoin~\cite{bitcoin} and Ethereum~\cite{ethereum} blockchains, a burgeoning of decentralized services are being deployed, including cryptocurrency exchanges~\cite{uniswap,coinbase}, content delivery network~\cite{meson}, domain name service~\cite{handshake}, messaging~\cite{matrix}, and computation~\cite{dfinity}.

An attractive avenue for decentralization is data storage~\cite{ipfs,filecoin,ar,storj}.
Compared to their centralized counterparts~\cite{amazon_s3,google_cloudstore,dynamo,dropbox}, decentralized storage is better positioned to address the issues of data breaches, censorship, content availability, and high storage cost.
We have already seen successful large deployment of decentralized storage systems:
The InterPlanetary File System (IPFS)~\cite{ipfs} has over 300 thousand active participating peers globally, collectively storing more than 1000 PB of data.

A critical requirement for decentralized storage systems is \emph{data durability}, particularly for deployments that store data which represents high-value assets.
Ethereum, for instance, holds account records that are worth more than \$233 billion in total~\cite{eth_market_cap}.
Non-fungible tokens (NFT) listed on blockchains such as Solana~\cite{solana}, Polygon~\cite{polygon}, and Arbitrum~\cite{arbitrum} are already worth tens of billions of dollars~\cite{nft_stats} and quickly growing.
These high-value data cannot be stored on centralized systems due to anti-censorship requirements; neither can they be stored on best-effort P2P solutions like BitTorrent~\cite{bittorrent} and IPFS, as any data loss will have high financial implications.

Decentralization presents fundamental challenges to the durability guarantees of a storage system.
To handle data loss caused by failures, redundancy-based approaches such as replication~\cite{smr,pb,pbft} and erasure coding~\cite{reed-solomon} are commonly used.
These solutions work well in a centralized deployment, where operators have full control over the infrastructure, failure domains, and placement groups with minimum correlated failures.
A decentralized system, on the contrary, has no central authority to manage the behavior and trustworthiness of the participants;
nodes join and leave the system at high churn rate;
there exists high variance in node performance, reliability, and network conditions;
adversarial behaviors are prevalent.
In such open and asynchronous environment, traditional redundancy schemes lose their effectiveness in preventing data losses.
Recently, more than 1600 TiB of data on the Filecoin~\cite{filecoin} network lost all replica copies simultaneously~\cite{filecoin_loss}.

To accurately formalize the challenge of handling correlated failures, we make the following definition of fault and fault tolerance of an open storage system:
\begin{itemize}
    \item There are a certain number of failure domains in the storage system, whose members are hidden to protocol designers.
    The size of failure domains ranges from 1 (\ie independent failure) to the total number of storage nodes (\ie the whole system go down simultaneously, which probably only happen in a nuclear winter).
    Every storage node belongs to at least one failure domain and may belong to multiple failure domains.
    For example, a storage node may belong to one failure domain of all other storage nodes in the same city by considering local nature disasters. If it is running on a cloud platform, it may also belong to another failure domain of all other storage nodes from that cloud platform by considering the cloud platform authority. It may belong to yet another failure domain with all other storage nodes that equips the disks from the same manufacture batch by considering the hardware failures. Again, protocol designers are not able to learn any of these failure domains.
    \item In each failure event, all storage nodes belong to a failure domain permanently leave the system.
    For simplicity, we are not considering transient failures/availability in this work, and if the failure domain may partially fail, we simply model the failed part as another failure domain.
    The churn rate of the system is measured by the total number of left storage nodes in all failure events in a unit time interval.
    In all studied systems we assume (or configure) the total number of contained storage nodes remains constant.
    The faster nodes fail, the faster nodes join.
    Unlike failure domains, we assume the churn rate can be predetermined \ie it's impossible to predict which/when nodes will fail, especially which nodes will fail together, but it's possible to estimate how much portion of nodes will fail in a time window.
    \item The faulty degree of the system is measured by the distribution of the failure domain sizes.
    For example, fixing the other factors, the more the failure domains, or the larger failure domains are, the more faulty the system is.
    \sgd{``The larger the more faulty'' part is straightforward, for the ``the more the more faulty'' part, it means each storage node will involve in more failure domains, so that when selecting it with one random other storage node, there's higher chance that two nodes happen to belong to any common failure domain.}
    A system is considered as not faulty at all if all failure domains have the size one \ie there are only independent failures.
    This also means that a protocol can tolerate failures does not necessary mean it can tolerate fault - only so if it can tolerate correlated failures.
    \item A protocol is considered to tolerate a certain faulty degree if, when the protocol is running on a system whose failure domains are randomly configured according to the failure domain size distribution of that faulty degree, then every stored data object has overwhelming probability to be recoverable at the end of storage period.
    In another word, the protocol tolerates \emph{almost all} possible failure domain configurations.
    Note that it's usually impossible to ensure no data loss under all possible failure domains configurations given any nontrivial failure domain size distribution, as in the worst case the failure domains may be identical to the actual placement.
\end{itemize}
Notice that according to these definitions, churn rate does \emph{not} contribute to the faulty degree.
In this work, we only consider the cases where the churn rate is low enough that the interval between consecutive failure events related to the same data object are much longer than the time to detect and repair for the former failure event, which means the repairs of the data object are never concurrently happening.
With this assumption, a (known to be) higher churn rate can simply be addressed by tweaking parameters related to failure detection/handling.
This means that according to our definition, the systems with same faulty degree produces correlated failure events of same difficulty to be handled, which is exactly what to expect from a definition of faulty.
Nevertheless, it's still meaningful to perform evaluations on repair overhead of systems under different churn rates, in order to show how the systems react to increasingly frequent failure events.

With proper definitions of fault and fault tolerance in mind, we conduct a series of analysis on the previous works.
Given a target faulty degree and churn rate, we generate synthetic system traces in three different ways
\begin{itemize}
    \item Random generate failure domain configurations for \XXX times, report the average results.
    \item Designated failure domain patterns for individual protocols. The failure domains are decided deterministically without feeding the runtime behavior of the protocol.
    \item A fully adversarial failure domain pattern simulating the presence of targeted attacks.
\end{itemize}
We show that all previous works have significant probabilities to lost data even with fully random failure domains.
Most data are lost with designated failure domains, and they always lost all data in the case of adversarial attacks.

With all the analysis presented, it is clear that in order to build fault tolerate storage system, we need to distribute fragments into different failure domains without knowing the failure domains.
To this seemingly impossible challenge, our proposed solution is random sampling.
According to the law of large numbers, when the sampling count is going larger, the number of fragments distributed into each failure domain will be proportion to the size of the failure domain with smaller variance.
By deploying large code that generates enough number of fragments, we are able to guarantee that there will be sufficient failure domains that at least one fragment is distributed into them with high probabilities.
Thus tolerate as many correlated failures as desired.

In this work, we propose a new decentralized storage system, \sys, to address this durability challenge.
At the core of our approach is two durability principles we identified for decentralized storage, namely \emph{information asymmetry} and \emph{data uniformity}.
The information asymmetry principle states that, in the presence of targeted adversarial attacks, data durability can only be guaranteed if some metadata information is asymmetrical in the system.
The intuition behind the principle is that if adversaries have equal and complete view of storage metadata, they can concentrate attack powers on specific nodes to break durability of certain objects.
The data uniformity principle says that to maximize durability, encoding of all stored objects should be distributed uniformly random across storage nodes.
The principle hinges on the unpredictability of churning and adversarial behaviors in an open, decentralized system.

Following the information asymmetry principle, \sys uses a \emph{rateless erasure code} to generate a virtual stream of encoding chunks for each object.
To create asymmetry, a client uses its \emph{private key} to materialize the infinite stream into a finite set of randomly selected chunks.
Critically, the mapping between the materialized chunks and the original object is \emph{opaque} to all participants except the client.
With sufficient objects stored in the system, adversaries have negligible probability to attack enough materialized chunks of the same object to compromise durability.

This opaque object-to-chunk mapping, unfortunately, also precludes object repair.
To ensure long-term durability of the object, \sys applies erasure coding a second time for each encoding chunk with only public information.
Here \sys chooses to use rateless code again: Compared to conventional maximum distance separable code (MDS), rateless code offers better fault tolerance properties in a highly asynchronous network and faulty environment.
Rateless code support efficient \emph{large code} encoding.
The large number of code symbols improves statistical reliability of the chunk without increasing redundancy.
More importantly, it eschews the need for time-sensitive encoding repair --- an impractical requirement in a decentralized network --- and permits repair at a steady average-rate.
The bigger symbol space also facilitates nodes to perform repair \emph{independently}, avoiding costly coordination.

To comply with the data uniformity principle, \sys applies \emph{verifiable randomness} to select randomly distributed nodes to store code symbols.
The procedure avoids centralization by using verifiable random function~\cite{vrf} to determine participant eligibility.
Selection results are unforgeable and publicly verifiable.
Randomness and verifiability of the selection outcome ensures that sufficient code symbols are stored on non-faulty nodes, even when significant portion of the participants are adversarial.
