\section{Evaluation}
\label{sec:eval}

In this section, we evaluate \sys to answer the following questions:
\begin{itemize}
    \item Can \sys achieve practical latency? Can \sys fully utilize network bandwidth when storing objects?
    \item Can \sys evenly distribute blocks among the storage nodes? Does \sys maintain bounded redundancy under different system conditions?
    \item Can \sys perform efficient repair without overwhelming storage nodes?
\end{itemize}

We run experiments on a world-wide \sys deployment to understand performance characteristics of \sys;
we also use simulation to explore long-term behavior and resource usage of \sys.
In both evaluations, we compare \sys to two other storage systems: a full replication baseline and a DHT-based decentralized storage system.
We construct a hierarchical transmission mesh for the replicated storage to mitigate its bottlenecks in the \fn{Put} operations:
objects are first sent to \emph{regional primaries}, who are responsible for disseminating the object to local storage nodes.

The DHT storage system is inspired by prior decentralized storage systems~\cite{glacier,carbonite,irisstore,past}.
The system stores each data block on a randomly-selected, fixed-sized placement group.
Prior works use various selection strategies, such as neighbor nodes or equally-distanced nodes on the DHT ring.
Nevertheless, they all involve a DHT walking with $O(log(N))$ message complexity.
In our evaluation, we perform an ideal selection with $O(1)$ message complexity that selects the successor nodes locally from the client nodes.
This selection method serves as a (rather loose) theoretical limit for any DHT performance, and allow us to focus on the performance of data dissemination and aggregation.

If not stated otherwise, we use the following default parameters.
The system size $N$ is $10000$;
at most $f = N/3$ of them are faulty.
We deploy a rateless erasure code with 1~GB block size, $k = 2^{15}$, and a target redundancy of 3.05x, \ie, each data chunk is 32 KB and each storage node stores 10 fragments for each object.
All objects have the size of a single block (1~GB).
For the full replication baseline, we reduce $N$ to 100 due to its poor scalability.
For DHT storage, we fix the placement group size to 100, and deploy the same erasure code as \sys but with $k = 32$;
as such, one fragment per storage node can tolerate $1/3$ faulty nodes in each placement group.
The DHT storage also uses 1 GB block size, but the chunk size is 32 MB.
As shown in \autoref{sec:background:loss}, this provides weaker durability guarantee than \sys, since $N/3$ faulty nodes can dominate a single placement group.

\subsection{Worldwide Deployment Benchmarks}

We first evaluate the performance characteristics of \sys using our reference implementation written in 4359 lines of Rust code.
We implement a \sys storage node using a pair of foreground HTTP server and two background workers: one for disseminating gossip messages, and the other for handling gossip messages.
This design decouples server behaviors and client-side requests, and avoids cascading synchronous blocking.

\paragraph{Operation latency.}
We measured the latency of all systems using 10000 storage nodes deployed on 100 AWS EC2 instances across five regions (ap-east-1, us-west-1, eu-central-1, sa-east-1, af-south-1).
Each instance has 16 vCPUs, 128~GB memory, 500~GB gp3 storage and up to 12.5Gbps bandwidth.

We measured the latency of \fn{Put} and \fn{Get} operations with three settings: the operation is invoked directly by a storage node; the operation is requested by a separate client either in the same region or a remote region.
In all settings, we perform a \fn{Put} operation with an object filled with random bytes, waits for the object to reach all the nodes, then \fn{Get} the object and compare the checksum.

\begin{figure}
    \centering
    \hspace{-8pt}\includegraphics[width=0.76\columnwidth]{graphs/d_latency}
    \includegraphics[width=0.74\columnwidth]{graphs/d_scale}
    \caption{Latency of \fn{Put} and \fn{Get} operations in a world-wide deployment: (top) fixed 10K nodes with three settings (bottom) increasing system sizes}
    \label{fig:deploy-latency}
\end{figure}

As shown in \autoref{fig:deploy-latency}, \sys achieve 32.9s and 12.1s average latencies on direct \fn{Put} and \fn{Get}.
It is slower than DHT storage (19.4s and 6.7s) for two reasons:
a) \sys has a significantly larger $k$ parameter, resulting in a 2.77x higher redundancy than DHT storage.
This leads to longer data dissemination latency.
b) \sys disseminates smaller but more fragments than DHT storage.
The dissemination scope is also wider, \ie, to all the 10K nodes compared to only 100 nodes in a placement group.
As such, the dissemination of \sys is less efficient.
However, both systems are significantly faster than the fully replicated baseline in \fn{Put} operation, which takes 88.8s on average.
The replication baseline completes the \fn{Get} operation instantly under the direct setting, since a full copy is always available on the node.

When a separate client requests from a local region, a small latency penalty (3-5s) is added to all the systems.
A significant slowdown is observed when the client is in a remote region.
While the replication system is still much slower in \fn{Put} operation (154.6s compared to 94.2/95.2s of \sys/DHT storage), its \fn{Get} is almost the same as the other two systems: all of them are around 72-73s.

\paragraph{Scalability.}
Next, we measure the latency of direct \fn{Put} and \fn{Get} with increasing system sizes.
We skip the replication baseline, since it fail to scale beyond 100 nodes.
The result is shown in \autoref{fig:deploy-latency}.

% \begin{figure}
%     \centering
%     \caption{Latency of \fn{Put} and \fn{Get} operations with increasing system sizes}
%     \label{fig:deploy-scale}
% \end{figure}

Both systems show good scalability.
DHT storage always disseminates to and aggregates from 100 nodes, so its performance is stable regardless of system sizes.
Each \sys operation contacts all the nodes, and its performance slightly improves as system scales up.
The \fn{Put} latency decreases from 41.2s to 32.9s, while the \fn{Get} operation latency decrease from 15.3s to 12.2s.
This shows \sys performance does not degrade with more nodes.

As the system scales, the number of fragments stored on each node decreases (from 20 to 10).
Because each fragment is transmitted in a dedicated HTTP request, the fewer fragments result in fewer communication rounds, improving the latency particularly for cross region traffic.

\paragraph{Write throughput.}
Beside latency, we also measured \fn{Put} throughput of \sys and DHT storage.
The benchmark gradually increased the number of concurrent \fn{Put} operations.
Throughput is calculated as the total size of the objects that have been \fn{Put} divided by the total time of the operations.
We spawn all 100 EC2 instances in the ap-east-1 region to avoid the high data transfer cost.
To get realistic results with cross-region bandwidth constrains, we limit the ingress bandwidth of each storage node to 10Mbps in our implementation.

\begin{figure}
    \centering
    \includegraphics[width=0.7\columnwidth]{graphs/d_tput}
    \caption{Comparing the \fn{Put} throughput of \sys and DHT storage with increasing client workloads}
    \label{fig:deploy-tput}
\end{figure}

As shown in \autoref{fig:deploy-tput}, \sys sustains a stable write throughput of around 238~MB/s.
Since each storage node uniformly involves in every \fn{Put} operation, \sys fully utilizes the available bandwidth of the whole system at any concurrency level.
DHT storage, however, performs worse than \sys at lower load, as only the bandwidth of the nodes selected by the placement groups are utilized.
As the concurrency increases, the throughput of DHT storage increases and surpasses \sys thanks to its lower redundancy.
However, its throughput is not as stable as \sys: random placement group selection results in load imbalance on different nodes.
As we show later in simulations, this issue cannot be addressed by storing more objects, as the variance of the load increases when more data are stored.

\subsection{Simulation}

We also conduct simulations to evaluate the long-term behaviors of the systems.
All the simulations are performed for $10^7$ steps if not stated otherwise.
The system is initialized with 1000 random objects stored by 10K storage nodes, with a 0.01 node/step joining and leaving rate.
No \fn{Put} operation is invoked after initialization.

\paragraph{Redundancy in dynamic systems.}
Next, we study how \sys adjusts its redundancy against dynamic system scales.
In the first $10^7$ steps the number of nodes grows from 10K to 100K, and then the simulation continues for $2 \dot 10^6$ steps without further scaling.
This simulation is performed with 100 objects.
We studied three settings in this simulation.
In ``one-shot'', every node estimates $N$ only once when it joins the system.
For the other two settings, the nodes periodically estimate $N$, with $10^4$ and $10^6$ steps interval respectively.
The former provides near-perfect responsiveness to the changing system scales, while the latter one is more realistic.

As shown in \autoref{fig:simulate-scale}, even in the one-shot setting, the increase in redundancy gradually slows down.
The newly-joined nodes are initialized with the proper redundancy, while old nodes who store unnecessary redundancy gradually leave the system.
When the system stops growing, the redundancy growth drops, and eventually drops to the expected level.

Under the ideal setting, all the nodes reduce their redundancy after $N$ estimation, resulting in significant redundancy drop in short intervals.
Due to rounding errors, the redundancy curve shows a sawtooth wave, but is still much lower than the one-shot setting.
Finally, when performing $N$ less frequently, the system reacts slower than the ideal setting, but eventually matches its redundancy level.

\paragraph{Repair overhead.}
In the following simulation we track the egress traffic of individual nodes for assisting repair during failures.
The graph \autoref{fig:simulate-repair} shows the average traffic of different system scales, in the unit of block size.

\begin{figure}
    \centering
    \includegraphics[width=0.7\columnwidth]{graphs/s_repair}
    \caption{Average node repair traffic}
    \label{fig:simulate-repair}
\end{figure}

In both systems every node only need to transfer few block size amount of repair data during its lifetime, and the overhead decreases as the number of nodes increases.
The repair overhead of \sys is smaller than DHT-based storage thanks to the flattened view fragments (\autoref{sec:optz}).
In \sys only chunks that directly required by the remote node need to be transferred, and no reconstruct is necessary.
The larger $k$ results in smaller chunk size, which leads to better repair traffic efficiency.

\paragraph{Redundancy over time.}
In the last simulation we check for the safety guarantee of \sys.
Unlike the other two systems that eagerly detect and repair for failures and maintain a near-constant redundancy level, \sys takes a more lazy approach (\autoref{sec:protocol:reconfig}), results in a more fluctuated redundancy.
In this simulation, we collect the \emph{logical redundancy} data, \ie the number of available fragments divided by $k$, instead of the \emph{physical redundancy} showing in the above simulations.

The results are shown in \autoref{fig:simulate-logical}.
As the number of nodes increases, the fluctuation of redundancy decreases.
But the redundancy is never going below 3x \ie the system never violates durability guarantee in the presence of $N/3$ faulty nodes.

\autoref{fig:op} shows the overhead of \code compares to LT code.
Both code uses $k = 2^{15}$ and 1GB block size.
The benchmark generates a block filled with random bytes (where \code additionally initialize the Merkle tree), then repeat encode-decode cycle until the block is reconstructed.
For \code the encoded fragment is verified before decoded.
The accumulated time spent on each kind of operation is then reported.

As shown in the graph, \code is significantly more efficient than LT code in both encoding (3.30s vs 44.99s) and decoding (0.16s vs 1.24s).
This is because \code eliminate the XOR operations with its flattened view representation, so both encoding and decoding are mostly pure data copying.
As the result, although \code introduces extra initialize (0.74s) and verify (9.19s) operations for self-certifying, the overall overhead is still less than LT code.

\paragraph{Fault tolerance.}
To evaluate how well \sys tolerates adversaries, we simulate a network with Byzantine faulty nodes.
Byzantine nodes participate correctly in all \sys protocols; however, they do not store any encoding fragment.
A data object is consider permanently lost when less than $\kout$ of its encoded chunks are irrecoverable (for \sys) or no replicas are left (for the replicated system).
The \autoref{fig:faulty} shows the percentage of lost objects in a one-year trace.
This simulation validates that a simple replication system does not tolerance strong adversaries: The baseline system loses all of its objects when less than 5\% of the nodes are faulty.
On the other hand, \sys can tolerate a significant fraction of faulty nodes without losing data.
The degree of tolerance depends on the inner code parameters.
Using the default parameter, \sys can tolerate around the targeted 33\% faulty nodes, while a more conservative configuration can improve tolerance further at the expense of increased redundancy.

\subsection{Discussion}

\lijl{We can include this discussion in the submission if there is space.}

As our evaluation results have shown, \sys incurs higher performance overhead and management complexity compared to centralized deployments and prior best-effort systems.
However, we believe there exists inherent trade-offs between performance and security guarantees (e.g., anti-censorship and strong adversary tolerance).
As we demonstrated earlier (\autoref{sec:intro} and \autoref{sec:background}), these properties are more critical than performance for our target deployment scenarios.

\ifspace
We also note that \sys is not the only decentralized system that pays this price.
Both Bitcoin and Ethereum require around one hour to confirm a transaction.
And it has been proved that the long confirmation time is critical to their safety guarantees in a permissionless setting.
Algorand~\cite{algorand} takes 13 message steps to commit in the presence of adversaries, and relies on randomized peer selection for security.
