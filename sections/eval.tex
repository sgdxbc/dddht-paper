By default k = 64, persistence parameter $k_p = 1.2k$, select rate $K = 2k$
\sgd{This description assumes single-stack nodes.}
In practical we decide to make \store operation returns only when there are $1.6k$ peers start to gossip.
This improves system stability without too much overhead.

\subsection{Simulations}

Perform discrete event simulation on a network with 10K peers. Poisson distributed peer failure according to peers' average AFR.
In simulation each peer periodically gossip until it is selected to fail. Then after gossip timeout, next responsible peers will notice and may choose to start to repair.
We record the repair traffic with data object size as basic unit.
We also record the overall raw capacity occupied. Notice redundancy reduction is not simulated, so the redundancy is more than result from deployed environment.
Every simulation runs 10 times with different seeds and takes the average.

Beside of \sys we also simulate a Ceph-like replicated storage. 
The replicated system replicate every object on 3 random selected peers, and perform repair as soon as possible when one of the peer fails.
This is similar to datacenter-level distributed storage. We use it to check how much overhead we paid for decentralization.

\begin{figure}
    \addgraph{repair}
    \caption{Repair traffic over different number of objects and AFR. The number behind entropy indicate how many repair hits booster peers' cache.}
    \label{fig:repair}
\end{figure}

\textbf{Repair traffic.} We record the total number of repairing in the first year. 
\autoref{fig:repair} shows repair traffic linearly increase according to the data object number.
When booster peers caching data object perfectly, every repairing only transfer $1/k$ unit of data object, and the overall traffic is comparable to replicated system.
However when cache hit rate decrease, the traffic increases hugely because each cache missing cause almost one whole extra object size to be transffered.
As shown in the graph, repair traffic increases mostly when cache hit rate dropping from 100\% to 75\%, which is a 16.6x increasing.
After that, repair traffic only get doubled for 75\% to 50\%, and roughly doubled again with 0\% cache hit.
Certain incentive should be provided to booster peers to encourage them to cache for a longer time and reduce repair traffic.
Luckily as shown later, most repairing happens in a relatively short interval, so that booster peers do not need to cache long and may still achieve good overall cache hit rate.

\autoref{fig:repair} shows repair traffic with various AFR in the first year.
Repair traffic also grow linearly according to AFR both in \sys and replicated system.
This shows \sys has good responsiveness to the change of system's average AFR.
And it also scales well respect to the increase of AFR, i.e., the overhead per peer failure keep constant.

\sys has less redundancy in most of the time, and the only short intervals with large redundancy can be further shorten by aggressively redundancy reducing introduced in \autoref{sec:implementation}.
Although \sys deploy lazy repairing, comparing to 10 year simulation time, the repairing delay is still short enough that looks straight up.
\autoref{fig:time} shows accumulated repair traffic in 10 years.
The number of steps for \sys is less than replicated, which is a strong evidence that \sys do repair more lazy than replicated and require less synchronous network.

\subsection{World-wide deployment}

\sgd{Add this explanation to somewhere if necessary.}
Every peer is limited to single thread because of limited number of machines.
This results in sequentially generation of all fragments.
In practice, it could be parallelized and improve \store performance.

Deploy on AWS, in 5 zones (us-west, ap-southeast, eu-central, sa-east, af-south).
c5a.24xlarge machines with 96 vCPU and 192GiB memory, 25GBps bandwidth.

Besides implementation of our \sys protocol, we also implemented a Kademlia p2p network which perform typical DHT operations on \store and \query.
We use that to compare \sys's operation overhead with exist decentralized storage system.
We also deployed a Ceph cluster with one replicated pool and one erasure coding pool, all with stocking configuration, to compare with a typical distributed storage system.

Performance evaluation. For every run, a fresh operating peer is spawned. After it connects into network stably, it \store a randomly generated object and get its id.
Then another fresh peer is spawned to use the id to \query the object back. It performs sanity check to make sure the object is identical.

Kademlia implementation. Kademlia does not include object-hosting. So we make a minimal extension to Kademlia, by pushing object to a random peer in the network.
The peer then claims to be provider of the object through DHT. After the claim is done, it responds operating peer with id.
Notice that erasure coding cannot be easily adapted into Kademlia, which causes the implementation quite limited.

\begin{figure}
    \addgraph{latency}
    \caption{Latency of \store and \query operation in a world-wide deployment. Entropy and Kademlia operate with 64MiB data objects while Entropy-1GB operate with 1GiB data objects.
    EntropyL-1GiB is a variant that finalize \store when received $k_p$ gossip messages.}
    \label{fig:latency}
\end{figure}

\autoref{fig:latency} show average latency of \store and \query operations. With 64MiB data objects, \sys outperform both the other systems a lot.
\sys is significantly more stable in terms of latency distribution compare to Kademlia, because fragments are uniformly distributed across all peers,
while in Kademlia the object is sequentially transmitted to one remote peer, and the latency is highly affected by the link between the two peers.

As a result, we are able to increase data object size to 1GiB while latency is only doubled.
At the same time Kademlia may take ~120s to finish one operation because of sequentially transmission.
We also measure a variant with slightly reduced $k_{put} = 1.2k$ which tolerance less faulty peers on \store operations.
The result is quite close to Kademlia, while Kademlia is limited with 64MiB data objects.

\textbf{Latency breakdown.} Compare to Kademlia, \sys perform less sequential steps of peer communication, but has an extra encoding/decoding workload.
However thanks to highly-optimized fountain code library, the erasure coding's latency overhead is surprisingly small: for 1GiB object, it takes only 4.2s from receiving the pull request from first responsible peer to send out all $k_p$ encoded fragments.
More than half of the interval is waiting on gossip spreading rather than generating fragment.
The fragment decoding latency is negligible, and after peer collects enough fragments to recover, the object recovery only takes 1.2s.
As a comparison, computing SHA256 hash for the 1GiB object takes 4.7s.
Actually, computing SHA256 hash is the major increasing overhead when switching from 64MiB objects to 1GiB.
The good support provided by the library not only make operations blazing fast, but also makes it feasible to regularly recover tons of whole objects among the peers without worrying about performance overhead.
