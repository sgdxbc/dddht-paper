We use two types of experiments to evaluate \sys: discrete event simulation and physical deployment on geo-distributed EC2 virtual machines.
Unless otherwise specified, we use $k = 64$ for the rateless erasure code in \sys, and a persistence parameter $k_p$ of $1.2k$.
The total number of nodes selected in each epoch, $K$, is set to $2k$.
%By default k = 64, persistence parameter $k_p = 1.2k$, select rate $K = 2k$
%\sgd{This description assumes single-stack nodes.}
In our physical deployment, \store operations return only when $1.6k$ persistence proofs are received through gossip.
This safeguard policy improves system stability without introducing significant overhead.

When evaluating physical deployments, we compare \sys to two other systems.
Firstly, an IPFS-like decentralized storage system that uses Kademlia DHT to store publisher record.
We only slightly modified IPFS in the following way: When storing an object, we transfer the object to a random peer instead of storing locally.
Note that IPFS (and our modified version) by default only stores a single copy of the object, therefore offering no durability guarantee.
Second, we also evaluate against the Ceph~\cite{ceph} distributed storage system.

\subsection{Simulations}

We first use discrete event simulation to evaluate the repair overhead and fault tolerance guarantees of \sys.
We simulate a network of 10K nodes.
For simplicity, we parametrize one annualized failure rate (AFR) for all nodes.
Node failures follow a Poisson distribution according to the AFR.
Each node periodically gossips until it fails.
%Then after gossip timeout, next responsible peers will notice and may choose to start to repair.
We use data object size as the basic unit for repair traffic.
The overall storage capacity which \sys occupied is also recorded.
%Notice redundancy reduction is not simulated, so the redundancy is more than result from deployed environment.
We run each simulation 10 times with different seed values and take the average.

Besides \sys, we also simulate a Ceph-like replicated storage.
This system replicates each object on 3 randomly selected peers, and performs repair immediately after one of the replicas fails.
%This is similar to datacenter-level distributed storage.
Such replication scheme is commonly employed in data center settings, and we use it as a baseline to compare to our decentralized scheme.

    \caption{Repair traffic over different number of objects and AFR. The number behind entropy indicate how many repair hits booster peers' cache.}
    \label{fig:repair}

\textbf{Repair traffic.}
We first simulate how much encoding repair traffic \sys generates, and compare it to the baseline replication approach.
We record the total number of repairing in the first year.
\autoref{fig:repair} shows the total repair traffic (in units of data object sizes) in the first year.
The different lines of \sys indicate the percentage of nodes that regenerate encoding fragment using the booster optimization (\autoref{sec:protocol:optimization}).
Repair traffic for \sys increases linearly with the total number of data objects.
When booster peers cache object perfectly, every repair only transfers $1/k$ of data object size, so the overall repair traffic is comparable to the replicated system.
However, when booster hit rate decreases, there is a sudden jump in the repair traffic due to the high ``cache miss'' penalty.
Concretely, repair traffic increases by 16.6x hit rate drops from 100\% to 75\%.
Beyond that, repair traffic only doubled from 75\% hit rate to 50\%, and doubled again when the booster optimization is turned off.
This demonstrates that our booster optimization is effective.
As such, incentives should be provided to encourage booster nodes to cache for a longer time to reduce repair traffic.
Fortunately, as shown later, most repairs finish quickly, so a short caching period can lead to good overall cache hit rate.

\autoref{fig:repair} shows total repair traffic in the first year with increasing AFR.
In both \sys and the replicated system, repair traffic grows linearly with AFR.
This demonstrates that \sys responds well to the change of the system's average AFR.
Another implication is that \sys scales well with an increase in AFT, i.e., the overhead per node failure remains constant.

Every peer is limited to single thread because of limited number of machines.
This results in sequentially generation of all fragments.
In practice, it could be parallelized and improve \store performance.

Deploy on AWS, in 5 zones (us-west, ap-southeast, eu-central, sa-east, af-south).
c5a.24xlarge machines with 96 vCPU and 192GiB memory, 25GBps bandwidth.

Besides implementation of our \sys protocol, we also implemented a Kademlia p2p network which perform typical DHT operations on \store and \query.
We use that to compare \sys's operation overhead with exist decentralized storage system.
We also deployed a Ceph cluster with one replicated pool and one erasure coding pool, all with stocking configuration, to compare with a typical distributed storage system.

Performance evaluation. For every run, a fresh operating peer is spawned. After it connects into network stably, it \store a randomly generated object and get its id.
Then another fresh peer is spawned to use the id to \query the object back. It performs sanity check to make sure the object is identical.

Kademlia implementation. Kademlia does not include object-hosting. So we make a minimal extension to Kademlia, by pushing object to a random peer in the network.
The peer then claims to be provider of the object through DHT. After the claim is done, it responds operating peer with id.
Notice that erasure coding cannot be easily adapted into Kademlia, which causes the implementation quite limited.

\begin{figure}

    \caption{Latency of \store and \query operation in a world-wide deployment. Entropy, Ceph and Kademlia operate with 64MiB data objects while Entropy-1GB operate with 1GiB data objects.
    EntropyL-1GiB is a variant that finalize \store when received $k_p$ gossip messages.

\autoref{fig:latency} show average latency of \store and \query operations. With 64MiB data objects, \sys outperform both the other systems a lot.
\sys is significantly more stable in terms of latency distribution compare to Kademlia, because fragments are uniformly distributed across all peers,
while in Kademlia the object is sequentially transmitted to one remote peer, and the latency is highly affected by the link between the two peers.

As a result, we are able to increase data object size to 1GiB while latency is only doubled.
At the same time Kademlia may take ~120s to finish one operation because of sequentially transmission.
We also measure a variant with slightly reduced $k_{put} = 1.2k$ which tolerance less faulty peers on \store operations.
The result is quite close to Kademlia, while Kademlia is limited with 64MiB data objects.

\textbf{Latency breakdown.} Compare to Kademlia, \sys perform less sequential steps of peer communication, but has an extra encoding/decoding workload.
However thanks to highly-optimized fountain code library, the erasure coding's latency overhead is surprisingly small: for 1GiB object, it takes only 4.2s from receiving the pull request from first responsible peer to send out all $k_p$ encoded fragments.
More than half of the interval is waiting on gossip spreading rather than generating fragment.
The fragment decoding latency is negligible, and after peer collects enough fragments to recover, the object recovery only takes 1.2s.
As a comparison, computing SHA256 hash for the 1GiB object takes 4.7s.
Actually, computing SHA256 hash is the major increasing overhead when switching from 64MiB objects to 1GiB.
The good support provided by the library not only make operations blazing fast, but also makes it feasible to regularly recover tons of whole objects among the peers without worrying about performance overhead.
