\section{Evaluation}
\label{sec:eval}

In this section we explore various aspects of \sys including performance, storage capacity and scalability.
To answer the following questions:
\begin{itemize}
    \item Can \sys achieve practical latency? Can \sys fully utilize bandwidth resource into write throughput?
    \item Can \sys evenly distribute blocks among the storage nodes? Can \sys maintain bounded redundancy in long term under various system conditions?
    \item Can \sys efficiently repair for failures without overwhelming storage nodes?
\end{itemize}
We perform evaluations with both deployed system and simulation.

In both kind of evaluations, we compare \sys with two other storage systems: a fully replicated baseline and a DHT-based decentralized storage network.
We construct a basic hierarchical transmission mesh for the full replication storage to mitigate its single-point bottleneck in \fn{Put} operations.
In \fn{Put} operations the data block is sent to several \emph{regional primaries}, who are responsible for relaying the block to local storage nodes.

The DHT-based storage network is inspired by various previous decentralized storage networks \sgd{cite}.
In this network, each data block is stored on a randomly-selected fixed-size placement group.
The selection strategy varies in previous works, such as successive nodes or equally-distanced nodes on the ring network and closest XOR distance.
\sgd{cite}
However, all of them go through a $O(log(N))$ message complexity DHT walking procedure.
In our evaluation, we simulate the selection with a $O(1)$ procedure that selects the successive nodes locally from the \fn{Put} or \fn{Get} client nodes.
This simulated selection can serve as a (rather loose) theoretical limit of various kinds of DHT walking performance, and allow us to focus on the performance of data dissemination and aggregation within placement groups.

Without further statement our evaluation are performed with the following parameters:
the number of nodes $N = 10000$, and assuming at most $f = N/3$ of them are faulty.
As discussed in \autoref{sec:optz}, we deploy a rateless erasure code with 1GB block size, $k = 2^{15}$ and the nodes target a redundancy of 3.05x \ie each chunk (or fragment of degree 1) is 32KB size and each storage node stores 10 fragments for each block.
For full replication baseline we reduce $N$ to 100 for its poor scalability.
For DHT-based storage system, we fix placement group size to 100, and deploy the same erasure code of \sys but with $k = 32$, so that when each node stores one fragment for each block the system is able to tolerate $1/3$ faulty nodes in each placement group.
Notice that this is a weaker guarantee than the one provided by \sys, since $N/3$ faulty nodes can dominate a single placement group \ie results in more than $1/3$ faulty nodes in the group.
Consequentially, the DHT-based system also uses 1GB block size, but the chunk size is 32MB.

\subsection{Worldwide Deployed Benchmarks}

We measure the performance characteristics of \sys with our reference implementation written with 4359 lines of Rust code.
We implement a \sys storage node as a pair of foreground HTTP server and two background event loops: one for disseminating gossip messages, and the other for reacting the gossip messages.
This design decouples server-like behaviors with client-side requests which are all performed by the event loops, and avoids cascading synchronous blocking.

\paragraph{Operation latency.}
We measured the latency of \sys and compared systems with 10000 storage nodes deployed on 100 AWS EC2 instances across five regions (ap-east-1, us-west-1, eu-central-1, sa-east-1, af-south-1).
Each instance has 16 vCPUs, 128GB memory, 500GB gp3 storage and up to 12.5Gbps bandwidth.

We measured the latency of \fn{Put} and \fn{Get} operations with three settings: the operation is initiated directly by a storage node, the operation is requested by a client to a storage node that is geologically locally or remotely located.
The benchmark first perform a \fn{Put} operation on a randomly-selected node with a block filled with random bytes, then wait for the block reaches all the storing nodes, then \fn{Get} the block back and compare the checksum.
In the second settings the two random nodes are constraint to be in the same region of the client, while in the third setting they are constraint to be in regions different from the client.
The results are shown in \autoref{fig:deploy-latency}.

\begin{figure}
    \centering
    \includegraphics[width=0.8\columnwidth]{graphs/d_latency}
    \caption{Latency of \fn{Put} and \fn{Get} operations}
    \label{fig:deploy-latency}
\end{figure}

\sys achieve 32.9s and 12.1s average latencies on direct \fn{Put} and \fn{Get}.
It is slower than DHT-based storage (19.4s and 6.7s), because of two reasons:
\begin{itemize}
    \item The $k$ code parameter of \sys is significantly larger than the one of DHT-based storage, which results in 2.77x more redundancy than the DHT-based storage system.
    The more bytes for dissemination results in longer latency.
    \item The fragments disseminated by \sys is more and smaller than the DHT-based storage, and the dissemination scope is much wider \ie to all of the 10K nodes compared to only 100 nodes of the placement group.
    So the dissemination of \sys is less efficient.
\end{itemize}
However, both of the systems are significantly faster than the fully replicated baseline in \fn{Put} operation, which takes 88.8s on average.
At the other hand, the \fn{Get} operation is instantly finished in a fully replicated system under direct setting, since every storage node keeps a full copy of the original block that is ready for fulfilling the operation at any time.

When client requests from a local storage node, a small latency penalty (3-5s) is added to all the system.
When the request is from remote region, a significant slowdown is observed.
While fully replicated baseline is still much slower in \fn{Put} operation (154.6s compared to 94.2/95.2s of \sys/DHT-based storage), its \fn{Get} is almost the same as the other two systems: all of them are around 72-73s.

\paragraph{Scalability.}
Next we measure the direct \fn{Put} and \fn{Get} with various numbers of nodes ranging from 4000 to 10000 for \sys and DHT-based storage.
Fully replicated baseline is not benchmarked because it can hardly go over 100 nodes.
The result is shown in \autoref{fig:deploy-scale}.

\begin{figure}
    \centering
    \includegraphics[width=0.8\columnwidth]{graphs/d_scale}
    \caption{Latency of \fn{Put} and \fn{Get} operations with different numbers of nodes}
    \label{fig:deploy-scale}
\end{figure}

Both systems show desirable scalability.
The DHT-based storage always disseminates to and aggregates from 100 nodes, so its performance is expected to maintain constant.
\sys on the other hand performs the operations system-wide, and the performance slightly improves as system scales up.
The \fn{Put} operation latency decreases from 41.2s to 32.9s, while the \fn{Get} operation latency decrease from 15.3s to 12.2s.
This shows \sys performance does not degrade with more nodes.

The reason \sys performs better with more nodes is that when there are more nodes, the number of fragments stored by each node is less (\ie from 20 decreases to 10).
Because each fragment is transmitted in a dedicated HTTP request, the fewer fragments result in fewer communication rounds, which helps to improve the latency especially in such a worldwide deployment scenario.

\paragraph{Write throughput.}
Beside latency, we also measured write throughput of \sys and DHT-based storage.
The benchmark is conducted by performing a certain number of \fn{Put} operations and measure the total time for all the operations to finish.
The write throughput is calculated as the total size of blocks that have been \fn{Put} divided by the total time of the operations.
The benchmark is performed with different number of concurrent operations.
For example, when concurrency is 100, at any time there are 100 ongoing \fn{Put} operations.

In this benchmark we spawn all 100 EC2 instances in the ap-east-1 region, to avoid high data transfer cost.
To cancel the effect of unrealistic high bandwidth brought by AWS's datacenter network, we limit the ingress bandwidth of each storage node to 10Mbps in our implementation.

\begin{figure}
    \centering
    \includegraphics[width=0.8\columnwidth]{graphs/d_tput}
    \caption{Write throughput}
    \label{fig:deploy-tput}
\end{figure}

The result is shown in \autoref{fig:deploy-tput}.
This benchmark shows \sys can sustain a stable write throughput of around 238MB/s.
Because every storage node uniformly take part in every \fn{Put} operation, \sys fully utilize the available bandwidth resource of the whole system at any concurrency level.
On the other hand, the DHT-based storage performs worse than \sys with small concurrency, as only part of the nodes (\ie the ones that have been selected by the placement groups) can take part in the operations, and the bandwidth of other nodes are wasted.
As the concurrency increases, the throughput of DHT-based storage increases and surpasses \sys thanks to its smaller redundancy.
However, its throughput is not as stable as \sys: the system bottlenecks on the nodes that is selected by the most number of placement groups.
As we can see in the later simulation, this issue cannot be addressed by storing more blocks with more concurrency, as the variance of storage node load goes up when there are more data to store.

\subsection{Simulation}

While the deployed evaluations verifies the practical performance of \sys, we additionally simulate \sys and the DHT-based storage for insights of long-term behaviors of the systems.
Without further clarification all the simulations are performed for $10^7$ steps.
The system is initialized with 1000 random data blocks stored by the 10K storage nodes, with a 0.01 node/step joining and leaving rate.
There is no \fn{Put} operation happened during the simulation.

\paragraph{Node load uniformity.}
We collect the \emph{load} of the nodes when they leave the system, in the unit of block size.
The CDF of loads of both systems are shown in \autoref{fig:simulate-load}.

\begin{figure}
    \includegraphics[width=0.4\columnwidth]{graphs/s_pdf_entropy}
    \includegraphics[width=0.4\columnwidth]{graphs/s_pdf_dht}
    \caption{Node storage load CDF of \sys (left) and DHT-based storage (right)}
    \label{fig:simulate-load}
\end{figure}

In this simulation \sys shows better uniformity.
Every node in the system is utilized, and most of the nodes have similar load.
On the other hand, the CDF graph of DHT-based storage shows steps, each of which corresponds to a set of nodes that are selected by a certain number of placement groups.
The lines all starts from 0, means there are always nodes that are not selected and utilized by any group.
Also, as the number of data grows, the load of top-utilized nodes grows dramatically.
Eventually the system load is unevenly distributed to the nodes.

\paragraph{Redundancy of stable system.}
In the following simulations, we collect system statistics every $10^5$ steps.
We first study the redundancy of the constantly-scale systems with different number of nodes.
The graph \autoref{fig:simulate-scale} shows the average redundancy of different systems.

\begin{figure}
    \centering
    \includegraphics[width=0.8\columnwidth]{graphs/s_scale_static}
    \caption{Redundancy of various numbers of nodes}
    \label{fig:simulate-scale}
\end{figure}

Both \sys and DHT-based storage shows perfect scalability, while \sys has a higher redundancy because of the larger $k$ parameter.
On the other hand, the fully replicated baseline has unbounded redundancy.

\paragraph{Redundancy adjustment for scaling up.}
Then we study how well \sys can adjust redundancy against growing system scale.
In the first $10^7$ steps the number of nodes grows from 10K to 100K, and then the simulation continues for $2 \dot 10^6$ steps without system growing.
This simulation is performed with 100 data blocks.

We studied three settings in this simulation.
The ``oneshot'' setting demonstrate the baseline: every node only estimate $N$ once upon joining the system and initialize its storage accordingly.
Then it never reacts to the changing $N$.
In the other two settings the nodes periodically perform estimation of $N$, with $10^4$ and $10^6$ steps interval respectively.
The former one corresponds to the ideal near-perfect responsiveness to the changing system scale, while the latter one is more realistic.

\begin{figure}
    \centering
    \includegraphics[width=0.8\columnwidth]{graphs/s_scale}
    \caption{Redundancy of \sys during system scaling up}
    \label{fig:simulate-scale-up}
\end{figure}

As shown in \autoref{fig:simulate-scale-up} the simulation results have a few takeaways.
First, even in the baseline, the redundancy increases slower and slower because the newly-joining nodes are initialized with proper redundancy level, while the old nodes that persists unnecessary redundancy gradually leave the system.
When the system stops growing the redundancy immediately drops, and it will eventually get back to expected level.

Then, under the ideal setting we can clearly observe the effect of actively redundancy adjustment.
In this case all the nodes reduce their redundancy almost at the same time, results in the significant drop in short intervals.
Because of the rounding error the redundancy cannot drop back to the exact same level as initial, but it is still much less than the baseline.

And finally, the realistic setting sits in between the other two settings.
It reacts slower than the ideal setting, but it eventually matches the ideal case.

\paragraph{Repair overhead.}
In the following simulation we track the egress traffic of individual nodes for assisting repair during failures.
The graph \autoref{fig:simulate-repair} shows the average traffic of different system scales, in the unit of block size.

\begin{figure}
    \centering
    \includegraphics[width=0.8\columnwidth]{graphs/s_repair}
    \caption{Average node repair traffic}
    \label{fig:simulate-repair}
\end{figure}

In both systems every node only need to transfer few block size amount of repair data during its lifetime, and the overhead decreases as the number of nodes increases.
The repair overhead of \sys is smaller than DHT-based storage thanks to the flattened view fragments (\autoref{sec:optz}).
In \sys only chunks that directly required by the remote node need to be transferred, and no reconstruct is necessary.
The larger $k$ results in smaller chunk size, which leads to better repair traffic efficiency.

\paragraph{Redundancy over time.}
In the last simulation we check for the safety guarantee of \sys.
Unlike the other two systems that eagerly detect and repair for failures and maintain a near-constant redundancy level, \sys takes a more lazy approach (\autoref{sec:protocol:reconfig}), results in a more fluctuated redundancy.
In this simulation, we collect the \emph{logical redundancy} data, \ie the number of available fragments divided by $k$, instead of the \emph{physical redundancy} showing in the above simulations.

\begin{figure}
    \centering
    \includegraphics[width=0.8\columnwidth]{graphs/s_logical}
    \caption{Logical redundancy of \sys}
    \label{fig:simulate-logical}
\end{figure}

The results are shown in \autoref{fig:simulate-logical}.
As the number of nodes increases, the fluctuation of redundancy decreases.
But the redundancy is never going below 3x \ie the system never violates durability guarantee in the presence of $N/3$ faulty nodes.

\paragraph{Fault tolerance.}
To evaluate how well \sys tolerates adversaries, we simulate a network with Byzantine faulty nodes.
Byzantine nodes participate correctly in all \sys protocols; however, they do not store any encoding fragment.
A data object is consider permanently lost when less than $\kout$ of its encoded chunks are irrecoverable (for \sys) or no replicas are left (for the replicated system).
The \autoref{fig:faulty} shows the percentage of lost objects in a one-year trace.
This simulation validates that a simple replication system does not tolerance strong adversaries: The baseline system loses all of its objects when less than 5\% of the nodes are faulty.
On the other hand, \sys can tolerate a significant fraction of faulty nodes without losing data.
The degree of tolerance depends on the inner code parameters.
Using the default parameter, \sys can tolerate around the targeted 33\% faulty nodes, while a more conservative configuration can improve tolerance further at the expense of increased redundancy.

\subsection{Discussion}

\lijl{We can include this discussion in the submission if there is space.}

As our evaluation results have shown, \sys incurs higher performance overhead and management complexity compared to centralized deployments and prior best-effort systems.
However, we believe there exists inherent trade-offs between performance and security guarantees (e.g., anti-censorship and strong adversary tolerance).
As we demonstrated earlier (\autoref{sec:intro} and \autoref{sec:background}), these properties are more critical than performance for our target deployment scenarios.

\ifspace
We also note that \sys is not the only decentralized system that pays this price.
Both Bitcoin and Ethereum require around one hour to confirm a transaction.
And it has been proved that the long confirmation time is critical to their safety guarantees in a permissionless setting.
Algorand~\cite{algorand} takes 13 message steps to commit in the presence of adversaries, and relies on randomized peer selection for security.
