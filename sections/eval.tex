We use two types of experiments to evaluate \sys: discrete event simulation and physical deployment on geo-distributed EC2 virtual machines.
Unless otherwise specified, we use $k = 64$ for the rateless erasure code in \sys, and a persistence parameter $k_p$ of $1.2k$.
The total number of nodes selected in each epoch, $K$, is set to $2k$.
%By default k = 64, persistence parameter $k_p = 1.2k$, select rate $K = 2k$
%\sgd{This description assumes single-stack nodes.}
In our physical deployment, \store operations return only when $1.6k$ persistence proofs are received through gossip.
This safeguard policy improves system stability without introducing significant overhead.

When evaluating physical deployments, we compare \sys to two other systems.
Firstly, an IPFS-like decentralized storage system that uses Kademlia DHT to store publisher record.
We only slightly modified IPFS in the following way: When storing an object, we transfer the object to a random peer instead of storing locally.
Note that IPFS (and our modified version) by default only stores a single copy of the object, therefore offering no durability guarantee.
Second, we also evaluate against the Ceph~\cite{ceph} distributed storage system.

\subsection{Simulations}

We first use discrete event simulation to evaluate the repair overhead and fault tolerance guarantees of \sys.
We simulate a network of 10K nodes.
For simplicity, we parametrize one annualized failure rate (AFR) for all nodes.
Node failures follow a Poisson distribution according to the AFR.
Each node periodically gossips until it fails.
%Then after gossip timeout, next responsible peers will notice and may choose to start to repair.
We use data object size as the basic unit for repair traffic.
The overall storage capacity which \sys occupied is also recorded.
%Notice redundancy reduction is not simulated, so the redundancy is more than result from deployed environment.
We run each simulation 10 times with different seed values and take the average.

Besides \sys, we also simulate a Ceph-like replicated storage.
This system replicates each object on 3 randomly selected peers, and performs repair immediately after one of the replicas fails.
%This is similar to datacenter-level distributed storage.
Such replication scheme is commonly employed in data center settings, and we use it as a baseline to compare to our decentralized scheme.

\paragraph{Repair traffic.}
We first simulate how much encoding repair traffic \sys generates, and compare it to the baseline replication approach.
We record the total number of repairing in the first year.
\autoref{fig:repair} shows the total repair traffic (in units of data object sizes) in the first year.
The different lines of \sys indicate the percentage of nodes that regenerate encoding fragment using the booster optimization (\autoref{sec:protocol:optimization}).
Repair traffic for \sys increases linearly with the total number of data objects.
When booster peers cache object perfectly, every repair only transfers $1/k$ of data object size, so the overall repair traffic is comparable to the replicated system.
However, when booster hit rate decreases, there is a sudden jump in the repair traffic due to the high ``cache miss'' penalty.
Concretely, repair traffic increases by 16.6x hit rate drops from 100\% to 75\%.
Beyond that, repair traffic only doubled from 75\% hit rate to 50\%, and doubled again when the booster optimization is turned off.
This demonstrates that our booster optimization is effective.
As such, incentives should be provided to encourage booster nodes to cache for a longer time to reduce repair traffic.
Fortunately, as shown later, most repairs finish quickly, so a short caching period can lead to good overall cache hit rate.

\autoref{fig:repair} shows total repair traffic in the first year with increasing AFR.
In both \sys and the replicated system, repair traffic grows linearly with AFR.
This demonstrates that \sys responds well to the change of the system's average AFR.
Another implication is that \sys scales well with an increase in AFT, i.e., the overhead per node failure remains constant.

\paragraph{Repair and redundancy over time.}
In the next simulation, we trace one data object for a duration of 10 years.
\autoref{fig:time} plots the raw capacity, i.e., the aggregated encoding size, a single data object occupies in the whole system.
As a reference point, capacity of a 3-way replication system is kept constant at 3.
\sys incurs less redundancy most of the time.
The short interval in which \sys incurs larger redundancy can be further reduced by aggressive redundancy reducing introduced in \autoref{sec:implementation}.
Note that although \sys deploys lazy repairing, comparing to the overall simulation time (10 years), the repair delay is still appears instantaneous.

The lower subplot of \autoref{fig:time} shows the accumulated repair traffic over 10 years.
The number of step increases taken by \sys is less than the replicated system.
This serves as a strong evidence that \sys performs repair more lazily than a replication system, and thus relies less on synchrony in the system.
As a comparison, \sys using an alternative parameter $k_{repair} = 1.6k$, thus tolerating 25\% more faulty peers, is also plotted in the graph.
Compared to the default parameter, object repairs happen more frequently, but still less than that of a replicated system.

\paragraph{Fault tolerance.}
To evaluate how well \sys tolerates adversaries, we simulate a network with Byzantine faulty nodes.
Byzantine faulty peers participate in gossip protocols; however, they do not store any encoding fragment.
A data object is consider permanently lost when the survived fragments drop below $k+\epsilon$ (for \sys) or no replicas are left (for the replicated system).
\autoref{fig:faulty} shows the number of lost objects in a one-year trace with a total of 1000 data objects.
This simulation verifies that a replicated system does not tolerance strong adversaries: the system starts to lose data as soon as a single faulty node appears.
On the other hand, \sys can tolerate a significant fraction of faulty nodes without losing data.
The degree of tolerance depends on the parameters.
Using the default parameter, \sys can tolerate around the targeted 33\% faulty nodes, while a more conservative configuration can improve tolerance further at the expense of increased redundancy.

\subsection{Global Deployment}

Next, we evaluate \sys using our real implementation.
We deploy 1000 -- 5000 \sys nodes on Amazon EC2 in 5 AWS zones (us-west, ap-southeast, eu-central, sa-east, af-south) across 5 continents.
All nodes run on c5a.24xlarge instances with 96 vCPU, 192GiB of memory, and a network bandwidth of 25GBps.

As mentioned earlier, we implemented a IPFS-like decentralized storage system using Kademlia DHT as a comparison system.
This Kademlia-based system serves as a state-of-the-art decentralized storage system.
Kademlia by default does not store data object, only metadata.
We therefore make a minimal extension to Kademlia to make the comparison fair.
When issuing \store, the client node pushes the object to a random peer in the network.
The peer then claims as the provider of the object by updating the publisher record in DHT.
Note that erasure coding, unfortunately, cannot be easily adapted into Kademlia.
We also deployed a Ceph cluster with one replication pool and one erasure coding pool, all with the stock configuration.
The cluster contains 5 servers, one in each region.
The Ceph cluster serves as a reference distributed storage system design.

In every run of the evaluation, to remove any caching effect, we spawn a fresh node as client.
Once the node successfully connects to the network, it issues a \store with a randomly generated object.
After the \store returns an object ID, another fresh node is spawned to issue a \query with the returned ID to retrieve the object.
The node performs sanity check to make sure the object is properly retrieved.

\paragraph{Latency Results.}

\begin{figure}
    \addgraph{latency}
    \caption{Latency of \store and \query operation in a world-wide deployment. Entropy, Ceph and Kademlia operate with 64MiB data objects while Entropy-1GB operate with 1GiB data objects.
    EntropyL-1GiB is a variant that finalize \store when received $k_p$ gossip messages.
    Dashed line and dotted line represent average latency of Ceph's replicated pool and erasure coding pool repectively}
    \label{fig:latency}
\end{figure}

We measure end-to-end latency of \store and \query operations for each system, and show the results in \autoref{fig:latency}.
For the default object size of 64 MiB, \sys outperforms both Kademlia and Ceph by a wide margin in latency.
Moreover, \sys also enjoys a much lower latency variance compared to Kademlia.
The better performance of \sys comes from its large code design.
In \sys, encoding fragments are uniformly distributed across many peers.
Fragment transfers thus can be done in parallel, utilizing the network bandwidth more efficiently.
Kademlia, in the contrary, requires the object to be sequentially transmitted to the remote peer.
The latency is therefore highly limited by bottleneck link bandwidth between the two peers.

The benefit of \sys's design is even more obvious with larger objects.
When we increase data object size by 16 times to 1 GiB, the latency is only doubled.
Kademlia, on the other hand, takes more than 120s to finish one operation due to sequential transmission.
We also measure a \sys variant with slightly reduced $k_p = 1.2k$ which tolerance less faulty peers on \store operations.
Its latency when storing 1 GiB objects is even close to Kademlia but with 64 MiB object size.

\paragraph{Latency breakdown.}
Compared to Kademlia, \sys requires less sequential peer communication, but performs extra encoding/decoding for an object.
Thanks to highly-optimized fountain code library, the coding latency overhead is surprisingly small: for 1GiB object, it takes only 4.2s from receiving the pull request from the first responsible peer, to send out all $k_p$ encoding fragments.
More than half of the duration is waiting for gossip dissemination, rather than generating fragment.
Fragment decoding latency is negligible, and after the node collects enough fragments to recover, actual object recovery only takes 1.2s.
For a comparison, computing SHA256 hash for a 1 GiB object takes 4.7s.
Actually, SHA256 hash computation is the major source of the additional latency when switching from 64 MiB to 1 GiB objects.
