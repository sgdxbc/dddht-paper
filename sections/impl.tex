\textbf{Determine eligibility.} Thanks to VRF, each peer can check for whether it is eligible independently, with transferrable authentication.
Similar to Algorand, peer calls $\{h, \pi\} = VRF_{sk}(H(obj), age)$, interprets the resulting hash $h$ as a floating number between $[0, 1)$, and check whether it falls in the binomial distribution's cumulative probability range $\textbf{Pr}(X \le k')$.
If the check is positive, the peer is eligible to take care of $obj$ for $age$, and the fragment it should store is the $h\ \textrm{mod}\ 2^{n}$-th fragment generated by fountain code.
Any peer receives the health proof can verify the peer's eligibility with $\pi$ and peer's public key.

\textbf{Verify fragments.}
The fragments received from peers can be individually verified thanks to homomorphic hashing.
Given $H(obj)$, the hash of the $i$-th fragment of $obj$ generated by fountain code can be derived.
Peer rejects the fragment if the hashes mismatch.
To avoid expensive homomorphic hashing operations, peers can do optimistic recovering.
It recovers the data object first, then check the hash of recovered object. If the hash is correct then recovery is successful.
Otherwise, it computes homomorphic hashes for each fragment and filter out incorrect fragments.
Then it fetches for more fragments and try to recover again later.

\textbf{Repair booster to reduce repair traffic.} One problem with \sys is that it can suffer from amplified network traffic caused by repairing.
Each responsible peer has to individually fetch $k + \epsilon$ fragments before storing, and it only stores one generated fragment.
This issue can be addressed by a set of repair booster peers, who fetch fragments, decode objects and generate fragments on behalf of responsible peers.
Thanks to VRF, booster peers can verify responsibility of peers. And thanks to homomorphic hashing, peers can verify the fragments generated by booster peers.
Booster peers do a best-effort caching after recovering data objects, so when later another fragment need to be generated for the same object, it does not need to fetch fragments again and significantly reduce repair traffic.
Any peer participants in \sys can behave as booster peer, but heuristically the peer who recently becomes responsible for an object is a good choice.
So we can extend the protocol as follows: \begin{itemize}
    \item A peer caches the recovered object for a while after generating its own fragment, and become a booster peer.
    Later we can introduce incentive to encourage such caching.
    \item In persistence proof gossip, an extra flag is included to indicate whether the peer can behave as a booster peer.
    \item Upon generating fragment, peer optimistically fetch the fragment from a booster peer if it knows any.
    If the booster peer is not generating correct fragment for it, the fallback vanilla algorithm is applied.
\end{itemize}
Notice that a faulty booster peer has no effect on object durability, but only can increase network usage.

\textbf{Select parameters.} A fixed $B$ is given such that at most $BN$ nodes are faulty where $N$ is the total number of nodes.
A proper repair threshold $k_0$

should be selected, and the VRF should be configured as 
(a) it selects at least $k_0$ peers for each epoch with high probability, so the peers do not observe unhealthy objects by false positive and repair too soon, and
(b) it selects at most $k_0/B$ peers for each epoch with high probability, so there's no more than $k_0$ faulty peers get selected in every epoch and ensure safety.
This implies $k_0$ should be sufficiently large so the range between (a) and (b) is large enough to make is possible to configure the VRF.
Finally, the $k$ should be selected so that 
(a) $k + \epsilon \le (1 - B - \beta)k_0$ where $\beta$ is determined based on a conservative estimation of AFR, and
(b) $1 - k/k_0 \le \alpha$ where $\alpha$ is the desired storage redundant rate.
