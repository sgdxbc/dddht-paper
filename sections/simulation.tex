\paragraph{What are we simulating?}
The simulated failures are not based on reality, as the realistic failure domains are hard to determine.
The simulated failures are probably more critical than in real, so it could act as an \emph{envelope} to the reality.

\paragraph{Simulation overview.}
Our simulation program consists of the operational model described in \autoref{sec:model} and an evaluated protocol that attempt to repair for the failures.
The simulation is performed in \emph{steps}, which is the virtual time unit determined by the responsiveness of the protocol.
Each step is simulated with two phases.
In the first phase, nodes fail and fresh nodes join according to the failure generator; in the second phase, the evaluated protocol performs arbitrary maintenance works.
The simulation collects key statistics per step, including average number of node failures per step (which derives average churn rate), redundancy \ie number of existing fragments of data, and most importantly, the number of alive data \ie data whose existing fragments can support recovery.
The simulation starts by populating certain number of data objects into storage network (along with other initialization, discussed later), which exact procedure is specified by the evaluated protocol.
Then the simulation repeatedly steps the system until maximum number of steps is reached or all data objects are lost.

\paragraph{Failure generator.}
In simulation is failure generator generates two kinds of failure domains.
The first kind is for independent failures, one failure domain for each node and contains only that single node.
The failure rate is the same across all first kind domains.
This kind of failures are the ``background'' failures that ensure every node eventually leave the system.
The second kind of failure domains contain at least two nodes and represent correlated failures.
The sizes of the failure domains follow geometrical distribution, so larger domains are rarer than smaller ones.
The failure rates of the failure domains follow exponential distribution, so higher failure rate is more unlikely.
Notice that failure rate is independent to the domain size: it is possible for large domain to have high failure rate.

We performed the simulation with different average domain size while keep the average node failure rate constant by adjusting the failure rate distribution accordingly.
With this setup the evaluated protocol experiences systems with similar churn rates, only varying correlations.

\paragraph{Evaluated protocol.}
We implement a decentralized storage protocol, similar to \sgd{cite}.
In this protocol, the fragments are stored on the $n$ consecutive storage nodes whose IDs are immediately after to the data hash, and the data is recoverable as long as $k$ of them is alive.
Most previous protocols if not all select placement groups with similar strategies that are optimized for performance.
We evaluate the protocol with different $n$ and $k$, simulating different placement group sizes and redundancies.
We also simulate a baseline protocol that only initially populates fragments to random nodes and does not repair.

\paragraph{Common system parameters.}
In the following, we simulate a storage system with 1K nodes.
All simulations last at most 1M steps and a $10^{-5}$ independent failure rate is applied to all storage nodes, in addition to the correlated failure rates.
Without further mentioning, a $n = 8$, $k = 5$ erasure code is deployed in both evaluated protocol and baseline.

\paragraph{Tolerate independent failures.}
We first simulate the case where only independent failures happen.
As shown in \autoref{fig:repair}, the evaluated protocol effectively tolerates the independent failures, aligning the conclusion from previous works.
Failure of individual nodes cannot cause data loss and the protocol immediately repairs for the failure in the same step.
There are chances that multiple independent failures happen in the same step, but the probability of simultaneous failures in the same placement group decreases exponentially as the number of failures grows.

\paragraph{Correlated failures.}
In the next simulations, we add correlated failures with different average domain sizes, but keep the average churn rate per step to 2\% of the total number of nodes.
As shown in \autoref{fig:domain-scale}, adding minimal correlated failures immediately results in data loss in the evaluated protocol.
The impact of correlated failure is huge.
When more than 1\% of storage nodes have correlations, the system fails catastrophically.

\paragraph{Scale up redundancy.}
In the next simulation we study the effect of increasing redundancy by scaling up $n$ while fixing $k$.
The result is shown in \autoref{fig:redundancy}.
Adding more redundancy works, but it also storage overhead to the system.
In our simulation the system is only durable in 1M steps when redundancy is increased over 37\%, results in significant degradation in capacity.

Can we affect durability without more redundancy?
We notice that as $n$ increases, not only redundancy but also placement group sizes is affected.
Larger placement group sizes help distribute fragments more widely, which also mitigates the impact of correlated failures.
Based on this observation, we perform the next simulation.

\paragraph{Scale up placement groups.}
In this simulation we keep a constant 1.6x redundancy, and increase both $n$ and $k$.
As shown in \autoref{group-scale}, the durability indeed gets better.
In our case, with $n = 24$ and $k = 15$ erasure code, the evaluated protocol is durable in the simulated duration without incurring additional redundancy.

\paragraph{Takeaway.}
Both redundancy and placement group size are the key factors of tolerating correlated failures.
Though redundancy is effective, it sacrifices system capacity, and previous studies also shows the effectiveness becomes marginal as redundancy grows.
\sgd{cite}.
On the other hand, increasing the placement group size does not affect the overall capacity.
Larger placement groups help the data objects ``escape'' correlated failures of smaller scales.
