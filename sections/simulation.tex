\paragraph{Simulation overview.}
Our simulation program consists of the operational model described in \autoref{sec:model} and an evaluated protocol that attempt to repair for the failures.
The simulation is performed in \emph{steps}, which is the virtual time unit determined by the responsiveness of the protocol.
Each step is simulated with two phases.
In the first phase, nodes fail and fresh nodes join according to the failure generator; in the second phase, the evaluated protocol performs arbitrary maintenance works.
The simulation collects key statistics per step, including average number of node failures per step (which derives average churn rate), redundancy \ie number of existing fragments of data, and most importantly, the number of alive data \ie data whose existing fragments can support recovery.
The simulation starts by populating certain number of data objects into storage network (along with other initialization, discussed later), which exact procedure is specified by the evaluated protocol.
Then the simulation repeatedly steps the system until maximum number of steps is reached or all data objects are lost.

\paragraph{Failure generator.}
The failure generator for simulation is under certain restrictions to enable practically efficient simulation.
Roughly speaking, in every step, the joining fresh nodes and the failed nodes are \emph{equivalent in the sense of failure domain}.
That is, there is a one-to-one mapping between the joining fresh nodes and the failed nodes so that, for each failed node, there is a joining node that take place in the failure domains that the failed node belonged to.
The failure rates of the failure domains are unchanged.
This simplification enables the simulation to be performed with failure domains set up a priori, and the nodes rotated in replace upon failures.
The simulation of systems with evolving failure generators \eg varying correlation degree or average failure rate would be upcoming research topic.

In simulation is failure generator generates two kinds of failure domains.
The first kind is for independent failures, one failure domain for each node and contains only that single node.
The failure rate is the same across all first kind domains.
This kind of failures are the ``background'' failures that ensure every node eventually leave the system.
The second kind of failure domains contain at least two nodes and represent correlated failures.
The sizes of the failure domains follow geometrical distribution, so larger domains are rarer than smaller ones.
The failure rates of the failure domains follow exponential distribution, so higher failure rate is more unlikely.
Notice that failure rate is independent to the domain size: it is possible for large domain to have high failure rate.

\paragraph{Evaluated protocol.}
We implement a decentralized storage protocol, similar to \sgd{cite}.
In this protocol, the fragments are stored on the $n$ storage nodes whose IDs are successive to the data hash.
Most previous protocols if not all select placement groups with similar strategies that are optimized for performance.
We also simulate a baseline protocol that only initially populates fragments to random nodes and does not repair.

\paragraph{Tolerate independent failures.}
Compare to baseline, the evaluated protocol tolerate independent failures perfectly.
Failure of individual nodes cannot cause data loss and the protocol immediately repairs for the failure in the same step.
There are chances that multiple independent failures happen in the same step, but probabilistic of simultaneous failures in the same placement group decreases exponentially as the number of failures grows.

\paragraph{Correlated failures.}
The evaluated protocol cannot tolerate correlated failures well.
Noticeably, as long as the average failure domain size is large enough, data loss happens even if the average node failure per step is less than the size of placement group.
In such case, although the failures rarely happen, each failure event may have large impact on the whole placement group to cause permanent data loss.

\paragraph{Discussion.}
More redundancy helps, but more fragments help more significantly.
To one's surprise, increase number of fragments help even without increasing redundancy (so each fragment get smaller).
By distributing to more nodes, the impact of each domain decreases quickly.
