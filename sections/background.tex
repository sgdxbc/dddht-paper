\section{Background and Motivation}
\label{sec:background}

In this section, we start with the problem definition of our system.
We then discuss prior solutions and their weaknesses in guaranteeing durability a decentralized environment.

\subsection{Problem Definition}
\label{sec:background:problem}

We consider the problem of \emph{durable} object storage system.
The system exposes a simple object store and retrieval interface to end users.
Each object contains a blob of binary data.
The system provides \emph{durability}: Once an object is successfully stored, the object can be \emph{eventually} recovered with its original content, even if part of the system fails.
Note that the guarantee differs from \emph{availability}, which ensures objects can always be retrieved in a \emph{timely} fashion.

Objects are \emph{immutable}, \ie, users cannot modify an object after it is stored.
The system presents a \emph{flat view} of all objects;
it does not offer explicit hierarchies such as those in a file system.
It serves as a base persistent storage layer where higher-level functionalities, such as files and relational databases, can be built atop.

Within the overall storage stack, we target the \emph{cold storage} layer which emphasizes \emph{data durability}, \emph{storage capacity}, and \emph{cost}, as opposed to the warm~\cite{f4} or the hot storage~\cite{haystack} layers.
Amazon Glacier~\cite{amazon_glacier,amazon_s3}, Google Coldline~\cite{google_coldline} and Archive~\cite{google_archive} storage, and the archive tier~\cite{azure_tier} in Azure Storage~\cite{azure_storage} are popular production-level, centrally managed systems in this category.
Performance and availability are not key design metrics.

\paragraph{\textbf{Deployment and failure model}}
Given the durability challenges of centrally managed storage systems (\autoref{sec:intro}), we target deployments in a \emph{decentralized} and \emph{open} network.
The deployment model mirrors existing permissionless blockchain systems such as Bitcoin~\cite{bitcoin} and Ethereum~\cite{ethereum}.
There is no central entity to manage or administer the system.
Participants of the network belong to different administrative organizations~\footnote{The model permits single-participant-organizations, effectively individuals joining the network.}.
They do not \emph{trust}, nor could they \emph{control}, entities outside their own organizations.
This ensures that the behavior of one organization cannot violate the durability guarantees of the system.

The network is \emph{permissionless}, \ie, anyone can join the network without any authorization required, and can leave at any time.
This open model typically leads to nodes distributed across geographical locations around the globe.
Each participating node has some local storage for storing data and network access to the wide area network.
There is, however, no requirement on the type, speed, or quality of their physical storage or network devices.

Storage devices can fail due to hardware issues or external events (\eg, natural disasters).
Once a storage device fails, all objects stored on the device are lost permanently.
Since the network is permissionless, a node can leave the system at any point;
the effect is identical to a failure to all its storage devices.
We also consider \emph{adversarial} participants in the network.
Adversaries can deviate arbitrarily from the storage protocol, including deleting any stored objects.
They may also collude and attack other \emph{honest} participants in the network.
Similar to other BFT work, we only make weak assumptions about the total attack power of the adversaries.
Note that recoverable transient failures, \eg, temporary network issues and node reboots, do not impact storage durability.

\subsection{Ensuring Durability}
\label{sec:background:durability}

Durability requires that stored objects are never \emph{lost}.
Data losses occur when the device storing an object fails, when the node hosting the device permanently fails or leaves the system, or when the object is intentionally erased.
Since these events occur regularly in large deployments, storage systems distribute copies of each object to multiple storage devices.
As long as not all devices storing a copy fail simultaneously, the object can be recovered.
To maintain the desired fault tolerance level, storage systems perform periodic repair to redistribute lost copies due to failures.

Simply replicating objects introduces large redundancy, which impacts the overall storage efficiency.
To reduce redundancy without compromising durability, modern storage systems apply erasure coding~\cite{google_storage,was,hitchhiker,xor}.
Erasure coding encodes an object into fragments.
A subset of fragments can be used to recover the original object.
In particular, maximum distance separable (MDS) codes, e.g., Reed-Solomon code~\cite{reed-solomon}, are a common choice.
Replication, in fact, is a simple form of erasure coding.

\emph{Placement group} is a critical design decision for storage systems.
A placement group consists of a set of storage devices.
The encoded fragments (or copies) of an object are distributed to devices within a placement group.
To ensure that the fragments are not lost simultaneously which leads to data loss, devices in a placement group should have low failure correlation.
The placement groups are either assigned by an operator in a centrally managed system, or decided by the storage protocol in a decentralized deployment.

\subsection{Prior Solutions}
\label{sec:background:relwk}

With the popularity of peer-to-peer file sharing networks in the late 90s, designing storage systems from a network of decentralized computers was an active research topic at the time.
Representative work during this period include xFS~\cite{xfs}, Farsite~\cite{farsite}, OceanStore~\cite{oceanstore}, CFS~\cite{cfs}, Glacier~\cite{glacier}, Carbonite~\cite{carbonite}, and IrisStore~\cite{irisstore}.
These systems aggregate storage capacity on computers across geographical locations to provide durable and available storage services.
Storage devices in the system are managed by mutually untrusted entities.
Distributed hash tables (DHT)~\cite{chash, chord} are commonly used to place and locate objects.
To handle correlated failures, some systems~\cite{oceanstore} apply introspection to predict failure correlations.

Departing from centralized deployment, handling unreliable and malicious participants is a key design goal.
 To provide data availability and consistency in the presence of Byzantine failures, they apply BFT protocols~\cite{pbft} to replicate file data and metadata to groups of servers.
 BFT protocols, however, require less than $1/3$ of the replication group to be Byzantine faulty.
 These solutions often sidestep the issue and sometimes rely on centralized, trusted certification authorities~\cite{farsite}, equivalent to a permissioned setting.
Limited by the hardware resources, those works focused on extending capabilities of single machine while still maintaining adequate durability.
The trend was quickly superseded by the centrally managed solutions as part of the emergence of cloud services.
\fi

Recently, there has been renewed interest in decentralized storage, following the success of blockchain systems such as Bitcoin~\cite{bitcoin} and Ethereum~\cite{ethereum}.
One example is IPFS~\cite{ipfs}, a widely deployed decentralized storage network that consists of more than 400 thousand peers globally.
IPFS divides user files into uniquely identified chunks.
File metadata is represented as a Merkle Directed Acyclic Graph (DAG)~\cite{merkle_dag} constructed from the constituent file chunks.
IPFS uses content addressing through the Kademlia~\cite{kademlia} DHT.
By writing to the DHT, peers storing a file chunk announce a publisher record which maps the chunk to the peer identifier.
The DHT replicates the publisher record to peers in proximity in the hash space and handles peer failures through gossip.
Retrieving a file involves querying the DHT for the publisher records and the address of the publishers for each file chunk.
IPFS, however, does not offer any file durability guarantee.
File content in IPFS is only stored on the original file publishers;
the protocol has no explicit redundancy mechanism to enforce file content durability.

\paragraph{Handling correlated failures}
As discussed in \autoref{sec:background:durability}, correlated failures can lead to data losses even when the storage system applies erasure coding and object repairs.
In a centrally managed systems, failure correlations are known to the operators;
they can therefore reason about failure domains with high accuracy in their deployments.
Decentralized environment, however, lacks global failure correlation information.
Without a reliable notion of failure domains, prior systems~\cite{xfs,farsite,cfs,glacier,carbonite,irisstore} assume failures in decentralized environments are independent.
As we demonstrated in \autoref{sec:simulation}, such assumptions can lead to significant data losses.
OceanStore~\cite{oceanstore} leverages introspection to predict correlated failures.
Prior research~\cite{glacier} has shown that accurate prediction of failure correlation is unrealistic in decentralized systems.

\paragraph{\textbf{Prior distributed storage systems.}}
There is a long line of work on centrally managed distributed storage systems~\cite{ceph,gfs,bigtable,dynamo,liquid}.
These systems commonly divide objects into equal-sized chunks, and deploy a large pool of nodes to store those chunks.
A dedicated set of nodes are responsible for maintaining and processing storage metadata.
It is also common to use a centralized consensus service such as Chubby~\cite{chubby} to manage configurations and other critical system states.

At the deployment scale of these systems, failures of storage devices, servers, racks, clusters, and even entire data centers are frequent events.
To guarantee data durability and availability, replication techniques such as primary-backup~\cite{pb} and state machine replication~\cite{smr} are commonly deployed.
However, replication introduces large redundancy, negatively impacting the overall storage efficiency.
To reduce storage redundancy without compromising data reliability, modern storage systems apply erasure coding~\cite{google_storage,was,hitchhiker,xor}.
In particular, maximum distance separable (MDS) codes, e.g., Reed-Solomon code~\cite{reed-solomon}, are a common choice.
Being centrally managed, the system administrator defines \emph{placement groups}.
Each erasure code strip (or replicas of an object) is mapped to one placement group.
To reduce the risk of data losses, placement groups are chosen to minimize correlated failures, where factors such as failure domains and annualized failure rate (AFR) of the storage devices~\cite{pacemaker,tiger} are usually considered.

These systems, however, only consider crash failures of individual components.
All participants of the system are under a single, protected administrative domain, so there is no requirement to tolerate Byzantine failures~\cite{bft}.

\paragraph{\textbf{State of the art decentralized storage.}}
With the popularization of peer-to-peer file sharing networks in the late 90s, designing storage and file systems from a network of decentralized, untrusted computers was an active research topic at the time.
Representative work during this period of time include xFS~\cite{xfs}, Farsite~\cite{farsite}, and OceanStore~\cite{oceanstore}.
Departing from centralized deployment, handling unreliable and malicious participants is a key design goal.
To provide data availability and consistency in the presence of Byzantine failures, they apply BFT protocols~\cite{pbft} to replicate file data and metadata to groups of servers.
BFT protocols, however, require less than $1/3$ of the replication group to be Byzantine faulty.
These solutions often sidestep the issue and sometimes rely on centralized, trusted certification authorities~\cite{farsite}, equivalent to a permissioned setting.

Recently, there has been renewed interest in decentralized storage, following the success of blockchain systems such as Bitcoin~\cite{bitcoin} and Ethereum~\cite{ethereum}.
One recent successful example is IPFS~\cite{ipfs}, a widely deployed decentralized storage network that consists of more than 400 thousand peers globally.
IPFS divides user files into uniquely identified chunks.
File metadata is represented as a Merkle Directed Acyclic Graph (DAG)~\cite{merkle_dag} constructed from the constituent file chunks.
IPFS uses content addressing through Kademlia~\cite{kademlia}, a distributed hash table (DHT)~\cite{chash,chord}.
By writing to the DHT, peers storing a file chunk announce a publisher record which maps the chunk to the peer identifier.
The DHT replicates the publisher record to peers in proximity in the hash space and handles peer failures through gossip.
Retrieving a file involves querying the DHT for the publisher records and the address of the publishers for each file chunk.
IPFS, however, does not offer any file durability guarantee.
File content in IPFS is only stored on the original file publishers;
the protocol has no explicit redundancy mechanism to enforce file content durability.
